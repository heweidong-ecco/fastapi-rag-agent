# `/specs` —— 模块规格对账

**用户输入**：`$ARGUMENTS`

---

## 第 1 步 · 永远先跑对账（**别凭记忆**）

```bash
bash scripts/spec_status.sh
```

它会告诉你三件事：
- ✅ **有 spec 的**（并列出它们**自报的状态**）
- 🔴 **没 spec 的** ← ⭐ **这些就是"别人不知道它存在 / 不知道做到哪"的模块**
- 🗑 **spec 有、代码没了** ← 模块删了，spec 残留

> ⛔ **不要把"没 spec"读成"这个模块没做"** ——
> 它只说明 **没人核过并写下"做到哪"**。**那本身就是信息。**

---

## 第 2 步 · 看用户要什么

### 情况 A · **没给模块名**（`$ARGUMENTS` 为空）

**就报到第 1 步为止。** 给用户：
1. **总数**（有 spec / 没 spec / 残留）
2. **没 spec 的按行数降序前 10**（大模块更值得先核）
3. **一句话建议**：「要我先核哪一个？」

⛔ **不要自动开始给所有模块写 spec** —— 那是几十份，**得用户挑**。

### 情况 B · **给了模块名**（如 `reranker`）

给**那一个模块**建/更新 spec。按下面走。

---

## 第 3 步（情况 B）· 读代码，写 spec

### 3.1 先读代码（**别照抄别的文档**）

```
api/<模块名>.py      ← 主文件，逐行读
```

**同时查这几处**（它们常有"看代码看不出来"的信息）：

```bash
grep -rn "<模块名>" --include="*.py" api/ | grep -v "^api/<模块名>.py"   # 谁在用它
grep -rn "<模块名>" --include="*.md" . | grep -v 归档                     # 文档里怎么说的
bash scripts/check_doc_orphans.sh --quiet >/dev/null 2>&1               # （顺带核引用）
```

⚠️ **本仓的白名单**：
- `ROADMAP.md` 的**功能现状表**（按功能）
- `docs/说明/测试.md` **§六 覆盖缺口**（这个模块是不是"零覆盖"）
- `后端补齐清单-待裁-20260929.md`（它有没有在 B1–B14 里）
- `docs/decisions/`（有没有裁过它）

### 3.2 写 spec（**照 `docs/specs/README.md` 的模板**）

```
docs/specs/<模块名>.md
```

**四节，第三节最重要**：

| 节 | 写什么 |
|---|---|
| 表头 | **状态**（✅完整 / 🟡部分 / ⬜未做 / ⚰️遗留）· 对外提供 · 谁在用 |
| ✅ 做了什么 | 功能 + **落点行号** |
| 🟡 做到哪 / 缺什么 | 缺的 + **它在哪个待办里** |
| ⭐ **⚠️ 看代码会误判的地方** | **读代码推不出来的那些** —— **这一节是整份 spec 的价值所在** |

> ### ⭐ 第三节怎么写（**这一节决定这份 spec 有没有用**）
>
> **判据**：问自己「**一个只看代码的人，会以为它是什么？实际是什么？**」
>
> 已写好的 8 份里有现成范例：
> * `reranker.md` —— 看着完整，**实际容器里跑不了**（镜像裁了 torch）
> * `hybrid_search.md` —— 看着是 RRF 实现，**实际是第二份**，且**测试测的是第三份副本**
> * `quota_limiter.md` —— 看着有限额，**实际匿名完全绕过**
> * `api_v1_rag.md` —— 看着 15 条正经端点，**实际 3 条是模拟测试**
> * `embedding_client.md` —— 看着配置齐全就能跑，**实际模块级 `OpenAI()` 会炸 import 链**

### 3.3 改完扫一眼

```bash
bash scripts/check_doc_links.sh --quiet   # 新 spec 里的路径对不对
```

**注意**：新 spec 会被 `check_doc_orphans.sh` 当成"孤儿" ——
⚠️ **它需要有人在 `docs/specs/README.md` 里指向它**，而那张表是**生成的**：

```bash
bash scripts/spec_status.sh --write       # ⭐ 重生成模块表 ⇒ 新 spec 自动被索引
```

---

## 第 4 步 · 回话

**给用户**：
1. **对账结果**（有 N / 没 M / 残留 K）
2. （情况 B）**这个模块的 spec 建好了** + **一句话说最要紧的那条"看代码会误判的地方"**
3. **建议下一个核哪个**

---

## ⛔ 三条禁令

1. **别凭记忆写** —— 「我记得这个模块是干 X 的」**不算证据**，**回去读代码**。
2. **别把"没 spec"当"没做"** —— 那是两回事。
3. **别一次写几十份** —— **用户挑**，或者写**大模块优先**的几个。
