# 四硬门 · 定义与验收标准（通用）

> **这份文档是「通用」的** —— 讲的是**方法**，不绑定任何具体项目。
> 项目侧的具体实现与差距，见 `fastapi-rag-agent/现状与差距.md`。
>
> **适用场景**：任何「我做了一个 AI 应用，想拿给别人自己点开看」的场合。
> 核心判据一句话：**写在文档里不算数，必须当场能演示、并且能被别人自己验。**

---

## 1. 为什么需要「能被别人自己验」的形态

一个人做出来的东西，天然存在一个信任问题：

| 你有的 | 缺的 |
|---|---|
| 代码、仓库、提交历史 —— **深度可能够** | **只有你能打开** |
| 文档里写了边界与限制 | **别人要读代码才能判断好坏** —— 成本太高，对方不会读 |
| — | **有些能力读代码根本看不出来** |

**最后一条是关键。** 举一个真实的例子：

> 你在代码里写了「中断」—— 对方读代码看到 `abort()`，**他没法判断后端到底停没停**。
> 可能前端停了、后端还在跑、还在烧钱。**这件事只有跑起来才知道。**

⇒ 所以需要把"我说我会"变成"**你自己看**"。

## 2. 验收三层（L0 / L1 / L2）

| 层 | 判定 | 硬指标 |
|---|---|---|
| **L0 有地址** | 一个能发出去的 URL | HTTPS、公网可达、**别人不看说明就能打开**（不需要注册、不需要你本地起服务） |
| **L1 四硬门能演示** | A/B/C/D 四个动作在浏览器里逐个走通 | 每个硬门有"证明是真的"的手段（见 §3），**不是口头承诺** |
| **L2 别人能自己验** | 把 URL 发过去，对方**自己点**也能验 | 不需要你在场解说；有独立可点的入口（trace 面板 / eval 面板 / 接管队列） |

> **L2 是真正的分水岭。**
> 常见的失败长这样：**「只有你能演示」** —— 你投屏讲一遍，对方点头；
> 链接发过去，他自己点，什么都复现不出来。

### 2.1 最终验收场景（通用模板）

> **对方收到一条链接，你不在场，他一个人能做完这 5 件事：**

1. 问一句 → **答案一个字一个字打出来**，他能切到 Network 看到那条连接**没断**
2. 点答案里的 `[1]` → **弹出原文、高亮命中段**
3. 生成到一半点 **"停止"** → 停住，且能看到 token 计数**停在哪**
4. 问一个敏感的 → **系统自己停下来**说"需人工确认" → 有个地方能看待接管、能批准
5. 看到一个 **Trace 面板**：每次调用多少 token / 多少钱 / 走了哪几步

**全程你不需要解说。** 这就叫"补上了"。

## 3. 四硬门逐个定义

图例：**判定** = 什么算过 ｜ **演示** = 当场要看到什么 ｜ **证真** = 怎么证明不是假的 ｜ **反例** = 会被抓穿的样子

### 硬门 A｜流式输出

| 项 | 内容 |
|---|---|
| **判定** | 答案逐字出现；DevTools → Network 里那条 `text/event-stream` **连接保持不关闭**、chunk 持续到达 |
| **演示** | 发一问 → 答案逐字出现 → **当场切 Network 面板，指着那条未关闭的连接** |
| **证真** | ① Network 里 chunk 时间戳**是递增的、不是一次性** ② 后端日志里那条请求的 token 计数**随 chunk 增长** |
| **反例** | 前端 `setInterval` 切字符 / 先拿完整 response 再假打字 —— Network 里是**一次性 response** |

> ⚠️ **最容易忽略的一种失败：中间层把流缓冲掉了。**
> 你的代码是对的、接口是 SSE、连接也在 —— **但中间那一层（代理/网关/隧道）缓存了 `text/event-stream`**，
> 对方看到的就是"一次蹦出来"。**这类问题只在真链路上才会暴露。**

### 硬门 B｜引用溯源

| 项 | 内容 |
|---|---|
| **判定** | 答案里的 `[1][2]` **点开能展开原文片段并高亮命中段**，再点能跳到原文位置 |
| **演示** | 问一个**库里确实covered**的问题 → 点 `[1]` 展开 → 高亮那段；<br>再问一个**库里没有**的 → **明确拒答**（说"资料中没有"，而不是编） |
| **证真** | 引用**由检索结果注入**、不是模型自由生成；点开能看到 **chunk id + 相似度分** |
| **反例** | 引用是模型自己编号的，点不开、或点开对不上原文 |

### 硬门 C｜生成中断

| 项 | 内容 |
|---|---|
| **判定** | 点"停止" → 前端停输出，**且后端 LLM 调用真的终止** |
| **演示** | 生成途中点"停止" → 前端立刻停 → **切到后端日志，展示那条 cancel 记录** |
| **证真** | 后端日志有 cancel 事件，**或 token 计数在该时间点停止增长** |
| **反例** | **只做前端 `abort()`，服务端还在烧 token** —— 账单继续涨 |

> ⚠️ **这是四门里最容易"假完成"的一个。** 实现要点：
> 很多框架在客户端断连时会向生成器抛 `GeneratorExit`/`CancelledError`，
> **但底层对上游模型的 HTTP 流不一定跟着停** —— 取决于那个 stream 是否活在正确的上下文里。
> **必须实测**（断连后看上游计费/日志），不能靠"我写了 abort"就当完成。

### 硬门 D｜人工接管

| 项 | 内容 |
|---|---|
| **判定** | 系统走到某步**主动停下**（低置信度 / 敏感操作 / 需审批）转人工；人工在同一会话回复；**系统拿回上下文继续** |
| **演示** | 构造一个会被判为需接管的请求 → 系统**自动暂停** → 接管队列出现待处理项 → 点开后**能看到完整上下文**、能改写答案 → 提交 → 续跑 |
| **证真** | 接管事件有记录（**谁、何时、为什么**）；接管后会话**上下文连续** |
| **反例** | 口头说"可以人工介入"，界面上找不到 |

## 4. 通用的"证真"原则（不止这四门）

四硬门之外的任何能力，都可以用同一套判据自查：

| 原则 | 说明 |
|---|---|
| **可复现** | 一条命令能重跑出同样的结果；**改一版必须附带"分数/指标变化"** |
| **可观测** | 能看到每一步：入参、出参、耗时、token、成本、有无重试降级 |
| **被外部触发过** | 对方**自己输入一个坏 case**（不是你准备的 happy path），系统不崩不空转 |
| **失败可解释** | 出问题能定位到是哪一步，不是"全都红了" |

> ❌ **统一的不合格长相**：
> 「只能演示你准备好的那 3 个问题」·「我这个效果挺好的」·「只有 console.log」

## 5. 优先级

> **A / B / C / D 是硬门，缺一个掉一档。**
> 其余（任务编排进度、工具调用可见、模型降级、成本可见、租户隔离、注入防护、评测、CI/监控）是分水岭 ——
> **决定你是"能做个应用"还是"能把应用做上线"。**

> 🔴 **另有一条不属于"演示能力"、但比上面全部更致命的：限额 / 熔断 / 可见提示。**
> 它**不会在演示时暴露** —— 你演示五分钟，什么问题都看不出来；
> 但它会在**你不知情的时候把账单烧穿**，或者让对方以为"你的系统坏了"。
>
> 属于「**关键功能必须开发**」，见
> `从代码完成到链接可分享-通用方法.md` **§7.1**（四层限额 + 熔断四要素 + 提示怎么写）
> 与 **§7.2**（"关键功能"的判据）。
