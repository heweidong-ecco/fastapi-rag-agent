# agent-eval-gate · 部署决策（**不上云**）

> **本文档记录一件事**：`agent-eval-gate` 要不要上云 / 部署。
> 结论与做法见下。**日期**：2026-09-24 ｜ **选定方案**：**方案 A**。
>
> **角色分工**：本文写**「应该做什么」与「做到什么算过」**；具体实施由项目侧负责。

---

## 0. 结论

> ### ⛔ **不上云，不部署。**
>
> 它的正确位置是 **本机 / CI**。
> 需要被展示的是它的**产出**（报告 · 分数 · trace），做法是
> **把报告渲染成静态 Eval 页**，跟主站一起托管。

---

## 1. 四条理由

### ① 它是一个 CLI 工具，不是一个服务

`agent-eval-gate/docs/部署.md` 自己写的：

> 「本产品是 **CLI 工具**（纯 CLI 竖切，签核 D-3），**零运行时依赖**（纯标准库），**无服务端、无数据库**。」

它的产出是 **退出码**：

| code | 含义 |
|---|---|
| `0` | 全绿 → 放行 |
| `1` | **block** → 阻断 |
| `2` | conditional / human → 人工复核 |
| `3` | 运行错误 / 熔断 degraded |

⇒ **把它包装成网页，是逆着它的设计走，也是自降身价** —— 它的说服力在**那四个数字**上。

### ② 它没有"别人点开用"的场景

> ⚠️ **关键区分**：
> **要上云的是「别人要自己点开验」的东西；评测是「你自己在改动前后跑」的东西。**
>
> 评测不是一个给别人点的功能，它是**你在自己这边把关**的手段。
> **它不属于「别人能自己验」要解决的问题。**

### ③ 部署成本 > 收益

**零运行时依赖** ⇒ 任何装了 Python ≥ 3.10 的机器上：

```bash
git clone <本仓> && cd agent-eval-gate
python3 -m venv .venv && .venv/bin/pip install -e '.[dev]'
./tools/setup-hooks.sh      # 必做，否则本地门禁静默失效
```

就能跑。**为它多养一台机器、多一份运维，收益是负的。**

### ④ 上云反而扩大攻击面

它要同时持有**被测的 Key** + **judge 端点的 Key**。

| 跑在哪 | 密钥风险 |
|---|---|
| 本机 / CI | 密钥不出本地 ✅ |
| 公网服务器 | **多一个泄漏点** —— 而这两把 Key **都能直接烧钱** ❌ |

## 2. 分工：什么上、什么不上

| 组件 | 上云？ | 为什么 |
|---|---|---|
| **`agent-eval-gate` 本体**（CLI） | ❌ **不上** | 没有对外服务的场景；零依赖，本机 / CI 足够 |
| **被测系统** `fastapi-rag-agent` | ✅ **上** | 它才是要给别人看的那个 |
| **评测的产出**（报告 / 分数 / trace） | ✅ **要展示** | 但方式是**静态页**，不是部署这个工具 |

> 💡 **一句话**：**不需要部署它，但需要展示它的产出。**

---

## 3. 它的正确位置是 CI —— 而且仓里已经备好了

仓里已有 **`.github/workflows/eval-gate.yml`**。
`docs/部署.md` 里写明了要点：

> 「**eval-gate 独立成 job**，不与代码门合并成一个绿灯；密钥走 CI secrets，不硬编码。」

⇒ **放在 CI 里跑，是它的设计用法**，而且**不花服务器一分钱**。

---

## 4. 方案 A 的做法

```
本机 / CI 跑 eval-gate
        ↓
产出：报告 JSON（逐条证据）+ trace JSONL + exit code
        ↓
把报告渲染成【静态 Eval 页】
        ↓
跟主站一起托管  →  别人点开就能看
```

**别人看到的是**：

- 这个系统**有评测门**
- 当前**分数是多少**
- **这一版比上一版好还是差**（对比箭头）
- 哪几条 case 失败了、失败原因

**这已经足够证明"有评测能力"**，而且：

| 收益 | 说明 |
|---|---|
| 零额外服务器成本 | 静态页跟主站一起托管 |
| 零额外攻击面 | 服务器上没有 judge 的 Key |
| 产出可展示 | 分数 / exit code / trace 都在页面上 |

---

## 5. 三种形态对比

| 方案 | 做法 | 评价 |
|---|---|---|
| **A（✅ 选定）** | 只在本机 / CI 跑；报告渲染成**静态 Eval 页**塞进主站 | ✅ 零额外成本 · 零攻击面 · 产出可展示 |
| B | 本机跑 + 报告放进 GitHub README | ✅ 更省，但展示效果弱 |
| **C** | 把它 **API 化部署成服务** | ❌ **不建议** —— 逆着设计走，且多一处 Key 泄漏点 |

---

## 6. ⛔ 要避免的做法

> **不要做「页面上点一下按钮，真的触发一次评测」。**

看起来很酷，但它意味着：

1. **服务器上要存 judge 的 Key** —— 攻击面扩大
2. **每次点击都烧 token** —— 而这跟每日额度熔断**会打架**
3. 熔断一来，评测也跟着挂 —— 把两个系统耦在一起

**正确做法：预跑 + 缓存结果。**
页面上是**只读的分数面板**，不是"评测触发器"。

> 📌 这条跟 `fastapi-rag-agent/施工单-本项目.md` §8.1 的**要求 R4**（成本与 token 可见）
> 与 §8.2 的**约束**（评估用的调用不占用、也不触发面向外部的每日额度）是同一件事。

## 7. 落地清单（项目侧）

| # | 事项 | 验收标准（做到什么算过） |
|---|---|---|
| 1 | eval-gate 在**本机**跑通一轮 | `python -m eval_gate run --evals eval/mini_rag_qa.evals.json --mode good --offline` → **exit 0** |
| 2 | 劣化输入**必须被拦** | 同命令 `--mode bad` → **exit 1** |
| 3 | CI 里能跑且**独立成 job** | `.github/workflows/eval-gate.yml` 生效；密钥走 secrets |
| 4 | 评测**产出落盘** | 报告 JSON + trace JSONL 可复现产出 |
| 5 | **Eval 静态页** | 页面可见：分数 + exit code + 与上一版的对比；**页面上没有"触发评测"的按钮** |
| 6 | 密钥**不在服务器上** | 线上主机上不存在 judge 的 Key |
