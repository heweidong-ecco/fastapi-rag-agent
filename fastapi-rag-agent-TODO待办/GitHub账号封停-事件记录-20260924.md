## 🔴 G8 · **"批处理"这个候选【至今没有证据】**（2026-09-30 · 业务方要求「③ 做」）

> ⇒ **这个问题本身值得留痕，因为它是"把一个未证实的猜测当成了已知风险"的典型。**

### 要把两个量分开

| | 是什么 | 会不会进风控视野 |
|---|---|---|
| **一个 commit 里有几个文件** | 一次提交的**内容** | ❌ **不会** —— GitHub 上每天百万量级，是**极普通**的开发行为 |
| **一次 push 推几个 commit** | 一次推送的**动作量** | ⭐ **这个才是"批处理"猜测指向的东西** |

### 本仓「批处理」这个说法的来源（**是本仓自己写的，不是 GitHub 说的**）

本文件 §原因分析 原文：
> 「封停是在**一连串全部成功的操作之后**落下来的 ⇒ **更像累计量 / 批处理**触发」

⚠️ **这是推测**。GitHub 只回了「abuse detecting systems」一句话，**没说命中哪一条**。

### ⇒ 留痕的目的：**防止把推测当事实**

| 写下来，免得下次 | |
|---|---|
| ❌ **不要再把「commit 多大 / 推了多少文件」当成已知风险** | 它**从来不是**被证实的触发因素 |
| ❌ **不要为它做"特殊处理"**（比如硬凑小 commit） | 那些是**没有依据的成本** |
| ✅ **要防的是 ①凭据**（本仓唯一有实锤的候选） | ⇒ 继续压凭据面（G2 / G7 / G6） |
| ✅ **「小批多次」照旧**（`DEC-039`） | ⚠️ **但它的理由是"没理由攒着"，不是"攒着会封号"** —— 别把它的理由也写错 |

> ### ⚠️ 一条**必须先确认**的
