# 未进demo/ —— 「已完成、可用、但没进 Demo」的归档区

> ⚠️ **这不是 `demo/`。** 两个目录**同级**，用途**相反**：

| 目录 | 是什么 | git |
|---|---|---|
| **`demo/`** | **正在做 Demo 的工作区**（含那份 `demo清单`） | ⛔ **已 gitignore ⇒ 不入库** |
| **`未进demo/`**（本目录） | **已完成 · 可用 · 但没能进 Demo** 的功能 / 代码 / 文档 | ✅ **入库**（业务方 2026-10-07 定） |

## 为什么本目录【入库】（而不像 `demo/` 那样 gitignore）

业务方原话（2026-10-07）：

> 「**未进demo/ 可以提交，让 clone 的人能知道这些是可用的，这是已完成的功能，不进 .gitignore**」

⇒ **目的**：**clone 的人**能看得到「**这个仓还做过这些**」，
**而不是以为"没进 Demo"就等于"没做"**。

⇒ 与 `demo/` 的分工：

* `demo/` = **当下的施工现场**（杂乱、会变 ⇒ **不入库**）
* 本目录 = **已完工的存量**（稳定、要给人看 ⇒ **入库**）

## 🔴 一条铁律：只进不出，**永不删除**

业务方原话（2026-10-07）：

> 「……**归到同一个文件夹下做好归类，存放好，避免直接删除**」

⇒ 内容**只会搬进来，不会从这里删掉**。
⇒ 真要淘汰某份 ⇒ **在这里再标一层「已废弃 + 原因 + 日期」**，⛔ **不是 `rm`**。
   （同仓立场：与 `docs/decisions/*`、`fastapi-rag-agent-TODO待办/归档/` 一样 —— **留痕不删**。）

## 归类（一份内容只进一个子目录）

| 子目录 | 放什么 |
|---|---|
| `代码/` | 可运行的代码 / 模块 / 脚本（Demo 里用不上的那些） |
| `文档/` | 说明 / 设计 / 分析 |
| `配置与部署/` | compose / Dockerfile / 部署脚本 |

> ⚠️ **子目录【按需创建】** —— **有第一份内容时才建**，⛔ **不预先摆空目录**。
> 📌 与本仓 `docs/` 一致：**先有内容，再有格子**（本仓立场：**不编空结构**）。

## 每份归档要带什么

搬进来时，**在同一处**写清下面四项：

1. **它是什么 / 能跑吗** —— ⭐ **这是重点**（clone 的人就是来看"**还能不能用**"）
2. **为什么没进 Demo** —— 平台限制 / 时间 / 不适合演示 / 依赖太重 …
3. **怎么用** —— 有依赖的，写清**怎么装、怎么起**
4. **日期 + 出处** —— 从哪搬来的
