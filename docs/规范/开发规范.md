# 开发规范

> ## 这份文档是什么
>
> **本仓「怎么写代码 / 怎么提交 / 怎么写文档」的规矩。**
>
> 🔴 **必须先说一件事**：
>
> ```
> 本仓【没有任何自动化的规范检查】——
> 没有 ruff · flake8 · black · mypy · pre-commit · editorconfig · pyproject.toml
> 唯一的自动门是 scripts/check_secrets.sh（凭据门）与 scripts/check_doc_links.sh（链接检查）
> ```
>
> ⇒ **下面的规矩全部是【靠人遵守】的，没有一条会被 CI 挡住。**
> ⚠️ **这不是好事** —— 它意味着"新人不会知道有这些规矩"（本仓在 skills 上吃过同样的亏：
> 「**门挂在别处，就等于没有门**」，见 `docs/复盘/2026-09-16-八个PR跳过了留痕门.md`）。
>
> 📌 **建议**（⬜ 待裁，见 §六）：至少加一个 `ruff` 的**最小配置**（只开 `E9`/`F` 这类真错误），
> 让"明显的错"自动被挡，而不是靠读这份文档。

## 一 · 代码规范

### 1.1 这些是**已存在的事实**（从代码里抽出来的，不是我希望的）

| 项 | 现状 |
|---|---|
| 缩进 | **4 空格** |
| 命名 | 函数 `snake_case` · 常量 `UPPER_CASE` · 类 `PascalCase` |
| 文件编码 | **UTF-8**，**注释用中文** |
| 导入 | 标准库 → 第三方 → 本地模块，**分组但无强制排序工具** |
| 类型注解 | 🟡 **部分有**（路由签名基本都有，内部函数常缺） |
| 文档字符串 | 🟡 路由函数**普遍有**（会显示在 `/docs`）；内部函数**不强制** |

### 1.2 注释：**本仓最有特色的规矩**

这不是"风格偏好"，是**本仓用血换来的**：

#### ⭐ 规矩 A · 注释写「**为什么**」，不写「**是什么**」

```python
# ✅ 本仓的写法（api/db.py:53-54）
# 注意：仅保留上方基于连接池的 get_db()（自动提交/回滚/归还连接）。
# 历史版本曾在下方重复定义 get_db() 覆盖连接池版本，导致写入不提交、连接池失效，已删除。

# ❌ 不会出现在本仓
# 定义 get_db 函数
```

**判据**：**删掉这行注释，后来的人会不会重犯同一个错？** 会 ⇒ 写。

#### ⭐ 规矩 B · 更正类注释要带**日期 + 出处**

```python
# ⚠️ 2026-09-20 删（§三·B7）：此处原有 `DB_CONFIG = {...}` —— **全仓零引用**
```

**格式**：`⚠️ YYYY-MM-DD <动作>（<出处>）：<原因>`
**出处**指：`DEC-0XX` / `§三·B7`（待办登记的节号）/ `复盘 <文件名>`

**为什么**：**注释也会过期**。带日期的注释**能判断它是不是还有效**；
不带日期的注释，后人只能猜。

#### ⭐ 规矩 C · 删除代码时，**留一行说明"删了什么、为什么"**

```python
# 50:# ⚠️ 2026-09-20 删（§三·B7）：此处原有 `DB_CONFIG = {...}`
```
而不是**静默删掉** —— 否则 `git blame` 到这一行时，看到的是一个凭空多出来的空行。

### 1.3 错误处理（**硬规矩**）

| 规矩 | 为什么 | 出处 |
|---|---|---|
| 业务错误一律 `raise AppException(ErrorCode.XXX, msg)` | 统一错误码与 HTTP 映射 | `CLAUDE.md` |
| ⛔ **中间件里【不许】抛 `AppException`** —— 必须直接返回 `JSONResponse` | `@app.exception_handler` **只捕获路由层**；中间件里抛会变成 **500** | 2026-08-17 修复记录 #12 |
| 数据库一律用 `get_db()` 上下文管理器 | 自动 commit/rollback/归还连接 | `api/db.py:36-48` |
| ⛔ **禁止直接创建原始数据库连接** | 会绕过连接池 | 同上 |

### 1.4 配置（**硬规矩**）

| 规矩 | 为什么 |
|---|---|
| 环境变量**从 `api/config.py` 导入**，⛔ 不要直接 `os.getenv` | 否则**本地/Docker 切换会不一致**（`config.py` 会按 `IS_DOCKER` 覆盖主机名） |
| ⚠️ **实测有 5 处违反** | 见 `docs/契约/环境变量.md` §三 —— **那是已知欠账，不是范例** |
| 敏感配置**不设默认值** | 启动时 `validate_config()` 缺了就拒启 ⇒ **fail-closed** |

## 二 · 提交规范

> 📌 **这一节的详细版在 `CLAUDE.md` 的「推送节奏」与「判据纪律」两节** —— 此处只列要点，不复制。

### 2.1 提交信息

**格式**：`<类型>(<范围>): <一句话>`

| 类型 | 用在哪 |
|---|---|
| `feat` | 新功能 |
| `fix` | 修 bug |
| `docs` | 只改文档 |
| `chore` | 杂项（依赖、配置、gitignore） |
| `refactor` | 重构（不改行为） |

**本仓的实际写法**（从 `git log` 看）：中文描述 + 必要时多行展开"为什么"。

### 2.2 **两个门的两问**（⛔ 每次 commit 都要答）

1. **「这次改动里，有没有在多个方案之间做过选择？」**
   有 ⇒ **建一份 `DEC-nnn`**（含备选方案 / 评估标准 / 反悔成本）
   无 ⇒ **在 commit message 里写明「本次无决策事项」**
2. **「CHANGELOG 写了吗？」** 没写 ⇒ **先补，再 commit**

### 2.3 推送节奏

* **本地 commit 随便攒**；**推送以「一个可验证单元」为界**（一个 PR 的活儿做完再推）
* ⛔ **`git` 挂了先分清「抖动」还是「拦截」** —— 处置相反（重试 vs 换通道）
* ⚠️ **本地 = 不 durable** ⇒ **当天结束前至少推一次**

> 📌 全文见 `CLAUDE.md`。

### 2.4 提交前跑这两个（**目前是唯一的两道自动门**）

```bash
bash scripts/check_secrets.sh        # 凭据门（扫 staged 的新增行）
bash scripts/check_doc_links.sh      # 链接检查（改了文档才需要）
```

> ⚠️ **凭据门的口径**：它**只扫 staged 的新增行**。没 `git add` 就跑，
> 会打印「staged 区为空」然后 **exit 0** —— **那不是"通过"，是"没扫"**。

## 三 · 文档规范

| 规矩 | 出处 |
|---|---|
| **一份文档只有一个权威** | `DEC-035` |
| **接口清单不写进文档** —— 跑 `scripts/list_endpoints.sh` | `DEC-036` |
| 文档按**四层**放（入口 / 契约 / 说明 / 过程） | `DEC-036` · `docs/文档地图.md` |
| **加/改文档后跑链接检查** | `scripts/check_doc_links.sh` |
| 改了文档要**同步 `docs/文档地图.md`** | 该文件 §五 |
| ⛔ **锚点/决策文档里写结论前，先 `grep` 一遍仓里有没有现成说法** | `docs/复盘/2026-09-29-…` 规则 3 |
| ⛔ **写「不存在 / 唯一 / 从来没有」时，必须附一条能打印出来的命令** | 同上 规则 1 |
| ⛔ **`grep` 出 0 命中时，先问「我的模式会不会漏」** | 同上 规则 4 |

> 📌 **后三条出自同一天的复盘** —— 那天**同一族错误犯了 3 次**。
> 复盘里写着：「**这不是某次不小心，是这套检查方法本身的盲区。**」

## 五 · 新加一个文件的检查清单

```
□ 它属于哪一层？（入口 / 契约 / 说明 / 过程）
□ 有没有【同一个问题】已经有文档了？（一份文档只有一个权威）
□ 它里面的路径引用是不是全的？（跑 check_doc_links.sh）
□ 它要不要在 docs/文档地图.md 里登记？
□ 改了行为的话，CHANGELOG 写了吗？
□ 做了选择的话，DEC 建了吗？
```

## 六 · ⬜ 本规范**没有**覆盖的（诚实清单）

| # | 缺什么 | 影响 |
|---|---|---|
| 1 | **无自动化检查**（无 ruff / black / mypy） | 全部规矩**靠人**，新人不知道 |
| 2 | **无 import 排序 / 格式化工具** | 各文件风格不完全一致 |
| 3 | **无类型检查** | 注解是"部分有"，且**没人验它对不对** |
| 4 | **无测试覆盖率门槛** | 见 `docs/说明/测试.md` |
| 5 | **无 commit message 的自动化校验** | 格式靠自觉 |
| 6 | **`docs/规范/` 目前只有这一份** | 还没有「命名规范」「API 设计规范」等 |

> 📌 **建议的下一步**（⬜ **待业务方裁**）：

> 这类是**真错误**，不涉及风格争论。
