## 二 · 承重事实（决定方案是否可行）

1. 子目录 `CLAUDE.md` 是**懒加载**：只在读写该子目录文件时注入；启动时只加载 cwd 及其父目录。根 `CLAUDE.md` 每次会话都进上下文。
2. 启动命令 `uvicorn main:app`，Docker 构建上下文 `./api`，容器内 `/app` 即 `api/` 的内容。
3. `api/*.py` 这个形状被四处硬编码：`pre-commit-gates.py` 第 ④ 道门（硬拦）、`spec_status.sh`、`spec-remind.py`、`route-auth-remind.py`。
4. `check_lint_baseline.sh` 的 ruff 基线按"文件名 × 规则号"记，文件一挪基线整份失效，必须重记。
5. `route-auth-baseline.txt` 按 URL 路径记，挪代码不影响。
6. `check_doc_links.sh` 只查反引号里的 `.md` 目标，`.py` 路径不在其射程内。

### 由此推出的五个"一挪就静默坏"的点

| 位置 | 症状 |
|---|---|
| `core/config.py` 的 `.env` 推算 | 挪进 `core/` 后读到 `app/.env`，静默落到代码默认值 |
| `core/logger_config.py` 的 `logs/` | 静默写到别的目录 |

| 30 个测试文件的 `Path(__file__)` 仓根推算 | 多一层，路径算错 |

## 三 · 容器名与嵌套层级的取舍

| 议题 | 结论 | 理由 |
|---|---|---|
| 容器叫 `packages/`？ | 否 | `packages/` 的语义是"多个可独立构建发布的包"，本仓是一个服务 |
| 套 `src/`？ | 否 | 本仓不 `pip install`、不发布 wheel；且 Docker `CMD` 与 154 个文件的 import 都绑在"`app/` 就是根"上 |
| `app/` 做成 Python 包（`from app.core...`）？ | 否 | 要 510 处导入改写 + Docker 构建上下文改到仓库根 + 新建仓根 `.dockerignore`（否则 927 MB 的 `venv/` 进 daemon）+ 一次 build 验证；而换来的不是缺陷修复 |
| `routing/` 改成 `api/`？ | 否 | 今天 `routing/` 与 URL `/api/v1/` 不撞名；改成 `api/` 会制造歧义（`app/api/api_v1.py` 会被导入成 `api.api_v1`） |

## 四 · 执行路径

业务方给的原始路径（16 步）与本轮的实际执行：

```
先核实项目大纲 → 出目录结构图 → 人工确认 → 建文件夹 → 建必备的空文档 → 移动文档 → 拆分文档
→ 移动代码文件 → 修改代码 import → 修复代码 → 修复守卫 → 修复项目级 .claude/*
→ 修复 ~/.claude 中与本项目有关的内容（人工确认） → 修复 CI → 修复配置文件 → 落盘
```

调整之处（已获授权）：

| 调整 | 原因 |
|---|---|
| **调序：代码先、文档后** | spec 的目标目录 `app/<组>/specs/` 要等 `app/` 拆完才存在 |
| **"修复守卫 / CI / 配置"不单独成步** | 它们的判据绑定路径，必须在同一段里跟着改，否则中间态必红 |

| **新增回归验证** | 原路径没有；"拿动作成功当结果正确"是本仓栽过多次的坑 |
| **拆 `docs/文档地图.md` 从"文档段"移到"索引段"** | 它要被分发到的正是各层 `CLAUDE.md`，之前没有落点 |
