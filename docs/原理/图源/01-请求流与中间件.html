一次请求怎么走 —— 中间件顺序陷阱

本仓最容易写错的一条：中间件的【执行顺序】与【源码顺序】逐层相反。 判据：import main 后打印 app.user_middleware。

① 实际执行顺序（洋葱由外向内）

客户端HTTP / WS
→
1文本规范化TextNormalizationMiddleware
→
2配额QuotaMiddleware · 每请求查一次 PG
→
3限流RateLimitMiddleware · Redis 令牌桶
→
4日志 / 指标log_and_track_request
→
路由3 张路由表

② 源码顺序（main.py）—— 逐层相反

第 1 个 add日志 / 指标
→
第 2 个 add限流
→
第 3 个 add配额
→
第 4 个 add文本规范化
add_middleware 内部是 user_middleware.insert(0, …)，而洋葱用 reversed() 包 ⇒ 最后 add 的在最外层、最先执行。

③ 由此产生的两个可观察后果

被拒的请求（429）走这条出口 从 ②配额 或 ③限流 直接返回 ⇒ 不经过 ④
⇒ 不进 Prometheus 指标 · 没有 X-Request-ID 响应头（那头在 ④ 里才加）。
📌 查「为什么某次 429 在指标里看不到」—— 先看这条。
配额那一层现在要查 PG（2026-10-03 起）—— 它排在最外层第 2 位， ⇒ 每个请求（含最终被限流拒掉的）都要先付一次 SELECT SUM(…) 的代价。 ⚠️ 旧实现是 Redis INCR，原先没有这笔开销。

④ 进到路由之后 —— 依赖先鉴权，再进业务

路由匹配
→
鉴权依赖API Key / JWT → 身份 + 角色
→
业务检索 / Agent / 记账 / 管理
→
存储PG(pgvector) · Redis
⚠️ 不是所有路径都有鉴权 —— 无鉴权路由清单跑 scripts/check_route_auth.py（基线另存）。

⑤ 启动时（startup，严格按此顺序）

#做什么注意
1validate_config()缺 4 个必填键 ⇒ 抛错 拒绝启动（fail-fast）
2init_pool()必须早于 3（建表要连接）
3create_table()—
4ensure_admin_exists()—
5warmup_cache()同步阻塞 · 逐个调 embedding（10 个热点查询）
6run_health_check()同步等待 · 每个工具起一个 MCP stdio 子进程
7定时健康检查之后每 120 秒一次
⚠️ 5 与 6 都阻塞 ⇒ 启动慢。另有 /ready 要求"启动满 10 秒"，那是另一道门，与 startup 无关。
