## 一 · `documents` —— RAG 知识库 ⭐

```sql
CREATE TABLE IF NOT EXISTS documents (
    id           SERIAL PRIMARY KEY,
    content      TEXT NOT NULL,
    source       TEXT,
    embedding    vector(1536),                        -- pgvector
    requested_by TEXT NOT NULL DEFAULT 'anonymous'    -- 归属人
);
```

| 字段 | 说明 |
|---|---|
| `id` | 自增主键 |
| `content` | 文档正文（**分块后的块**，不是整篇） |
| `source` | 来源标识。实测形态如 `eval_dataset.json#23` · `eval-gap-fill-*` |
| **`embedding`** | **`vector(1536)`** —— 由 DashScope `text-embedding-v2` 生成。⚠️ **维度写死在建表语句里**，换 embedding 模型**必须改这里** |
| `requested_by` | 归属用户名。默认 `'anonymous'` |

> 🔴 **⚠️ 多用户隔离是【打折的】**：注释写着「所有查询和修改都带上当前用户的 ID 进行过滤，
> 从而实现多用户数据隔离」—— **但实测多数检索端点没有按它过滤**。
> 这条业务方已裁「**不动**」（属 M5 裁决范围），登记在 `ROADMAP.md` **T7**。

### 索引（**实测活库**）

```sql
documents_pkey             CREATE UNIQUE INDEX ... USING btree (id)
documents_requested_by_idx CREATE INDEX ... USING btree (requested_by)
documents_embedding_idx    CREATE INDEX ... USING hnsw (embedding vector_cosine_ops)   ← ⚠️ 见 §四
```

## 二 · 认证 · `api_keys`

```sql
CREATE TABLE IF NOT EXISTS api_keys (
    id         SERIAL PRIMARY KEY,
    user_name  TEXT NOT NULL,
    key_hash   TEXT NOT NULL UNIQUE,     -- ⭐ 存的是 SHA256，不是明文
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    expires_at TIMESTAMP NOT NULL,
    is_active  INTEGER DEFAULT 1         -- 可空：老行为 NULL，COALESCE 放行
                                         -- 🔴 是 INTEGER(0/1)，⛔ 不是 BOOLEAN：
                                         --    `issue_api_key.py --revoke` 写 `SET is_active = 0`
);
```

> ### 🔴 这一列在真库里**曾经不存在** —— 2026-10-06 实测更正（`DEC-086`）
>
> 原文写「字段全集 = 上表 5 个 + `is_active`（**由迁移 `828721f77ef2` 加上**）」。
> **那句是错的**：本仓**没有** `alembic.ini`、没有 `migrations/`、全仓**没有任何 DDL 加过这一列**
> —— 那个迁移在真库上**从没生效**。
>
> **实测证据**：真库 `api_keys` 只有 5 列；`api/auth.py:105` 那句中带 `COALESCE(is_active, 1) = 1`
> ⇒ `UndefinedColumn: column "is_active" does not exist`
> ⇒ **每次 API-Key 认证 503**，且限流/额度两道闸**同时 fail-open**。
>
> ⇒ **本表口径改了**：这一列的**唯一来源是本仓 DDL** ——
> `api/db.py` 建表语句 + 启动期那句 `ALTER TABLE api_keys ADD COLUMN`（老库补列）。
> ⚠️ **⛔ 别再写成「由某个外部迁移加上」** —— 那种写法让代码与文档**一起**假设了一个不存在的前提，
> 而用例用**自建的表**跑（自带这一列）⇒ **一条都不会红**。
>
> ✅ 同时更正下文那句：`verify_api_key()` **现在会过滤 `is_active`**（`DEC-085` 契约 D，
> 用 `COALESCE(is_active, 1) = 1`，所以 `NULL` 的老行**照样通过**）。
> 📌 原先记在这里的「核查新发现 ④（停用不生效）」已闭合。

## 三 · 计量 · `token_usage_logs` / `cost_records` / `cost_records_archive`

**三张表结构高度相似**（后两张是前一张的展开），都是**按用户/线程/用途**记账。

### `token_usage_logs`（487 行）

```sql
CREATE TABLE IF NOT EXISTS token_usage_logs (
    id                SERIAL PRIMARY KEY,
    user_name         TEXT NOT NULL,
    thread_id         TEXT DEFAULT 'unknown',
    model             TEXT NOT NULL,
    purpose           TEXT NOT NULL,
    prompt_tokens     INTEGER NOT NULL,
    completion_tokens INTEGER NOT NULL,
    total_tokens      INTEGER NOT NULL,
    cost              REAL NOT NULL DEFAULT 0.0,
    created_at        TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);
```

**索引**（3 个）：`user_name` · `created_at` · `thread_id`

### `cost_records`（487 行）—— 比上面多「拆开的费用」

在 `token_usage_logs` 的字段基础上，把 `cost` 拆成
**`input_cost` / `output_cost` / `total_cost`**（三个 `REAL`），
并加了 **`tool_name` / `tool_args`**（工具调用的参数留痕）。

**索引**（4 个）：`user_name` · `created_at` · `thread_id` · `purpose`

### `cost_records_archive`（0 行）

**与 `cost_records` 字段完全一致** —— 是它的归档表。
⚠️ **目前是空表**，且**唯一的操作者是 `archive/scripts/data_retention.py`**（**未入库**）。
⇒ **不跑那个脚本，这张表永远是死的**。业务方待定（`DEC-022` §遗留①）。

> 🔴 **⚠️ 计费口径有一条已知不准**：`api/token_tracker.py:48-52` 的 `PRICING` 表
> **只有 qwen 系列，没有 DeepSeek 条目** ⇒ DeepSeek 调用**走兜底单价** ⇒ **金额偏低**。
> ✅ **Token 口径不受影响**（80% 预算预警仍然准）。

## 四 · 预算拦截 · `budget_intercepts`

```sql
CREATE TABLE IF NOT EXISTS budget_intercepts (
    id         SERIAL PRIMARY KEY,
    user_name  TEXT NOT NULL,
    tool_name  TEXT,
    reason     TEXT,
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);
```

⚠️ **建表方式与其余 5 张【不一样】**：这张是**惰性建表** ——
建表语句写在 `api/token_tracker.py:617` 的 `record_intercept()` 函数里，
**第一次发生拦截时才建**。其余 5 张在 `create_table()` 里、**启动时统一建**。
📌 **不一致，但无害**（有 `IF NOT EXISTS`）。

## 五 · 🔴 三套建表机制并存（**这是缺口**）

| 机制 | 在哪 | 覆盖 |
|---|---|---|
| **① 启动时 `create_table()`** | `api/db.py:56-174`，由 `api/main.py:491-495` 的 startup 事件调用 | 5 张表 + 全部索引 |
| **② 惰性建表** | `api/token_tracker.py:617` | `budget_intercepts` |
| **③ Alembic 迁移** | `api/alembic/versions/` | **只有 3 个**（见下），**与 ①② 不同源** |

**Alembic 现有 3 个迁移**：

```
f12a761ae626_init.py                        ← 初始
d171778a3bff_add_usage_logs_table.py        ← 加 token_usage_logs
828721f77ef2_add_is_active_to_api_keys.py   ← 加 api_keys.is_active
```

> 🔴 **问题**：**Alembic 覆盖不到 `cost_records` / `cost_records_archive` / `budget_intercepts`**，
> 而 `create_table()` 又**不是幂等迁移**（它只有 `IF NOT EXISTS`，**不能改列**）。
> ⇒ **改表结构时"该改哪一处"没有答案** —— 这是本仓的一条**结构性欠账**。
>
> ⬜ **建议**（未做）：把 `database/` 纳入文档体系时一并定：**以 Alembic 为唯一迁移入口**，
> `create_table()` 降级为"首次初始化"。

## 六 · 🔴 代码与活库**不一致**：向量索引类型

| | 类型 |
|---|---|
| **代码**（`api/db.py:97-101`） | `USING **ivfflat** (embedding vector_cosine_ops)` |
| **活库实测**（2026-09-29） | `USING **hnsw** (embedding vector_cosine_ops)` |

**为什么会不一致**：那句是 `CREATE INDEX **IF NOT EXISTS**` ——
**活库里那个 `documents_embedding_idx` 早就存在**（手工建的 **hnsw**）
⇒ **代码里写的 `ivfflat` 从来没有生效过。**

### ⚠️ 后果（**上云会踩**）

```
本机（已存在 hnsw 索引）  →  代码那句被 IF NOT EXISTS 跳过  →  继续用 hnsw
云上（全新库、无索引）    →  代码那句【真的执行】          →  建出 ivfflat
```

⇒ **上云后索引类型会与本机不同** ⇒ **检索性能特征不一样，且没人会注意到**。

### ✅ 两条处置（**待裁**）

| 选项 | 说明 |
|---|---|
| **甲** | **把代码改成 `hnsw`** —— 与活库对齐。⚠️ 需确认 pgvector 版本支持（hnsw 需要 pgvector ≥ 0.5.0） |
| **乙** | **把活库改成 `ivfflat`** —— 与代码对齐。⚠️ ivfflat **需要先有数据才能建好**（要 `ANALYZE`），而 hnsw 不需要 |

> 📌 **`DEC-034` §遗留③ 早就记了「索引是 hnsw」**，但**它没说"代码里写的是 ivfflat"** ——
> 那是这次写文档时才发现的（**建档本身发现了问题**）。
> ✅ **已登记**：`ROADMAP.md` 待办总账。

## 七 · 本仓数据层的既有约定

| 约定 | 出处 |
|---|---|
| **一律用 `get_db()` 上下文管理器** —— 自动 `commit` / `rollback` / 归还连接 | `api/db.py:36-48`。⛔ **禁止直接创建原始连接** |
| 连接池 `ThreadedConnectionPool`，min/max 由 `DB_MIN_CONN`/`DB_MAX_CONN` 控制（默认 2/30） | `api/config.py:77-78` |
| **建表在应用启动时自动做** —— 不用手工执行 DDL | `api/main.py:491-495` |
| **Redis 里还有一份"数据"**：Embedding 缓存（`emb:*`，24h）· 对话历史（`chat_history:*`，24h，只留最近 5 轮） | `api/cache.py:17/27/36/43` |

> ⚠️ **对话历史【只存 Redis，不落库】** ⇒ **进程重启即丢**。

## 八 · ⬜ 已知缺口

| # | 缺口 | 影响 |
|---|---|---|
| 1 | **无 `schema.sql`** | 表结构只存在于代码里；**这份文档就是补它的**（但它是**手写的**，会漂移） |
| 2 | **无外键** | 表之间没有任何 FK 约束 |
| 3 | **无软删除 / 无 `updated_at`** | `documents` 删除是硬删（`DELETE /rag/documents/{doc_id}`） |
| 4 | **多用户隔离打折** | `requested_by` 多数检索端点不过滤（业务方裁「不动」） |
| 5 | **`api_keys.is_active` 不生效** | 代码查询没过滤它 |
| 6 | **Alembic 覆盖不全** | 见 §五 |
| 7 | **向量索引代码/实况不一致** | 见 §六 |

> 📌 **1 的补法**：可以写一个脚本从**活库**导出 `pg_dump --schema-only`，
> 那样**永远不会漂移**（同 `list_endpoints.sh` 的思路）。⬜ **未做**。
