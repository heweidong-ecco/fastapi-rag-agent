## 二、规则正文（三条）

### 规则 1 · 每条规则必须写明**它绑在哪个仓库的哪个路径上**

判据不接受"文件名的自然语言描述"，必须是**可验证的路径**。

| ❌ 不接受 | ✅ 接受 |
|---|---|
| 「对照阈值文件」 | `agent-eval-gate/eval/阈值.md` |
| 「改了 prompt 相关文件」 | `api/answer_with_citations.py` · `api/query_rewriter.py` |
| 「跑回归」 | `eval_gate run --evals <path> --mode good`（在 `agent-eval-gate` 仓库执行） |

**为什么**：路径是**可检验**的（存不存在，`ls` 一下就知道）；自然语言描述**不可检验**，
于是它可以永远"看起来在跑"。

#### 🔴 规则 1 补 · **路径还必须声明「根」**

> **本补充来自一次真实误判**（2026-09-17，见 `docs/skill-适配体检-2026-09-17.md` 第三节）。

**光有路径不够。** `eval/阈值.md` 这种写法**不算绑定** —— 它在任何一个仓库里都可能存在。

**必须写成 `<根>/eval/阈值.md`**，`<根>` 是**可验证的绝对路径或仓库名**。

**判据**：**「把这个路径拿给另一个人，他能不能不靠猜就找到那个文件？」** 不能 ⇒ 没绑定。

**并且**：**同一个 skill 里不许混用两个根而不声明。**
反例 = `留痕-checks`：check 7 的路径相对 `agent-eval-gate`，
而同一处跑的 `git grep` 是相对**当前仓库** —— **两套根混在一句话里**，执行者只能猜。

> ⚠️ **我自己就是那个执行者，而且猜错了。** 我体检时只拿路径去对两个根
> （skill 自身目录、当前仓库），对不上就判"不存在"，**报了 3 个误报**。
> **判据不全，结论就是错的** —— 这与本规则要防的问题**同构**。

### 规则 2 · 绑不上的，必须标 `⬜ 待适配`；**没有替代判据就标 `⛔ 无法执行`，不许当作通过**

一份规则挂到新仓库时，凡是有路径在本仓**不存在**的，逐条标出来：

| 情况 | 标记 |
|---|---|
| 有明确的替代判据可用 | `⬜ 待适配` + **写明替代判据是什么** |
| **没有替代判据** | **`⛔ 无法执行`** —— **不当作通过** |

**禁止**：静默地把判据翻译成"我觉得差不多的意思"，然后照常输出"通过"。

> **裁决（业务方 2026-09-17）**：「标 ⛔ 无法执行，不当作通过」。
> **理由：宁可红着，不可空转。** 报表上看得见缺口，才会有人去补；
> 绿着的空转比红灯更贵，因为它消耗的是**信任**。

**理由**：**静默替换判据 = 门在空转，但报表上是绿的** —— 比没有门更糟。
这与本仓已记过的教训是同一条：
> `api/LEARNING_INDEX.md` 定义过一整套治理格式，**全仓 0 个文件使用、0 个文件引用它**。
> **有格式，没接线。**

### 规则 3 · 规则只做**加法**时，必须同时给出**删除条件**

新加一条规则时，同时写清：**什么情况下这条规则应该被删掉。**

**为什么**：这是本仓 `Product/CLAUDE.md` 里已经写过的减法优先原则
（「谁提的 / 删了谁会要加回」）在规则层的翻版。**只增不减的规则集，最后会变成没人读的墙。**
