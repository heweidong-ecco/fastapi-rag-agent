## 决策事项

`DEC-026` 把执行层改成**真调用工具**之后，§14.2 第 4 项列的「**超时 / 成本 / 失败重试 / 权限**」
那一串**必须一并解决**。怎么解决？

## 🔴 动手前实测：三个问题是**同一个洞的三个面**

`/agent/plan_execute` 对**任何登录用户（含 free）**开放，而它现在**真跑**：

| # | 实测发现 | 后果 |
|---|---|---|
| **①** | **`MAX_EXEC_TIME` 只被定义、从未被使用** —— `grep` 全文只有第 82 行的定义；实测 `while True: i += 1` **永不返回** | 死循环**挂住 worker 线程**；而工具描述却对 LLM **承诺**「最长执行时间：5秒」 |
| **②** | **`/agent/plan_execute` 完全不查预算、不记账**（0 处引用 token/cost/budget） | 真跑 LLM 却**账上一行不记** ⇒ **免费用户的 100 次/天配额管不到它** |
| **③** | 端点用 `get_current_user_hybrid` ⇒ **任何登录用户可调**；而 `execute_python` 是**代码执行** | 结合 ①②：**一个 free 用户可以让服务器跑死循环 + 烧 LLM 钱** |

📌 **对照**：2 代 `/agent/mcp_chat` **有** `check_token_budget` + `record_usage`（`agent_graph_advanced.py:303/315`）——
**3 代这条 Plan-and-Execute 路从来没有**。

⚠️ **这三条以前都不痛**，因为执行层是「LLM 模拟执行」：写什么都不真跑。
**`DEC-026` 一上线，它们同时从"纸面问题"变成"现实问题"。**

## ① 超时 —— 机制选择（唯一真正需要裁的）

**"真正的超时"在 Python 里只有一个可靠做法 —— 放子进程、超时硬杀。另外三条路我都核过，都不成立：**

| 机制 | 为什么不行 |
|---|---|
| `signal.alarm` | ⚠️ **只在【主线程】有效** —— MCP 服务端用 `asyncio.to_thread(handler, args)` 调工具 ⇒ 执行在 **worker 线程**，alarm 装不上 |
| 线程 + `join(timeout)` | **杀不掉 Python 线程** ⇒ 线程照跑，只是"你以为超时了"（**假超时** —— 比没有更糟，它给了错误的安全感） |
| `PyThreadState_SetAsyncExc` | 对**紧循环不可靠** —— 拿它当安全承诺的地基不诚实 |
| **子进程 + `terminate()`** ⭐ | ✅ **唯一能真正打断死循环的** |

**采纳子进程。** 收益不止超时：

- **全新解释器** ⇒ 隔离更强（比"同一个进程里关在 dict 里"强）
- 白名单**从同一个模块重建**（子进程 `import code_executor_impl`）⇒ **单一事实源，不会漂**
- 子进程**崩了（段错误 / OOM）带不走主进程**

**代价（如实记）**：每次调用多一次进程启动 —— **实测 ~56 ms**（比预估的 100ms 好）。
**判据**：对"执行代码"这类工具完全可以接受。

**同时给 `web_search` 加了 HTTP 超时**（`SEARCH_TIMEOUT_SECONDS = 20`，含兜底那条路）——
此前 `client.chat.completions.create(...)` **没有任何 timeout**。

## ② 成本 —— 照抄 2 代的模式，不另起炉灶

新增一个**统一的 LLM 调用入口** `_invoke_llm()`：**查预算 → 调用 → 按 `usage_metadata` 记真实用量**。
📌 与 `agent_graph_advanced.py:303/315` **同一套**，只是包成一个入口，免得在四个调用点各抄一遍。

| 做法 | 采纳 | 理由 |
|---|---|---|
| **甲 · 记账放端点层**（只做事前事后） | ❌ | `plan_execute` 会跑 **N 次** LLM（1 规划 + 每步 ×2），端点层**拿不到每步的真实 token** ⇒ 只能估 |
| **乙 · 在每个调用点各抄一遍** | ❌ | 四处重复，下次加调用点必然漏 |
| **丙 · 统一入口 `_invoke_llm`** ⭐ | ✅ | 单一入口 ⇒ 加新调用点**不可能漏记账** |

**`user_name` 显式贯穿**（7 个函数加形参），**不用 contextvar** —— 本仓重视显式，
且隐式上下文会让"配额算在谁头上"变得难以验证。

**新增三个 purpose**（`PURPOSE_ESTIMATED_TOKENS` / `PURPOSE_ESTIMATED_COST` **两套都加**——
本仓规矩：两套表并存、不可互相替代，见 `DEC-002`）：
`plan_execute.plan` · `plan_execute.dynamic_input` · `plan_execute.quality_check`。

**⚠️ 无 `usage_metadata` 时【如实不记】** —— 不编一个数字塞进账里（已写成用例）。

## ③ 权限 —— **本次【不动】权限**

**理由**：收窄"谁能用代码执行"是**产品决策**（谁能用、free 该不该能），不是技术修法。
而 **② 的记账让配额真正生效** ⇒ 免费用户的 100 次/天**现在管得到了** ——
**这是比"一刀切收窄"更精确的手段。**

⇒ **权限收窄留作独立选项，本次未做。**

## 顺带修掉的一个真问题：**端点阻塞事件循环**

`plan_task` / `execute_plan` 是**同步**的，而端点是 `async def` ⇒ 直接在事件循环里调会
**阻塞整个 API**。以前执行快所以不痛；**真调工具之后会真发网络请求，代价立刻显形。**

⇒ 改成 `await asyncio.to_thread(...)`（同型先例：`/agent/fetch_webpage` 那两个端点）。

## 执行内容

| 文件 | 改动 |
|---|---|
| `api/code_executor_impl.py` | 执行搬进**子进程**（`_SANDBOX_CHILD`）；超时**硬杀**；白名单从本模块重建；删掉因此变成未使用的 `io`/`contextlib` |
| `api/search_tools.py` | 两处 `client.chat.completions.create(...)` 加 `timeout=SEARCH_TIMEOUT_SECONDS`（20s） |
| `api/token_tracker.py` | 两套预估表各加三个 `plan_execute.*` 条目 |
| `api/plan_execute.py` | 新增 `BudgetExceededError` + `_invoke_llm()`；7 个函数加 `user_name`；3 个裸 `llm.invoke` 全部换掉 |
| `api/api_v1_agent.py` | 端点传 `user_name`、`asyncio.to_thread`、接住 `BudgetExceededError` → `QUOTA_EXCEEDED` |

## 验证（可复跑）

| 判据 | 结果 |
|---|---|
| **死循环被硬杀** | ✅ 实测 **5.05s** 返回「超过最长执行时间（5 秒）—— 已【强制终止】」（改前：**永不返回**） |
| **正常代码不受影响** | ✅ `print(6*7)`→`42` · `math.sqrt(16)`→`4.0` · `class A`→`A` · `raise ValueError`→错误文本 · `import math`→ImportError（预期） |
| **开销** | **~56 ms/次** |
| **新增用例** | **5 条**（1 条超时 + 4 条预算/记账） |
| **零回归** | 全套 我的 `15 failed / 88 passed / 3 skipped` vs 基线 `15 failed / 83 passed / 3 skipped` ⇒ **+5 passed（正是新增的 5 条），failed 一条没多** |

> ⚠️ 那 15 条失败**全是 `redis ConnectionError`**（当时 Docker daemon 没起），**两版一致 ⇒ 与本次无关**。

## 反悔成本

- **超时退回进程内**：低（git 历史完整），**但会退回"死循环永不返回"** ⇒ **不建议**
- **记账退回不记账**：低，但**配额会再次管不到这条路**
- 两处都是**单点改动**，且新用例会在回退时变红

## ⬜ 遗留

1. **`web_search` 仍没有离线验证过**（需网络）—— 超时是**加上了**，但**没实跑过**（承接 `DEC-026` 的遗留）
2. **端到端 `POST /agent/plan_execute` 仍未实跑**（需 LLM + API 在跑）
3. **权限收窄**未做（见③）
4. ⚠️ **`plan_execute` 整体仍无总时长上限** —— 现在是**每次工具调用**有上限（代码 5s / 搜索 20s），
   但"一个计划跑 7 步 × 每步重试 3 次"的总时长**没有上限**。已在登记里标注。
