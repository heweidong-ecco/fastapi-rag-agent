**`DEC-026` 一上线，它们同时从"纸面问题"变成"现实问题"。**

## ① 超时 —— 机制选择（唯一真正需要裁的）

**"真正的超时"在 Python 里只有一个可靠做法 —— 放子进程、超时硬杀。另外三条路我都核过，都不成立：**

| 机制 | 为什么不行 |
|---|---|
| `signal.alarm` | ⚠️ **只在【主线程】有效** —— MCP 服务端用 `asyncio.to_thread(handler, args)` 调工具 ⇒ 执行在 **worker 线程**，alarm 装不上 |
| 线程 + `join(timeout)` | **杀不掉 Python 线程** ⇒ 线程照跑，只是"你以为超时了"（**假超时** —— 比没有更糟，它给了错误的安全感） |
| `PyThreadState_SetAsyncExc` | 对**紧循环不可靠** —— 拿它当安全承诺的地基不诚实 |
| **子进程 + `terminate()`** ⭐ | ✅ **唯一能真正打断死循环的** |

**采纳子进程。** 收益不止超时：

- **全新解释器** ⇒ 隔离更强（比"同一个进程里关在 dict 里"强）
- 白名单**从同一个模块重建**（子进程 `import code_executor_impl`）⇒ **单一事实源，不会漂**
- 子进程**崩了（段错误 / OOM）带不走主进程**

**代价（如实记）**：每次调用多一次进程启动 —— **实测 ~56 ms**（比预估的 100ms 好）。
**判据**：对"执行代码"这类工具完全可以接受。

**同时给 `web_search` 加了 HTTP 超时**（`SEARCH_TIMEOUT_SECONDS = 20`，含兜底那条路）——
此前 `client.chat.completions.create(...)` **没有任何 timeout**。

## ② 成本 —— 照抄 2 代的模式，不另起炉灶

新增一个**统一的 LLM 调用入口** `_invoke_llm()`：**查预算 → 调用 → 按 `usage_metadata` 记真实用量**。
📌 与 `agent_graph_advanced.py:303/315` **同一套**，只是包成一个入口，免得在四个调用点各抄一遍。

| 做法 | 采纳 | 理由 |
|---|---|---|
| **甲 · 记账放端点层**（只做事前事后） | ❌ | `plan_execute` 会跑 **N 次** LLM（1 规划 + 每步 ×2），端点层**拿不到每步的真实 token** ⇒ 只能估 |
| **乙 · 在每个调用点各抄一遍** | ❌ | 四处重复，下次加调用点必然漏 |
| **丙 · 统一入口 `_invoke_llm`** ⭐ | ✅ | 单一入口 ⇒ 加新调用点**不可能漏记账** |

**`user_name` 显式贯穿**（7 个函数加形参），**不用 contextvar** —— 本仓重视显式，
且隐式上下文会让"配额算在谁头上"变得难以验证。

**新增三个 purpose**（`PURPOSE_ESTIMATED_TOKENS` / `PURPOSE_ESTIMATED_COST` **两套都加**——
本仓规矩：两套表并存、不可互相替代，见 `DEC-002`）：
`plan_execute.plan` · `plan_execute.dynamic_input` · `plan_execute.quality_check`。

**⚠️ 无 `usage_metadata` 时【如实不记】** —— 不编一个数字塞进账里（已写成用例）。

## ③ 权限 —— **本次【不动】权限**

**理由**：收窄"谁能用代码执行"是**产品决策**（谁能用、free 该不该能），不是技术修法。
而 **② 的记账让配额真正生效** ⇒ 免费用户的 100 次/天**现在管得到了** ——
**这是比"一刀切收窄"更精确的手段。**

⇒ **权限收窄留作独立选项，本次未做。**

## 顺带修掉的一个真问题：**端点阻塞事件循环**

`plan_task` / `execute_plan` 是**同步**的，而端点是 `async def` ⇒ 直接在事件循环里调会
**阻塞整个 API**。以前执行快所以不痛；**真调工具之后会真发网络请求，代价立刻显形。**

⇒ 改成 `await asyncio.to_thread(...)`（同型先例：`/agent/fetch_webpage` 那两个端点）。

## 反悔成本

- **超时退回进程内**：低（git 历史完整），**但会退回"死循环永不返回"** ⇒ **不建议**
- **记账退回不记账**：低，但**配额会再次管不到这条路**

## 🔴 补记（同日）：③ **漏掉了另一半** —— LLM 调用自身也没有超时

**做完 ③ 之后核出来的**，属同一类问题，**已补**。

```
planner_llm / executor_llm / quality_checker_llm  →  timeout = None
openai SDK 默认: connect=5s · read=600s（10 分钟）· write=600s   且 SDK 自己 max_retries=2
```

⇒ **一次 LLM 调用最坏可等 `600 × (1+2) = 30 分钟`**；
而 `plan_execute` 最坏跑「3–7 步 × 每步重试 3 次 × 每步 2 次 LLM 调用」
⇒ **理论上能挂几个小时。**

⚠️ **③ 只补了「工具调用」的超时（沙箱 5s / 搜索 20s），没补「LLM 调用」的。**
**同一类问题，漏了一半** —— 这条是**自己回头核出来的**，不是别人指出的。

**补法**：

| 项 | 值 | 理由 |
|---|---|---|
| `PLANNER_LLM_TIMEOUT` | 60s | prompt 大、输出是一份 JSON 计划 |
| `EXECUTOR_LLM_TIMEOUT` | 30s | 每步的参数值生成，输入小、输出一句话或一段代码 |
| `QUALITY_LLM_TIMEOUT` | 20s | 只回 PASS / FAIL |
| `LLM_MAX_RETRIES` | **1**（SDK 默认是 2） | ⚠️ **重试本身就是"再来一遍完整超时"** —— 层数越多最坏时长越难算 |
| `PLAN_TOTAL_BUDGET_SECONDS` | **120s** | 见下 |

⇒ **最坏情况第一次变得可算**：单次 = `timeout × (1 + max_retries)`。

### 顺带补上：**整条计划的总时长上限**

> **单次调用有上限 ≠ 整条计划有上限。**
> 一个 3–7 步的计划，哪怕每步都"守规矩"，叠起来也能很久。

在 `execute_plan_with_replan` 的循环开头加预算检查。**⚠️ 停下来时必须【如实说没跑完】**：

```
[系统] 已超过总时长预算（120 秒），执行【提前终止】——**结果不完整**，
剩余 N 个步骤未执行。提示：把目标拆得更小，或减少步骤数后重试。
```

**不能让它看起来像正常结束** —— 剩余步骤数一起报出来，调用方才知道**结果不完整**。

**验证**：新增 **2 条**用例（超时非 None + 总预算截断并如实说明）·
全套 `15 failed / 90 passed / 3 skipped` vs 基线 `15 failed / 88 passed / 3 skipped`
⇒ **+2 passed（正是新增那 2 条），failed 一条没多**。

📌 **测试里踩过的一个坑（记下来）**：最初用 `PLAN_TOTAL_BUDGET_SECONDS = 0` 造"已超"，
**结果第一步照跑** —— 因为判据是 `elapsed > budget`，而首次检查时 `elapsed ≈ 0`
（`time.time()` 微秒精度，两次连续调用甚至可能同值）⇒ `0 > 0` 为 False。
**那是边界，不是缺陷**；改用 `-1` 才是确定的"已超"。

## 🔴 再补记（同日）：**把"拍的数"换成【实测校准的数】**（遗留 #4）

**背景**：上面那三个超时（60/30/20）**是拍的** —— 我当时就写了「⚠️ LLM 超时的具体秒数是【拍的】」。

**实测方法**：在进程内包一层 `_invoke_llm` 计时，跑 2 个真实目标（4 步 / 3 步+真搜索），
拿到 **28 次真实调用**的耗时：

| 项 | n | min | 中位 | **max** | 原设超时 | 原余量 |
|---|---:|---:|---:|---:|---:|---:|
| `plan_execute.plan` | 2 | 1.81 | 2.68 | **2.68** | 60s | **22×** |
| `plan_execute.dynamic_input` | 13 | 0.60 | 0.98 | **1.77** | 30s | **17×** |
| `plan_execute.quality_check` | 13 | 0.82 | 1.17 | **1.56** | 20s | **13×** |
| **端到端** | | | | **10.5s（4 步）/ 27.2s（3 步+真搜索）** | | |

⇒ **原值对实测 max 有 13–22 倍余量，明显是"拍"的。**

🔴 **而且它有个真代价**：`plan` 的 60s × (1+1 重试) = **120s —— 正好等于总预算**
⇒ **【一次卡住就能吃光整个计划的预算】**，总预算形同虚设。

### 三个方案

| 方案 | 值 | 余量 | 风险 |
|---|---|---|---|
| 甲 | 20 / 15 / 10 | ~6–9× | ⚠️ **样本小（`plan` 只有 n=2）**，而 LLM 延迟**重尾** ⇒ 可能误杀 |
| **乙 · 保守折中**（**采纳**） | **30 / 20 / 15** | ~11–13× | 较稳 |
| 丙 | 不改，只记数据 | — | "拍的数"还在 |

**业务方 2026-09-21 裁「乙」。**

**`PLAN_TOTAL_BUDGET_SECONDS` 维持 120s**：实测端到端 10.5s / 27.2s ⇒ **4–11 倍余量，合理**；
且收紧超时后最坏 7×(20+15)=**245s > 120s** ⇒ **仍被总预算兜住** ✅

### 已固化成可执行判据（不是只写注释）

`test_llm_timeouts_are_calibrated_to_measurement` —— **两个方向都锁**：
- **下界**：每个超时 ≥ 实测 max 的 **5 倍**（防收太紧 ⇒ 误杀）
- **上界**：最坏单次（`timeout × (1+retries)`）**必须 < 总预算**（防吃光）

✅ **红→绿已证**：把值改回 **60/30/20** ⇒ 用例红，报
「最坏单次 = 120s ≥ 总预算 120s —— 【一次卡住就能吃光整个计划的预算】」。

**⚠️ 仍要记得**：**观测到的 max ≠ P99**（样本小）。若线上发现正常计划被截断，
**先调这三个数，别急着去掉上限**。
