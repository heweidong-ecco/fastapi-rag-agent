## 三 · `demo/` 的目录结构（**新**）

> **业务方原话**：「**demo 的内容落 `demo/` 这个（文件）夹，`demo/` 中有些内容不能提交，
> 有一些设置文件和命令行文件，你建一个子文件夹放进去，子文件夹加入 `.gitignore`。**」

```
demo/                                  ← ✅ 【入库】2026-10-08 从 .gitignore 释放
├── demo清单.md                        ← ✅ 入库 · Demo 的唯一权威
├── 待办-demo之后.md                    ← ✅ 入库（B14，⛔ 本仓不计未结）
└── 设置与命令/                         ← ⛔ 忽略（`.gitignore:69`）
    ├── 创空间-最小验证-操作步骤.md        ← 命令行文件（含 token 怎么传）
    └── probe-创空间最小验证/            ← 探针（Dockerfile / app.py / requirements.txt …）
```

**规矩两条**：
1. **`demo/` 里【文档类】⇒ 入库** —— 让 clone 的人看得见 demo 材料（这也是当初 `未进demo/` 想要的效果，见 §六·2）
2. **`demo/` 里【设置文件 / 命令行文件】⇒ 进 `demo/设置与命令/`，⛔ 不入库** ——
   它们里面写着**凭据怎么传**（`MODELSCOPE_API_KEY`、`oauth2:<token>@…` 这类）
   ⇒ 进 git 就是**把密钥送出去**（本仓密钥红线）

> ⚠️ **收窄了那条老规矩**：改前 `ROADMAP` 写「⛔ 引用 `demo/` 里的东西，路径别带 `.md`（断链门判红）」。
> 🔴 **现在只对 `demo/设置与命令/` 有效** —— `demo/demo清单.md` 这类**可以正常写 `.md` 链接**了。
> 📌 **为什么那条规矩原来是对的**：`.gitignore` 里的东西**不会随 clone 下来** ⇒ 断链门（口径 = 「**克隆者拿得到什么**」）必然判红。

⚠️ **`demo/` 会不会越变越乱？** 会 —— 但**乱的那半（命令/配置）本来就在被忽略的子文件夹里**，
入库的只有两份文档。⇒ 这正是"文档入库 / 命令忽略"这个切法的用处。

### 4.3 ⭐ 统一后的顺序（**今后照这条**）

> **收口**（含 `N12`）→ **定语料契约** → **语料重建** → **前端** →
> **demo 机制**（用**现有**语料先跑通）→ **切嵌入模型 + 重烤**（用**新**语料）→ **demo 上线创空间** →
> **本机 locust 压测** → **本仓最终收尾（文档：`README.md` / 架构图 / `FAQ` 等）**

### 4.4 🔴 为什么它和 `DEC-113` 那句「先 demo 再乙」**不矛盾**

`DEC-113 §二·9` 记的是业务方原话「**先进 `乙` 语料重建会导致收尾和测试报红 CI 过不了**」。
⚠️ **那条顾虑只对「切嵌入模型 + 重烤」成立** —— 那一件会**改维度、弄坏本机库**；
🔴 **而「产出语料」（写一批 `.md`）本身是安全的** —— 不动代码、不动库。
⇒ **本 DEC §4.3 把「重烤」从"语料重建"里单独拆出来、放在 demo 机制之后**，
⇒ **两条口径就同时成立了**（业务方的新列表 ✅ · `DEC-113` 的顾虑 ✅）。
📄 `DEC-113 §二·9` **不删、不改** —— 它记的是当时的原话，本 DEC 是**补出它管不着的那半边**。
