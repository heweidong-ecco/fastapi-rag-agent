# 决策记录:DEC-009 · `CLAUDE.md` 从 `.gitignore` 移出、改为入库

- 日期:2026-09-17
- 状态:已采纳
- 关联:`.gitignore:17` · `CLAUDE.md` 抬头 · PR #15

## 决策事项

一句话:`CLAUDE.md` 一直被 `.gitignore` 排除(**只在本机存在**)。**要不要让它入库?**

## 背景与约束

**原状**:`.gitignore:17` 有 `CLAUDE.md`,且该文件自己的抬头写着
「本文件**不纳入 git 管理**……提交前请勿 `git add CLAUDE.md`」。

**触发点**:当天把 superpowers 必用表写进该文件后,业务方裁决「**两份都留本仓**」。
而这句话暴露了一个矛盾:

> **如果 `CLAUDE.md` 不入库,那「留本仓」和「留全局」在物理上没有区别** ——
> 两者都**只在本机**。所谓"本仓试点"就只是心理上的。

**约束**:
- ⚠️ 本仓是 **PUBLIC** —— 入库意味着**内容会公开**
- `.gitignore` 里同段还有 `GIT_CHECKLIST.md`(仍应忽略)

## 备选方案

| 方案 | 思路 | 优点 | 缺点 |
|---|---|---|---|
| **甲** | **移出 `.gitignore` → 入库** | 「留本仓」名副其实;换机器/换人可见;可追溯 | ⚠️ **内容进 PUBLIC 仓库**,暴露面变大 |
| 乙 | 保持忽略,把内容复制到 `docs/` 入库 | 入库的只是挑选过的内容 | **两处真相**,必然漂移 |
| 丙 | 保持忽略,不动 | 零风险 | 「本仓试点」名不副实 |

## 评估标准

内容是否含敏感信息 / 是否有"两处真相"风险 / 换机器后是否还在 / 可追溯性。

## 方案对比

**甲的最大风险 = 泄漏。必须先扫再动。**

**入库前凭据扫描(实测)**:
```
5 个真实凭据(LOGIN_PASSWORD · TEST_USER_PASSWORD · POSTGRES_PASSWORD
             · JWT_SECRET_KEY · DASHSCOPE_API_KEY)
+ 3 个历史泄露字面量(原文见 git 历史,本文件不复写)
⇒ 全部 0 命中
```

> 🔴 **本文件初版曾把 3 个历史泄露字面量【原样写进来】—— 已脱敏。**
> 那是**第三次**犯同一个错(前两次见 `docs/复盘/2026-09-15-为记录漏洞而制造新漏洞.md`)。
> 根因:写"扫描结果"时**把检索词本身当成了引用对象**。
> **防错**:报告扫描结果**只写凭据的【名字】,不写它的【值】** —— 哪怕是"已知已泄露的旧值"。
> ⚠️ 这条纪律 `docs/CODE_INVENTORY.md` 开头已经写过一遍了,我读了、还是犯了。
另扫泛化模式(`sk-…` / `ghp_…` / `BEGIN … PRIVATE KEY`)—— 也 0 命中。

- 乙 的"两处真相"是**本仓反复吃过的亏**(`CLAUDE.md` 与 `ROADMAP.md` 都只放指针、不复制内容,就是为防这个)
- 丙 会让当天的裁决**落空**

## 最终决策 + 理由

**✅ 采纳甲。**

**业务方原话(2026-09-17)**:「本仓 CLAUDE.md 从 .gitignore:17 移出来,要入库。」

## 影响与后续行动

- `.gitignore:17` 移除 `CLAUDE.md`,并**在原地留下注释**说明「为什么曾忽略、为什么现在移出」
  —— 免得后人再改回去(`GIT_CHECKLIST.md` 仍在忽略名单里)
- `CLAUDE.md` 抬头**改为**:「2026-09-17 起入库 · **PUBLIC 仓库内容** · **不得写入明文凭据**」
  —— 把"为什么曾忽略"的那条约束**保留下来**,只是换了形式
- 入库经 PR #15,CI `pass`

## 反悔成本

**低 —— 但方向不对称。**
- 撤销 = 把 `CLAUDE.md` 加回 `.gitignore` 并 `git rm --cached`
- ⚠️ **但已推上去的内容会被缓存/索引** —— 「删了 ≠ 没发生」。
  故**入库前那次凭据扫描是关键闸门**,一旦漏扫,反悔救不回来。
