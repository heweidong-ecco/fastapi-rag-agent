## 🅰️ 决策一：**Docker 由本仓独占使用**

> **业务方原话**：「现在 Docker 一直都只有我们在使用，其他的项目的 docker 我都不会开，
> 基本上是开发阶段已经完成，不会使用到 docker 了。」

### 它解除了什么

`施工单 §2.1` 警告过三件**全局资源**（跟目录无关）：

| # | 撞什么 | 说明 |
|---|---|---|
| 1 | **容器名** | `container_name` 写死：`rag-api` / `postgres-rag` / `redis-rag` / `prometheus` / `grafana` |
| 2 | **端口** | 写死 8000 / 5432 / 6379 / 9090 / 3000 |
| 3 | **数据卷** | `name:` 钉死成 `my-fixed-name_postgres_data` 等 ⇒ 新目录会挂到同一个旧卷 |

⇒ **本决策的含义**：**不需要为此做隔离。**

| 后果 | |
|---|---|
| ✅ **不需要 `docker-compose.override.yml`** | `施工单 §2.2 的 B2 路径作废` |
| ✅ **不需要 `-p rag-demo` 换项目名** | 容器名/端口/卷名照旧 |
| ✅ **`施工单 §2.2 明确选 B1（用原目录）** | 与本决策一致 |
| ✅ **不必再担心"撞到别的项目的容器"** | 本机 Docker 里其余的容器都是**开发阶段遗留、不会再启动** |

### ⚠️ 但**没有**解除的两条（别读成"可以随便 up"）

1. 🔴 **`docker-compose.yml` 末尾那条警告仍然有效** ——
   `rag-api-eval` 曾被 `agent-eval-gate` 的评测使用 ⇒ **有评测在跑时不要 `docker compose up`**。
   📌 **2026-09-24 实测复核**：`rag-api-eval` 已 **Exited（8 天前）**，**当前没有评测在跑** ⇒ 现在可以 up。
   **判据（每次 up 前跑）**：`docker ps --format '{{.Names}}' | grep eval` → 空即安全。
2. ⚠️ **资源是实的** —— 本机 **8 GB**，Docker Desktop 只分到 **3.84 GB**
   （`施工单 §4.1` 实测）。**独占 ≠ 变多** ⇒ `施工单 §4.2 档 1（fast 模式、不装重排序）** 那条判断不变。

## 🅱️ 决策二：**后端先行 —— 先把后端全部完成并跑通，再进前端**

> **业务方原话**：「分阶段做，先把后端全部完成和跑通，再进入前端开发阶段。」

### 它相对于 `施工单` 调了什么

`施工单` 把 **③ 前端** 排在阶段 3。但 **③ 里其实混着后端活**（§3.3 四硬门补齐）：

| 硬门 | `施工单 §3.3` 说的 | 属于 |
|---|---|---|
| **A 流式** | 🔴 **`api_v1_agent.py` 不流式**，要补 | **后端** |
| **B 引用** | 后端已有 `answer_with_citations.py`，缺的是前端 | **前端** |
| **C 中断** | ① 前端按钮 ② **服务端 cancel 传播** | **两边都有** |
| **D 接管** | ① 触发条件 ② 界面 ③ 续跑 | **两边都有** |

⇒ **本决策 = 把 ③ 里的【后端部分】抽出来，先做完，再做页面。**

### 因此调整后的顺序

```
✅ ② 本机验证跑通
🔵 后端全部完成          ← 本决策插入的阶段（原混在 ③ 里）
      · 硬门 A 的 Agent 端流式
      · 硬门 C 的【服务端 cancel 传播】
      · 硬门 D 的【触发条件 + 续跑】（界面属前端）
      · R1–R4 限额 / 熔断 / 结构化错误（§8.1 —— 前端卡片属前端）
      · §8.2 eval 接入
⬜ 前端开发              ← 原 ③ 的页面部分
      · 对话页 / 接管页 / Trace 页（改造）/ Eval 页
      · 硬门 B 的界面部分 · 硬门 C 的停止按钮 · 硬门 D 的接管队列界面
      · R3.2 熔断提示卡片
⬜ ④ 测内存定机器 → ⑤ 买域名 → ⑥ 上云 → ⑦ 开隧道 → ⑧ 保护/自验/发链接
```

### 为什么这样排（业务方未展开理由，此处记**可观察的好处**，不代言）

- **后端是前端的输入** —— 页面要调的流式 / cancel / 接管队列 / 错误码，**都得先在服务端存在**，
  否则前端只能对着假数据做，做完还要返工。
- ⚠️ **`施工单 §3.3` 自己就把 C 标成「最容易假完成」** —— 而**它的难点全在后端**
  （"必须让上游模型的 HTTP 流也终止"）。**先做后端 = 先啃最硬的骨头。**
