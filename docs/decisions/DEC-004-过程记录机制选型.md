# 决策记录:DEC-004 · 本项目的过程记录机制选型

- 日期:2026-09-15
- 状态:已采纳
- 关联:全仓库治理 / `ROADMAP.md` / `docs/CODE_INVENTORY.md`

## 决策事项

一句话:本项目**没有任何过程记录机制**,导致本次会话产出的分析、决策与失误**只存在于对话里,换个会话就丢**。要建哪些机制?

## 背景与约束

**查证结果(本项目 vs 业务方体系)**:

| 机制 | 兄弟项目 | 本项目 |
|---|---|---|
| DEC 决策记录 | `agent-eval-gate/docs/decisions/` 有 **DEC-001～015**;`product-agent-dev-os` / `product-dev-os` / `ess-ai-sales-system` 均有 `decisions/` + `DEC-选型模板.md` | ❌ 无 |
| 复盘(过程错误集) | `agent-eval-gate/docs/复盘/` **10 份**,如 `2026-09-13-看完就发出去.md` | ❌ 无 |
| CHANGELOG | `ai-field-delivery-toolkit` / `ai-delivery-harness-engineering` 有(Keep-a-Changelog 格式) | ❌ 无 |
| 留痕×指标挂钩 / RUNBOOK / memory-规约 | `product-agent-dev-os/docs/` 与 `agent-eval-gate/docs/` 均有 | ❌ 无 |

本项目现有的只是**零散**记录:`api/bad_cases.md`(评估分析)、`api/cleanup_rules_notes.md`、`archive/README.md`、`硬性指标终极核查清单.md`、`性能基线报告模板.txt`。

**这与 M5 的定性一致:代码搬过来了,治理机制没搬过来。**

**既有教训(必须作为约束考虑)**:`api/LEARNING_INDEX.md` **已经定义了**一套治理格式(`status: active|superseded|deprecated` + `superseded_by` + `key_learning`)—— 但实测**全仓库 0 个文件使用它**(唯一正则命中是 `tool_visualizer.py:19` 的 dataclass 字段),且**没有任何文件引用它**。它成了一座孤岛。

⇒ **本决策的最大风险不是"建不建",而是"建了不用"。** 业务方的 `Product/CLAUDE.md` 对此有原话:「有结构才执行,只有文字就漏」。

## 备选方案

| 方案 | 思路 | 优点 | 缺点 |
|---|---|---|---|
| 只建 DEC | 决策进 `docs/decisions/` | 装得下"为什么没选另一条路" —— 本次最有价值的内容 | 装不下"过程错在哪"(复盘),也装不下"改了什么"(CHANGELOG)。三类内容混在一起会让 DEC 失焦 |
| 只建 CHANGELOG | 改动进 `CHANGELOG.md` | 与 `ai-field-delivery-toolkit` 一致,格式成熟 | 它记的是**改了什么**,装不下**为什么这样选**。而本次 5 个决策的价值恰恰在后者 |
| 只建复盘 | 失误进 `docs/复盘/` | 能钉住"下次别犯" | 只记错的,不记对的 |
| **三套全建(已选)** | 各司其职 | 完整对齐业务方体系;三类内容各有归属 | 一次性建三套,**"建了不用"的风险最大** —— 正是 `LEARNING_INDEX.md` 走过的路 |

## 评估标准

能否装下本次实际产出的内容类型 / 是否与业务方体系一致(降低切换成本) / **建成后被实际使用的概率** / 维护成本。

## 方案对比

**关键论证:三类内容性质不同,不能合并。**

| 内容类型 | 本次实例 | 该进哪 |
|---|---|---|
| **为什么这样选** | 认证走路线 C 而非 A/B;压测改脚本而非端点 | DEC |
| **过程错在哪** | 为记录漏洞而制造新漏洞;先转述后复核 | 复盘 |
| **改了什么** | CI 骨架、ROADMAP 锚点、三套机制 | CHANGELOG |

把三者塞进一份文件,会让"裁决依据"和"失误记录"互相稀释 —— 而 DEC 的价值恰恰在于**它能被单独检索与追溯**。

**对"建了不用"风险的处置**(这是本决策能成立的前提):
1. **挂进 `ROADMAP.md` 的「当前指针」** —— 该文件是每次会话的接续入口,不挂在那里就没有触发器。
2. **本次就写入真实内容**,不留空模板 —— 空模板＝永远空。三套机制**第一次使用必须在建它的那一次**。
3. 不建 `RUNBOOK` / `留痕×指标挂钩` 等其余机制 —— **等有真实需求再加入**,避免一次性铺开又全部闲置。

## 最终决策 + 理由

**三套全建(DEC + 复盘 + CHANGELOG),但只建这三套,且本次就填入真实内容。**

理由:三类内容性质不同,合并会互相稀释;业务方体系里三套并存已是被验证过的分工。选择"全建"而非分步建,是因为**本次恰好同时产出了三类内容** —— 有真实素材时建立机制,比对着空模板建立更不容易落空。

**放弃了什么**:放弃"一次只建一套、逐步验证"的稳妥路线。**为何放弃**:本次三类素材同时具备,分步建会导致后两类的素材先丢失。

**明确不做**:`RUNBOOK` / `留痕×指标挂钩` / `memory-规约` 本次不建 —— 本项目连 CI 都才刚有,一次铺开六套机制的结果大概率是六套都闲置。

## 影响与后续行动

- 新增 `docs/decisions/`(DEC-001～004)、`docs/复盘/`、`CHANGELOG.md`。
- **`ROADMAP.md` 的「当前指针」加一行**:决策进 `docs/decisions/`、过程错误进 `docs/复盘/`、改动进 `CHANGELOG.md` —— **这一条是本决策能落地的唯一保障**。
- `CHANGELOG.md` **只从本次起记,不追溯补写历史** —— 避免编造没发生过的记录;此前历史以 `git log` 为准。
- 后续:若 `LEARNING_INDEX.md` 那套代际治理规范要真正启用,应在 M5 裁决时**实际标注** `status: superseded` + `superseded_by`,而非继续当孤岛。

## 反悔成本

极低。三套机制都是新增的独立目录/文件,**零代码依赖**,删除不影响任何运行逻辑。若某套长期闲置,删掉即可,不会留下半截接线。
真正的成本不在"建错",而在"建了不用" —— 因此衡量本决策是否成功的标准是:**一个季度后,`docs/decisions/` 里是否新增了 DEC-005**。
