## 决策事项

`①b · Task 3` 要实现全局日级用量查询 + 判定。动手前核对来源，**三处在计划里没定死**：

| # | 问题 | 计划/来源怎么写的 | 冲突点 |
|---|---|---|---|
| **一** | **阈值取多少** | 源文档 B10 的「✍️ 裁」栏：**「⚠️ 附一问（仍待答）：具体阈值 ______（业务判断，我不替你定）」** | 仓里**有一个值**（`GLOBAL_DAILY_TOKEN_LIMIT` 默认 `1_000_000`，`①a` 落的），但它**从没被确认过**，也**不在环境变量契约里**（`.env.example` / `docs/契约/环境变量.md` 均无此名）——是**顺手写下的数**，不是裁定值 |
| **二** | 查库失败时**放行还是拒绝** | 计划的代码样例写了 `return 0.0`（= 放行），但**没写理由** | `api/deps.py` 的鉴权是 **fail-closed**。同仓两种相反取向，**没有文字说明就是埋雷** |
| **三** | 本任务**做完是不是"全局限额生效了"** | 计划把接线放在 `Task 4`（`B11`） | ⚠️ **与 `B7` 之前的状态完全同型**：常量/函数都在，**没有任何调用点** ⇒ 看起来"做完了"，实际**拦不住任何东西** |

### 为什么现在要定

- **阈值一**：接线**之前**它只是个没人读的常量；接线**之后**它就是
  「**今天全站花到多少 ⇒ 所有人一起被拒**」的开关。⇒ 用它之前必须有**业务方的数**，
  ⛔ 不能拿一个"看起来合理"的默认值先跑起来 —— 那是**替业务方做业务判断**。
- **方向二**：这不是风格问题。**方向选错的具体后果**：
  fail-closed ⇒ **PG 抖一下，全站所有人的请求一起 429**。
  会话级（`B8`）fail-closed 只打死一个会话；**全局级打死所有人**。⇒ 方向**必须写下来**。
- **边界三**：`B10` 单独做完**不产生任何行为变化**。不写明，下一个接手的人
  （或三个月后的我）会**把"有函数"读成"有额度"** —— `docs/复盘/2026-09-29-用我做过了当别人找得到.md` 记的正是这个病。

## 备选方案

### 一 · 阈值数值

**折算口径**（用来让三个选项可比）：`.env` 实际跑的模型是 `deepseek-v4-flash`，
`token_config.MODEL_PRICING` 记的是**输入 0.001 / 输出 0.002 元每千 token**
⇒ 该模型下 **100 万 token ≈ ¥1–2/天**。同时，`premium` 的**个人**日上限 = `100,000`
⇒ **1,000,000 = 10 个 premium 用户当天都跑满**。

| 方案 | 一句话 | 评价 |
|---|---|---|
| **甲 · 1,000,000 /天**（**采纳**） | 现默认值 · ≈ ¥1–2/天封顶 | ✅ **10 个 premium 满额**才触顶 ⇒ 与本机 8 GB、刚上公网的量级匹配；✅ **熔断真会触发**（不是永远不响的摆设） |
| 乙 · 5,000,000 /天 | ≈ ¥5–10/天 | ✅ 公开演示**不易误伤**<br>⛔ 代价：**熔断实际很难触发** ⇒ 这条限额**平时看不出来**，"有没有生效"无法验证 |
| 丙 · 200,000 /天 | ≈ ¥0.2–0.4/天 | ✅ 最省<br>⛔ 代价**很具体**：**2 个 premium 用户当天跑满就到顶** ⇒ 上公网后极易变成「正常用着突然全站被拒」 |

> 📌 **判据（`通用方法 §7.1` 的要素①）**要求阈值**说得出数、且与量级匹配**。
> 乙的数是说得出，但**触不到** ⇒ 熔断的四要素里「②触发动作」永远走不到，**验收时无法证明它成立**。
> 这正是丙/乙都不选的原因：**一个太松（测不出）、一个太紧（正常用就撞）**。

### 二 · 查库失败的方向

| 方案 | 一句话 | 评价 |
|---|---|---|
| **甲 · fail-open**（**采纳**） | 取数失败 ⇒ 返回 `0.0` ⇒ 放行 | ✅ 与仓里既有 `get_daily_token_usage` / `get_session_token_usage` **同取向**（三处一致）<br>✅ 额度是**成本控制**，不是安全边界 |
| 乙 · fail-closed | 取数失败 ⇒ 拒绝 | ✅ 「宁可不服务也不超支」<br>⛔ **代价在本维度被放大到最大**：**一次 DB 抖动 = 全站 429**。且它挡不住真正的超支（DB 都读不到，本来也记不了账） |

## 决策与理由

**一 · 阈值 ⇒ 甲（`1,000,000` /天）· 二 · 方向 ⇒ 甲（fail-open）· 三 · 边界 ⇒ 本任务不接线（接线在 `Task 4` / `B11`）。**

**业务方 2026-10-01 裁定**（选择「1,000,000 /天（现默认）」）——
**这条把源文档 B10 里那个 `______（业务判断，我不替你定）` 的空填上了。**

### 落地含义

| # | 做什么 | 落点 |
|---|---|---|
| ① | `get_global_daily_token_usage() -> float` —— 查库，`SUM(total_tokens) WHERE created_at >= CURRENT_DATE`，**⛔ 不带 `user_name`** | `api/token_tracker.py` |
| ② | `check_global_daily_budget(estimated_tokens=0) -> (bool, str)` | 同上 |
| ③ | 阈值 = **`token_config.GLOBAL_DAILY_TOKEN_LIMIT` 默认 `1_000_000`**（`DEC-040`：常量只有一个落点，⛔ 不许在函数里写死） | `api/token_config.py`（值不变） |
| ④ | 触顶动作 = **直接拒绝**（`B11` 要素②，业务方 2026-09-30 已裁：拒绝 429 + 明确提示，**不降级、不转人工**） | 随 `Task 4` 接线 |

### ⚠️ 三条必须一起写下来的（否则下一个人会当成 bug）

1. **「全局」的全部含义 = SQL 里没有 `user_name`。**
   做成参数（`user_name=None`）会让**漏传**静默退化成"某个用户"，**返回值正常、报错正常、只是偏小**。
   ⇒ 拆成**独立函数** + `api/test_global_daily_budget_offline.py` **静态钉住**
   （AST 取 `cur.execute` 的字面量，⛔ 不用 grep —— 注释里也有这些词）。
   ⚠️ **必须含 `admin`**：`admin` 的个人上限现在也是有限值，**但那是另一个东西** ——
   per-user 检查**永远看不到「大家加起来超了」**（源文档 B11 建议④）。
2. **fail-open 是有意的**，且**在本维度比 `B8` 更要紧** —— 理由见上「方向二」。
   ⛔ **别"顺手统一"成 `deps.py` 的 fail-closed。**
3. **本任务（`Task 3`）只产出函数，⛔ 全程没有调用点。**
   ⇒ **`Task 3` 全绿 ≠ 全局限额生效。** 接线在 `Task 4`（`B11` 断路器 + `main.py` 放行路径）。
   ⚠️ 这与 `B7` 之前「常量建好没接上」、`B8` 之前「有常量没判定」是**同一个陷阱的第三次**。

### 🔹 一处与计划样例的偏离（已实测）

计划的代码样例**收下了 `estimated_tokens` 参数却没有用它**（函数体里只判已用量）。
⇒ 这是「**签名看着对、行为是死的**」。本任务**让它真的参与判定**（与 `check_session_token_budget` 同构），
并加 `test_estimated_tokens_can_trip_it` 钉住 —— 变异验证：删掉那三行 ⇒ **该测试红**。

## 反悔成本

**低。**

- **阈值要改** ⇒ 改 `api/token_config.py` 的默认值一行，或**设环境变量**
  `GLOBAL_DAILY_TOKEN_LIMIT`（`_int()` 读它）⇒ **无需改代码**。
  ⚠️ **但环境变量契约里还没这一项**（见「遗留」1）—— 要走 env 覆盖，得先补文档。
- **方向要改成 fail-closed** ⇒ 把 `get_global_daily_token_usage` 的 `except` 分支
  从 `return 0.0` 改成抛/返回大值；**同时**要改 `B8` 那条与 `get_daily_token_usage` 那条，
  否则三处取向不一致。
- **接线位置要换** ⇒ `Task 4` 尚未开工，**改的是计划而不是代码**，零成本。

⚠️ **两件后果不会自己消失**：
① 阈值是**全站单点** —— 没有"分角色/分来源"的细分（eval 怎么隔离是 `决策三`，见下）。
② **`B10` 不做完接线就永远是 0 效果** —— 本 DEC 的状态**不能**被读成「全局日级已完成」。

## ⬜ 遗留 / 未决

1. **阈值不在环境变量契约里** —— `.env.example` 与 `docs/契约/环境变量.md` 都**没有**
   `GLOBAL_DAILY_TOKEN_LIMIT` / `SESSION_TOKEN_LIMIT`。⇒ 想不改代码就调阈值，**得先补契约**。
   ⬜ 不在本任务范围内（本任务只实现与验证），**记在这里**。
2. **接线未做** —— `Task 4`（`B11` 断路器）。在它落地前，本条**不产生任何行为变化**。
3. **`决策三`（eval 调用怎么与对外额度隔离）仍未落地** —— 源文档 B10 的「⚠️ 与 B14 冲突」栏写着：
   eval 跑全量会**烧被测额度** ⇒ 设了日上限后「跑分可能触发 `E_SUT_QUOTA` → 整批 aborted → exit 3」。
   ⚠️ 全局上限一旦生效，**这个问题就变成真的**（现在是假想的，因为限额不存在）。
4. **恢复条件（`B11` 要素④）仍标「未核」** —— 「跨天自然重置」依赖
   `SELECT ... WHERE created_at >= CURRENT_DATE` 这个**查询侧**窗口，**不依赖 Redis TTL**
   ⇒ 本条（`B10` 的取数）本身**天然满足"明天 0 点恢复"**。
   ⬜ 但源文档 B11 ④ 提到的「**Redis 日级 key 的 TTL 从未实测**」是**另一件事**（B11 若用 Redis 才相关），**仍未核**。
