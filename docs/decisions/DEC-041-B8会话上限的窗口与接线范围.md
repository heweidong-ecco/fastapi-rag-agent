## 决策事项

`①b · Task 2` 要实现会话级用量查询 + 判定。动手前核对来源，发现**三处计划里没定死、
且都会写进配额**的参数：

| # | 问题 | 计划/来源怎么写的 | 冲突点 |
|---|---|---|---|
| **一** | 用量的**计数窗口** | 计划的代码样例写了 `AND created_at >= CURRENT_DATE` | 来源文档叫「单会话**累计**上限」——「累计」读起来是**全程**，`CURRENT_DATE` 是**今日** |
| **二** | **会话 key** 是什么 | 计划只有 `thread_id` 一个参数 | 现有 4 个 Agent 端点的 `thread_id` **默认值是 `"default"`** ⇒ 不传的人**共用一个桶**（见下） |
| **三** | 接到**哪些端点** | 计划写「**两处主链**」 | 来源文档写「**覆盖全部对话链**（不只是 `/agent/mcp_chat`）」——「两处」≠「全部」 |

### 为什么现在要定

**三条都不是"实现细节"，是口径与覆盖面 —— 定错了不容易被发现。**

- **窗口**：与 `DEC-029` **同型**。仓里**同一个 `thread_id` 维度已经有上限了** ——
  `MAX_THREAD_COST`（5 元/线程，`token_tracker.py:692`），**它不带日期**。
  再加一个带日期的 token 上限 ⇒ **同一维度、两种窗口**。
  ⇒ 这正是 `DEC-040` 开头那句「否则各自挑一套口径，**又是三处真相**」要防的东西。
- **会话 key**：`thread_id` 默认 `"default"` ⇒ 照原样接，**所有没显式传 `thread_id` 的调用者
  共用一个 50000 token 的桶** ⇒ 谁先烧完，**谁就把其他默认用户一起挡在外面**。
  ⚠️ 这不是"新增的问题"——他们**本来就共享 LangGraph 检查点状态**（同一个 `thread_id`）。
  但**软共享**（状态串味）与**硬拒绝**（429）的后果差得远：前者是体验问题，后者是**服务不可用**。
- **范围**：实测（2026-10-01）四个对话文件里**只有 `api_v1_agent.py` 有 4 处预算判定**，
  `api_v1_rag.py` / `agent_graph.py` / `agent_graph_advanced_learning.py` **各 0 处**。
  ⇒ 「两处主链」落地后，**大部分对话链仍然完全不受会话上限约束**，
  而 B8 的判据（`通用方法 §7.1`）要求的是「**同会话连续对话超阈值 → 被拒或降级，且有明确提示**」。

## 备选方案

### 一 · 计数窗口

| 方案 | 一句话 | 评价 |
|---|---|---|
| **甲 · 会话 × 今日**（**采纳**） | 计数窗口 = 该会话**今天**的累计 | ✅ 与仓里**其余所有 token 预算**（用户日预算 `ROLE_TOKEN_BUDGET`）**同一口径**；成本控制本来就按天<br>⚠️ 代价两条：① 跨零点的会话计数清零；② 与 `MAX_THREAD_COST`（无日期）**不一致** |
| 乙 · 纯会话累计（不带日期） | 计数窗口 = 该会话**全程** | ✅ 名副其实「单会话累计」；与既有 `MAX_THREAD_COST` **一致**<br>⛔ 代价更重：会话桶**会被永久封死**（默认 `SESSION_TOKEN_LIMIT` 50000，一个长会话很快到）⇒ 用户**无自救手段**（既不能等，也不能重开——key 是他自己传的） |

### 二 · 会话 key

| 方案 | 一句话 | 评价 |
|---|---|---|
| 甲 · 只用 `thread_id` | 与计划原文一致 | ⛔ 默认值 `"default"` ⇒ **一个公共桶**：谁先烧完 50000，**其他默认用户全撞 429**。这不是"少见的边界"——**不传 `thread_id` 是默认行为** |
| **乙 · `user_name` + `thread_id`**（**采纳**） | 每人各自的会话桶 | ✅ 默认值不会互相踩；✅ 与"谁消耗谁受限"的成本归属一致<br>⚠️ 严格说语义是「**用户 × 会话**」，与源文档 R1.2 的「单会话」**字面不完全一致** —— 已在下方「落地含义」写明，⛔ 不假装它还是纯"单会话" |
| 丙 · 缺省时不判 | 只对显式传了 `thread_id` 的判 | ⛔ **留了绕开的口子**：不传 `thread_id` 就无上限，**而这恰好是默认行为** |

## 决策与理由

**一 · 窗口 ⇒ 甲（会话 × 今日）· 二 · key ⇒ 乙（`user_name` + `thread_id`）·
三 · 范围 ⇒ 甲（全部真正调 LLM 的对话链）。**

**业务方 2026-10-01 裁定**（原话记录）：

> 窗口：「**会话 × 今日（带 CURRENT_DATE）**」
> 范围：「**全部对话链（按源文档）**」
> key：「**key 改成 user_name + thread_id**」

### 落地含义

| # | 做什么 | 落点 |
|---|---|---|
| ① | `get_session_token_usage(user_name, thread_id)` —— 查库，`WHERE user_name = %s AND thread_id = %s AND created_at >= CURRENT_DATE` | `api/token_tracker.py` |
| ② | `check_session_token_budget(user_name, thread_id, estimated_tokens=0) -> (bool, str)` | 同上 |
| ③ | 接进**全部 7 条真正调 LLM 的对话链**（见下表） | `api_v1_agent.py` · `api_v1_rag.py` |
| ④ | 触顶动作 = **直接拒绝**（`AppException(ErrorCode.QUOTA_EXCEEDED)`） | 随 `B11` 要素② 的已裁口径 |

**③ 的 7 条落点**（实测每条都真调 LLM）：

| 端点 | `thread_id` | 用户身份 |
|---|---|---|
| `/agent/langgraph_chat` | ✅ 默认 `"default"` | ✅ |
| `/agent/advanced_chat` | ✅ 默认 `"default"` | ✅ |
| `/agent/memory_chat` | ✅ 默认 `"default"` | ✅ |
| `/agent/mcp_chat` | ✅ 默认 `"default"` | ✅（已挂 `check_budget`） |

### ⚠️ 四条必须一起写下来的（否则下一个人会当成 bug）

1. **数据源是 `token_usage_logs` 表，⛔ 不是内存里的 `_thread_summary`。**
   ⚠️ **来源文档 B8 的「落点」栏与此相反** —— 它写「`_thread_summary` 已在内存里按 thread 汇总，**可直接扩展**」。
   🔴 **那句话不成立**：`_thread_summary` 是**进程内存**，**重启即清零**
   ⇒ 拿它当上限，等于「**想绕开上限，重启一下就行**」。
   ⇒ 本 DEC **显式推翻源文档那一句**，以本 DEC 为准（源文档是「待裁」稿，不是权威）。
2. **函数名与源计划不同**：计划写 `get_thread_token_usage(thread_id)`。
   既然 key 变成两段（决策二·乙），**沿用原名会表述不实** ⇒ 改名为
   `get_session_token_usage` / `check_session_token_budget`，且 `user_name` 为**必填位置参数**
   —— ⛔ **不给默认值**：给了默认值，漏传的调用点会**静默落进同一个桶**，而这正是决策二要防的事。
3. **查库失败时 `fail-open`（返回 0.0 = 放行）** —— 与既有 `get_daily_token_usage` 一致。
   理由：配额是**成本控制**，⛔ 不是**安全边界**；DB 抖动时把服务全停掉的代价更大。
   ⚠️ **与 `api/deps.py` 的鉴权故意相反**（那里 `fail-closed`，因为**那是**安全边界）—— **别"统一"掉。**
4. **窗口不一致是【已知且有意】的**：`MAX_THREAD_COST`（元/线程，**无日期**）与
   本节（token/用户×会话，**按日**）**窗口不同**。⛔ **本 DEC 不假装已经解决它** ——
   归并由 `DEC-040` 的 `①b` Task 6 处理。

## 反悔成本

**低。** 三处全部落在**一处函数 + 7 个调用点**，且**无数据迁移**（`token_usage_logs`
本来就同时有 `user_name` / `thread_id` / `created_at` 三列）：

- **窗口要改回「纯累计」** ⇒ 删 `get_session_token_usage` SQL 里的一行 `AND created_at >= CURRENT_DATE`，改本 DEC 状态。
- **key 要改回只用 `thread_id`** ⇒ 删 SQL 里的 `user_name = %s` 并去掉那个必填参数。**⚠️ 但这会重新引入决策二·甲那个公共桶问题。**
- **范围要缩** ⇒ 删调用点即可，**不留脏数据**。

⚠️ **两件后果不会自己消失**：
① 若选窗口乙（纯累计），**已经被封死的桶不会自动解封**（没有"解封"入口）—— 这正是甲被选中的原因之一。
② 窗口不一致（`MAX_THREAD_COST` vs 会话 token 上限）**仍然在**，由 `①b` Task 6 一并处理。

## ⬜ 遗留 / 未决

1. 🔴 **`/ws/agent` 整条 WebSocket 没有鉴权** —— 没有用户身份，只能用 `user_name="unknown"`。
   ⇒ 该链的用量**全部记在 `unknown` 名下**，会话 key 实际退化成「每连接」。
   ⬜ **这是本轮**顺带**发现的既有问题**（不在 B8 范围内），**记在这里，⛔ 不顺手改**。
2. **`thread_id` 没有生命周期** —— 用户自己传，无过期、无回收。
   窗口选了「按日」正因如此：**日窗口至少给了用户一条自救路径（等到明天）**。
   ⬜ **但"一个会话桶该活多久"本身没人定** —— 不在 B8 范围内。
3. **`/ws/agent` 的拒绝方式** —— HTTP 端点抛 `AppException` 即可；
   WS 那条**没有 HTTP 状态码可用**，走「发一帧 `type:"error"` 再继续/关闭」，
   与它现有的 `except` 分支同一格式。
4. **`estimated_tokens` 谁来估** —— 接口留了参数，本轮**调用点一律不传**（= 只判已用量）。
   ⬜ 预估要准，得先有"按输入长度估 token"的东西，不在本轮。
