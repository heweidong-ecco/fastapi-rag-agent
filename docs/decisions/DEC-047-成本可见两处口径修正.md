## 决策事项

`B13` 的原话是「**先实跑核一遍，缺了再补**」，判据是「**界面上能直接看到数字；
能回答『今天花了多少、还剩多少』**」。2026-10-03 照着跑了一遍（起服务 → 看 4 个面），
**四个面都打得开**，但核出两处**"看代码会误判"**的错。

⚠️ **两处的共同点**：**不报错、测试全绿、界面照常出数**。
⇒ 这正是本仓反复栽的那一类（`docs/规范/开发规范.md` §3.1）。

| # | 核出来的事实 | 为什么它危险 |
|---|---|---|
| **一** | `/agent/cost/overview` 的三个总数读的是 **`get_user_summary` / `get_purpose_summary` —— 进程内存**（`token_tracker.py` 顶部三个 `defaultdict`，只在 `record_usage` 里累加、**从不回读 DB**）⇒ **重启归零**。<br>🔴 **实测**：admin 在 `token_usage_logs` 里有 **4216 tokens / 6 行**，端点答 **`0`** | 它的 docstring 自称「**这是最直观的"花了多少钱"查询接口**」。<br>⇒ **重启一次，"花了多少钱"就答 0**，而**没有任何报错**。<br>⚠️ 同一份响应里 `total_*` 是**本人**、`by_purpose` 却是**全站** —— 两个口径串在一个 JSON 里 |
| **二** | `B10`/`B11` 的**全站日级额度**（超了 `1_000_000` ⇒ **所有人**吃 429）**没有任何出口** —— `get_global_daily_token_usage()` 全仓**只被 `breaker` 调过**，无端点、看板也不显示 | `B13` 的判据里「R4.2『还剩多少』**依赖 `B10`**」指的就是这个数。<br>⇒ **用户级"还剩多少"答得出**（`/agent/token/budget`，库口径 ✅），<br>**全站级"还剩多少"答不出** —— 看不见它逼近，只能等 429。<br>⇒ **`B13` 的判据只成立了一半** |

## 备选方案

### 一 · `/agent/cost/overview` 的总数怎么办

| 方案 | 一句话 | 评价 |
|---|---|---|
| **甲 · 换数据源：新加 `get_user_overview()`（**采纳**）** | 保留那两个内存函数**原样**，另建一个**读库**的函数专门供对外展示 | ✅ **两个消费场景本来就不是一个语义**：`:148` 的告警要的是"本进程这段时间花了多少"（**不该**查库）；展示要的是"一共多少"（**必须**查库）<br>✅ 不动 `:148`，**不会把即时告警变成全时告警**（那是乙的坑） |
| 乙 · 把 `get_user_summary` 本身改成读库 | 一个函数两种用途 | ⛔ `token_tracker.py:148` 的**日花费告警**读的就是它。<br>改了之后告警语义从"本进程"变成**"全时累计 > 阈值"** ⇒ **重启后第一次调用就误报** |
| 丙 · 不改代码，只把文档改成实话 | 承认它是"本进程累计" | ✅ 零风险<br>⛔ 等于**把"最直观的花了多少钱"永久让给一个重启即失效的数** —— 与 `B13` 的判据（"界面能直接看到数字"）正面冲突 |
| 丁 · 删掉这个端点 | 让位给 `/agent/token/history` · `/agent/cost/records` | ⛔ 那两个是**明细/按天**，不是"总览"；且它已被 `B13` 列为落点 ⇒ 删了要重开一轮 |

| 方案 | 评价 |

| **甲 · 跟着 `total_*` 走，改成【本人】（**采纳**）** | ✅ 端点 docstring 写的就是"展示**当前用户**的 Token 消耗和费用概况"<br>✅ 一份响应里只有一个口径 |

| 方案 | 评价 |

| **甲 · 加进 `/agent/token/budget` + 看板第 5 格（**采纳**）** | ✅ 那个端点**就是回答"还剩多少"的地方** ⇒ 用户级与全站级**放在一起看才比得出来**<br>✅ 复用现成的 `get_global_daily_token_usage()` + `GLOBAL_DAILY_TOKEN_LIMIT`，⛔ **不新写汇总**（`B13` 明令） |

| 丙 · 只在看板显示 | ⛔ 看板是给人看的；**程序化取数**（告警 / 自检 / eval）拿不到 ⇒ 只算半个出口 |

## 决策与理由

**四处全部采纳「甲」。** 归成一句话：

> **一个函数只服务一个语义；一个响应只用一个口径；"还剩多少"的两个层级放在同一个接口里。**

- **一** —— 内存那三个函数**不是坏的**，它们服务的场景（进程内即时告警）**本来就不该查库**。
  坏的是**拿它们当对外展示的数据源**。⇒ 分开，⛔ 不是"把内存的改掉"。
- **二** —— `total_*` 这个名字已经把窗口写死了；选别的窗口要么与 `R1.3` 重复，要么让名字变成谎话。
- **三** —— 一个响应里混两个口径，**字段名还不区分** —— 这是本次两处错里**更难发现**的一处
  （数字"看着正常"，只是范围不对）。
- **四** —— `B13` 的落点单里就写着 `/agent/token/budget`；而且**"还剩多少"必须能同时看到本人和全站**，
  否则看到 `999961` 也不知道那是谁的上限。

### ⚠️ 四条必须一起写下来的（否则下一个人会当成 bug）

1. **内存那三个 `get_*_summary` 仍然存在、仍然有调用点**（`:148` 告警 · `/agent/token/overview` ·
   `/agent/thread/{id}/overview` · 看板「调用统计」）。⛔ **看到它们别当残留删掉** ——
   它们的语义是"本进程"，只是**不能当对外展示的数据源**。判据见 `test_cost_visibility.py`。
2. **`get_user_overview` 的窗口是【全时】**，⛔ 不是今天 —— 与 `B10` 的 `test_yesterdays_usage_does_not_count`
   **方向正好相反**（那边必须排除昨天，这边必须包含）。两个判据在同一天落地、**意图像是相反的**，别互相"修正"。
3. **`global_remaining` 在查库失败时会显示"还剩满额"** —— 因为 `get_global_daily_token_usage()`
   是 **fail-open**（返回 `0.0`，`DEC-042`）。⛔ **没有加特判**，与同族取舍一致；
   但要知道**它看不出来是"真 0"还是"库挂了"**。
4. **看板第 2 格「调用统计」仍然是内存口径**（本轮**只改标签**，没改逻辑）——
   ⬜ 见 §遗留 1。

## 反悔成本

**低。**

- **要回到内存口径** ⇒ 把 `agent_cost_overview` 里那一行换成 `get_user_summary` 即可（一次 `git revert`）。
- **要换窗口**（全时 → 近 N 天）⇒ 只改 `get_user_overview` 的一条 SQL + 两处 docstring；
  ⛔ 但**同时要改 `test_cost_visibility.py` 里"SQL 不许有 `CURRENT_DATE`"那条判据**，
  否则它会拦——⚠️ **这正是它存在的意义**。
- **要撤掉全站字段** ⇒ 字段是**加法**，删掉不影响任何既有调用方。

⚠️ **不会自己消失的两条**：
① **`by_purpose` 从全站变本人是一次【对外可见的行为变化】** —— 若有外部消费方依赖旧的"全站"语义，
   它会**静默拿到更小的数**。本仓现在的 `grep` 结果：**除测试外无消费方**。
② **内存与库两套口径同时存在**这件事**本轮没有消除**，只是**划清了各自的适用面**。
