## 一 · 审计：现状是什么（**全部有出处，⛔ 不是从印象推的**）

### 1.1 三层分开看 —— 只有中间那层是齐的

| 层 | 回答的问题 | 现状 | 在哪 |
|---|---|---|---|
| **鉴权** | 你是谁 | ✅ 齐 | `api/deps.py`（`get_current_user` / `…_jwt` / `…_hybrid`）· `api/auth.py` |
| **角色** | 你是什么级别 | 🟡 有，但**硬编码** | `api/permission.py` |
| **授权** | **你能碰谁的资源** | 🔴 **没有这一层** | —— **散在每个端点自己手里** |

**关键一条**：`api/auth.py`（**107 行**）只有三件事 —— **发 key / 验 key / 验口令**。
它**从头到尾没有任何隔离逻辑**，且**按职责也不该有**：它验完只返回一个 `user_name` **字符串**就结束了。

```python
# api/deps.py:55 —— 三种认证方式，出口【都是同一个 user_name 字符串】
async def get_current_user_hybrid(...) -> str:
```

- `api/auth.py:106` `authenticate_user()` —— 拿 `_get_users_db()`（**来自环境变量**）比对口令；
- `api/jwt_handler.py:25-31` —— JWT 的 payload **只有** `sub`（用户名）+ `type` + `exp` ⇒ **角色不在 token 里，每次请求现算**；
- `api/permission.py:26-35` —— `get_user_role()`：`admin`→ADMIN · `test_user`→PREMIUM · **其余一律 FREE**（**硬编码，未接 DB**）。

`require_admin`（`deps.py:68`）全仓**只用在一个端点**上：`POST /users/create`（`api/api_v1.py:159`）。

### 1.2 🔴 核心事实：**七条检索路径，只有 2 条按人过滤**

| # | 检索端点 | 召回 SQL / 调用 | 按人过滤 |
|---|---|---|---|
| 1 | `POST /rag/pg_search` | `api_v1_rag.py:411` `WHERE requested_by = %s` | ✅ |
| 2 | `WS /ws/agent` | `api_v1_rag.py:972` `WHERE requested_by = %s` | ✅ |
| 3 | `POST /rag/hybrid_search` | `hybrid_search(query, top_k)`（`hybrid_search.py:74`） | ⛔ **签名里根本没有 user 形参** |
| 4 | `POST /rag/rerank_search` | `rerank_search(query, top_k)`（`hybrid_search.py:93`） | ⛔ 同上 |
| 5 | `POST /rag/rewrite_search` | `hybrid_search_with_rewrite(query, top_k, history)`（`:105`） | ⛔ 同上 |
| 6 | `POST /rag/search` | `pipeline.search_async(query, top_k, history, generate_answer)`（`rag_pipeline.py:54`） | ⛔ 同上 |
| 7 | `POST /rag/jwt_ask` | `api_v1_rag.py:549` `SELECT content FROM documents LIMIT %s` | ⛔ **连 `WHERE` 都没有** |
| 8 | `POST /rag/stream_search` | `api_v1_rag.py:647-651` `FROM documents ORDER BY … LIMIT` | ⛔ **同样零 `WHERE`** |

> ⚠️ **看代码最容易误判的一处**：第 3/4/5/6 条的返回体里**有** `"requested_by": user_name`
> （`api_v1_rag.py:446` `:461` `:476` `:529`）——
> **那只是个回显，⛔ 不是过滤**。看到这个字段就以为"按人筛过了"，是**本仓最容易踩的误读**。

### 1.3 ✅ 做对了的地方（**而 `thread_id` 该抄的正是这个**）

| 位置 | 做法 | 判据 |
|---|---|---|
| **写入文档** | 三处 INSERT 都记 `requested_by = user_name` | `api_v1_rag.py:157` `:259` `:318` |
| **删文档** | **真查归属**：非 admin 且 `owner != user_name` ⇒ 403「只能删除自己上传的文档」 | `api_v1_rag.py:341-349` |
| **对话历史** | Redis key = `chat_history:{user_name}` —— **身份由鉴权给**，调用方碰不到 | `api/cache.py:43` |
| **长期记忆（mem0）** | `user_id = f"{user_name}:{memory_space}"` —— **身份前缀 + 调用方子空间** | `api_v1_agent.py:521` `:536` |

> 🔴 **第 4 行就是本 DEC 要推广的那个模式**：
> **「命名空间 = 鉴权身份 + 调用方自选的子空间」**。
> `thread_id`（`api_v1_agent.py:484`，默认 `"default"`）**偏偏没走它** —— 它是**裸的调用方字符串**。

### 1.4 真库佐证（2026-10-03 实查）

```bash
docker exec postgres-rag psql -U postgres -d rag_db -tAc \
  "SELECT requested_by, count(*) FROM documents GROUP BY 1;"
#   admin|84
docker exec postgres-rag psql -U postgres -d rag_db -tAc \
  "SELECT user_name, expires_at::date FROM api_keys;"
#   admin|2036-09-07
```

⇒ **全库 84 篇文档，`requested_by` 100% 是 `admin`；`api_keys` 里只有 admin 一个用户。**

### 1.5 ⇒ 结论：这个洞**现在是「潜伏」，⛔ 不是「已在漏」**

- **今天谁也读不到"别人的"文档 —— 因为不存在"别人"。** ⛔ 不许把这句讲成"已经在泄露"；
- 但**第二个用户一旦上传，它立刻变成真的跨用户读取**，且覆盖面 = **除第 1/2 条外的全部检索入口**；
- ⇒ **业务方那句判断成立**：「先创建几个测试用户并单独存入数据」——
  **只有一个上传者时，「隔离有没有用」这件事在物理上就测不出来。**

### 1.6 admin 的「配额」与「权限」（业务方 2026-10-03 点名要核的第二处）✅ 已核

业务方原话：「**admin 之前执行了降权和 premium 一样了，具体核一下**，
但是 **X_api_key 的权限不能降**，是**管理和创建的 admin 这个功能要保留**。」

#### 🔴 核出来的第一件事：**「降权」降的是【配额】，⛔ 不是【权限】**

| 事实 | 出处 |
|---|---|
| `ROLE_DAILY_TOKEN`：`admin` **曾是 `float("inf")`**，**2026-09-30 裁 / 10-01 实施后 = `100_000`**（= premium） | `api/token_config.py:48-53`，原文注释：「✅ 2026-09-30 裁（实施 2026-10-01）：admin = premium，⛔ 不再是 `float("inf")`」 |
| **有测试钉着它**（⛔ 不是"我记得"） | `api/test_token_config.py:16-17`：`assert ROLE_DAILY_TOKEN["admin"] != float("inf")` **且** `== ROLE_DAILY_TOKEN["premium"]` |

#### ✅ 核出来的第二件事：**「管理和创建」没有被降 —— 不用改**

**两条独立证据**（缺一条都不算核过）：

1. **`require_admin` 判的是【角色】，⛔ 不是配额** —— `api/deps.py:68-76` 走
   `permission.get_user_role(user_name) != UserRole.ADMIN` ⇒ **配额怎么改都碰不到它**。
2. **创建用户那条路【根本不进配额中间件】** —— 实测三处对上：

   ```bash
   # ① 真实路径（本版 FastAPI 用 _IncludedRouter 惰性挂载 ⇒ app.routes 里看不到，必须问 router）
   venv/bin/python -c "import sys;sys.path.insert(0,'api');import api_v1;\
     print([r.path for r in api_v1.router.routes if 'create_user' in r.path])"
   #   ['/api/v1/admin/create_user']
   # ② 豁免名单里逐字就有它          api/main.py:111
   # ③ 中间件开头就跳过整个名单       api/main.py:293
   ```

   ⇒ **admin 当天额度用光，`/api/v1/admin/create_user` 照常可用。**

> ⚠️ **豁免的只是【配额 + 限流】，⛔ 不是【鉴权】** —— 端点自己仍挂 `Depends(require_admin)`，
> 所以**只有 admin 调得动**。这个设计是对的（`DEC-046` §甲 写的「覆盖范围不变」成立）。
>
> 📌 **记一笔踩过的坑**：这条豁免写的是 `admin/`，而端点**函数名**叫 `create_user`
> ⇒ **我一度怀疑它是「挂在空处的死条目」**，核了才确认**逐字命中、是活的**。
> **判据：`PUBLIC_PATHS` 这类名单要拿【真实路由表】对，⛔ 不能拿函数名猜。**

#### ✅ 但有一处**确实变了** —— 业务方已裁：**按实际保持不动**

**admin 自己的 LLM 用量现在封顶 100k/天**（以前无限）—— **这才是「降权」的本体。**

> ✅ **业务方 2026-10-03 裁**：「**按实际的该**」⇒ **保持 `100_000` /天 不动**，
> ⛔ **不改 `token_config.py`**（`admin` 继续 = `premium`）。
>
> **理由是**：admin 的真需求是「**能管人**」，那个**已经豁免了**（本节前面两条证据）；
> 而**无限 LLM 额度在生产上是账号失控风险**（key 一旦泄露，账单没有上限）。
> ⇒ **"管理权限"与"LLM 额度"是两件事，本 DEC 只保住了前者，后者维持现状。**

## 二 · 根因：**没有中间授权层 ⇒ 默认是 fail-open**

| 表现 | 同一个根因 |
|---|---|
| 七条检索里五条不过滤 | 每个端点**自己决定**要不要加 `WHERE` |
| 新写的端点默认不过滤 | **不写就是全库** ⇒ 默认放行 |
| `thread_id` 不绑身份 | 没有一处规定"用户给的标识必须拼身份" |
| `/agent/approve` 无归属校验 | 同一个缺口，在**写侧** |

⇒ **判据：这不是"某几个端点忘了写"，是"没有一层东西强制他们写"。**
⇒ 所以修法**不能只是逐个补 `WHERE`** —— 那样下次加端点**还会漏**。
（同源道理见 `agent-pitfalls-kb` A2：**「装了 skills ≠ 会用 skills」—— 有结构才执行，只有文字就漏。**）

## 四 · 决策

### 决策 1 · **排序：读侧隔离（甲）在前 ⇒ `memory_chat`（乙）在后**（业务方 2026-10-03 已裁）

| 段 | 内容 | 谁在等它 |
|---|---|---|
| **甲 · 底座** | ① 测试用户/数据基建 ② **身份怎么贯穿到下游**的约定 ③ 一条**会红的**跨用户隔离用例 | 🔴 **`/agent/memory_chat` 的审批门等的是这一段** |
| **乙 · 逐端点收口** | 1.2 表里那 5 条各自补过滤（**可分批**） | 不等 |
| **丙 · `memory_chat`** | `thread_id` 拼身份 + 审批门（`DEC-051` §遗留·2） | 等**甲** |

**为什么这个顺序对**（业务方给的理由，我核对后同意）：
两个任务**唯一的交叠点就是「身份怎么贯穿」**——甲解决「`user_name` 怎么进 `hybrid_search(query, top_k)`」，
丙解决「调用方给的 `thread_id` 怎么拼命名空间」。**这是同一件事的两种形态。**
先做甲 ⇒ 约定定下来，丙**直接套用**；先做丙 ⇒ 我另写一套拼法，甲做完**又得回头改丙**。

⚠️ **本 DEC 加一条边界**（防止甲变成无底洞）：**丙只依赖甲的 ①②③ 三件，不等乙。**
甲做完（**不是"8 个端点全补完"**）丙就可以开工。

### 决策 2 · **测试基建先行：造多个测试用户 + 各自的数据/文档**（业务方 2026-10-03 已裁）

| 项 | 定 |
|---|---|
| **造几个** | **3 个**（业务方 2026-10-03 裁）：<br>· `isolation_a` · `isolation_b` —— 角色 **`FREE`**（主力对照：**A 不能看见 B 的**）<br>· `isolation_c` —— 角色 **`PREMIUM`**（业务方追加）⇒ 验「**非 admin 的角色不享受 admin 的读侧例外**」<br>⛔ **不许拿 admin 当测试对象** —— admin 在读写两侧**都是特例**，拿它测边界**测不出规则** |
| **⚠️ `isolation_c` 有一处坑：要改【硬编码】才成立** | `permission.get_user_role()`（`api/permission.py:26-35`）**只认 `admin` / `test_user`**，其余一律 `FREE` ⇒ **不加分支的话 `isolation_c` 会被判成 FREE，那个"premium 对照组"就废了**。⇒ 必须在 `get_user_role` 的 PREMIUM 分支里加上 `isolation_c`（**这是代码改动，⛔ 不是纯配置**） |
| **怎么造** | 走现成的 `auth.create_user_api_key(user_name, expire_days)`（`auth.py:15`）。⚠️ 它**只在生成时返回一次明文** ⇒ 落在 **`.env`**（本仓已有且**已被 `.gitignore` 排除**），⛔ 不进仓、⛔ 不写进测试文件 |
| **谁有权造** | `POST /api/v1/admin/create_user` 是 **admin-only**（`Depends(require_admin)`，`api_v1.py:157-159`）⇒ 用 admin 的身份去造 |
| **数据怎么区分** | 每篇探针文档的 `source` 打可识别标记（如 `isolation-probe-<日期>`）⇒ **可一键定位**（⚠️ **不必一键清**，见决策 6） |
| **身份怎么留档**（业务方 2026-10-03 裁） | 「**在对应代码位置注释或者写文档记录这几个用户身份**」⇒ **两处都做**：<br>· `api/permission.py` 的 PREMIUM 分支上写明 `isolation_c` **是测试用户**（⛔ 别让后人当成真业务角色）<br>· 本 DEC 的这张表（+ §七 裁决）就是那份记录，⛔ **不再另开文件** |
| **⚠️ 落点** | **就是那个真库**（业务方 2026-10-03 裁：「**不单开测试库**」）—— `api/conftest.py` 用 `TestClient(app)`，**本来就没有独立测试库**：`.env` `POSTGRES_PORT=5432` · `docker port postgres-rag` = `5432/tcp -> 127.0.0.1:5432` · `config.py:87` 非 Docker 时 `POSTGRES_HOST="localhost"` ⇒ **host 上跑的 pytest 直连容器里那一个 `rag_db`** |

⇒ 🔴 **由此得一条硬约束：⛔ 不许为了做测试往 `documents` 里灌大批量真文档** ——
探针数据是**加性**的、**小**的，且**只放合成内容**（见决策 6）。

### 决策 3 · **判据 = 「看得见 / 看不见」，⛔ 不是「过滤语句存在」**

这是本 DEC 最重要的一条，因为它直接决定"修没修好"怎么判：

| ⛔ 错的判据 | ✅ 对的判据 |
|---|---|
| `grep -c "requested_by" api_v1_rag.py` 变多了 | **用户 B 用真问题去检索用户 A 的文档 ⇒ 召回里没有 A 的** |
| 「我在函数签名里加了 `user_name`」 | **不传 `user_name` 的调用点会【报错】，而不是静默查全库** |

**先写会红的用例**（`test-driven-development`）：现在跑 ⇒ **A 的文档会被 B 召回**（红）；
修完 ⇒ 绿。**⛔ 没见过它红的用例，不算数。**

### 决策 4 · **身份贯穿：显式形参，⛔ 不用 contextvar / 全局态**

| 备选 | 判定 |
|---|---|
| **(a) 把 `user_name` 作为显式形参往下传**（`hybrid_search(query, top_k, user_name=...)`） | ✅ **选它** —— 调用点看得见"这里依赖身份"，改漏了**编译/运行就炸** |
| (b) `contextvars` 隐式传递 | ⛔ **不选** —— 改动最小，但**调用点看不出它依赖身份**；本仓已有「默认值填充 / 隐式依赖」的前科（`DEC-051` 的两个静默失效 bug 就是隐式假设造成的） |
| (c) 只改 SQL、不动函数签名 | ⛔ 单独不够 —— 5 条路径**拿不到 `user_name`**（端点有，但检索函数签名里没有这个口子） |

> ⚠️ **成本要如实说**：`rag_pipeline.py` 是**工厂 + 流水线模式**（`create_*_pipeline()`），
> 加形参要动**所有 pipeline 类**（`search_async` 及其内部对 `hybrid_search` 的调用）。
> 这是乙段里最大的一块，**要在甲段就把它估进去**。

### 决策 5 · **fail-open → fail-closed：让「按人过滤」成为必填**

根因那节说了：**补一轮 `WHERE` 治不了病**。⇒ 定一条结构约束：

> **检索函数的身份参数【必填、无默认值】。**

⇒ 效果：**新写的调用点不传就报错**（而不是静默查全库）。
⇒ 这才是把"软约束"（写在文档里）变成"结构约束"（写在签名里）。
📌 与 `docs/规范/开发规范.md` 里那条「**门要挂在会被走到的地方**」同源。

### 决策 6 · **探针数据【长期保留】在真库里**（业务方 2026-10-03 裁）

业务方原话：「**我的建议是不单开测试库，直接在现有数据库中加入就可以**，
在对应代码位置注释或者写文档记录这几个用户身份，**不要再开单独的数据库去处理**，
这几个用户**数据不大，就保留着**，放在现有数据库中，**之后部署出去，如果有类似问题，
这些也可以当做到时候的测试 document**。」

⇒ **采纳。** 但**理由要写对**，否则将来有人照错的理由做决定：

| ⛔ 不能当成理由 | ✅ 真正的理由 |
|---|---|
| 「**数据不大**，所以留着没事」 | **修完甲段之后，这些文档对【别人】根本不可见**（`requested_by` 过滤生效）⇒ **对真实用户零影响**。<br>⚠️ **与"大不大"无关** —— 再小，只要别人能召回，就是污染 |

**⇒ 由此定三条约束**（前两条是**安全前提**，⛔ 不是建议）：

1. 🔴 **只放合成内容** —— ⛔ **不许放任何真实资料**（真实业务文档 / 真实用户数据）。
   **理由**：在**甲段修完之前**，它们**对所有人都可见**（那正是这个洞本身）。
   这是个**时间窗口**，窗口内的内容必须是"被人看到也无所谓"的。
2. 🔴 **内容要自我标识** —— 正文里就写明"**这是隔离测试数据**"。
   **理由**：万一被误召回，LLM 会**拿它当知识回答** ⇒ 用户看到莫名其妙的内容；
   自带标识 ⇒ 回答至少是**自解释**的（⛔ 而不是"这模型怎么胡说八道"）。
3. 🟡 **`source` 打标记**（`isolation-probe-<日期>`），**并把"若要清怎么清"写下来**（§六 ④）——
   ⚠️ **即使本轮不打算清**。理由：将来真要清时，"**是哪几条**"**不能靠回忆**
   （本仓已有前科：判据靠记忆 ⇒ 记错）。

> ⚠️ **另外**：业务方那句「**之后部署出去可以当测试 document**」是个**额外收益**，不是"反正要留着"的借口 ——
> 它的成立前提**同样是第 1 条**（内容合成 ⇒ 拿到别的环境也敢用）。
>
> 📌 **测试用户本身**（`api_keys` 里那 3 行）**是加性的、无害**，与文档分开判。⚠️ 但 `isolation_c`
> 要在 `get_user_role` 里**留一行注释**说明它是测试用户（见决策 2）。

## 遗留

1. **`/agent/approve` 没有归属校验**（`api_v1_agent.py:300-362`：`thread_id` 由调用方给，
   函数体里 `user_name` **只出现在返回体的 `requested_by`**）—— 与读侧**同一个根因**，
   但落点不同（写侧）。**排期另定**，⛔ 不并进本 DEC 的实施范围。
2. **`pending_approvals.register()` 同一 `thread_id` 会覆盖**（`api/pending_approvals.py:28` 自己写着
   「同一 thread 重复登记 ⇒ **覆盖**」），而 `thread_id` 默认 `"default"` ⇒ **多用户下静默顶掉**。
   属决策 4 那个"标识必须拼身份"的同族问题。
3. **长期选项登记**：① ~~独立测试库~~ —— 🔴 **本轮已明确不做**（业务方 2026-10-03 裁「**不单开**」）。
   ⚠️ **重估触发条件**：探针数据将来若**变大**、或**掺进真实资料** ⇒ 那时候要重提。
   ② **Postgres RLS** · ③ **一处集中的授权层**（**本轮做的正是它的轻量版** = 决策 5 的 fail-closed）。
   ⚠️ 三者**互不替代**：① 管测试卫生 · ② 管数据库层防线 · ③ 管代码层不再漏。
4. **`/rag/stream_search` 与 `/rag/jwt_ask` 的 `WHERE` 是【零】**（不是"过滤写窄了"）——
   补的时候要**连语义一起定**：这两条按人过滤之后，**召回量会掉的**（用户自己的库可能很小），
   ⚠️ 别修完发现"答案质量下降"又回退 ⇒ 这是**产品面**的取舍，**要业务方知情**。
5. **`get_user_role()` 仍是硬编码**（`api/permission.py:26-35`）⇒ 🔴 **本 DEC 的 `isolation_c` 直接依赖它**：
   必须**改这张表**加 PREMIUM 分支（决策 2），并**留注释说明它是测试用户**（⛔ 别让后人当成真业务角色）。
   ⚠️ **连带**：§七 裁决 2 给 admin 的**读侧例外**，判据**也落在这张硬编码表上** ⇒
   将来它接 DB（`DEC-046` §遗留 4）时，**两处要一起改**。
6. ⚠️ **`/api/v1/admin/create_user` 同时豁免了【限流】中间件** —— `PUBLIC_PATHS` 对**两个中间件都生效**
   （`main.py:166` 与 `main.py:293`）⇒ **创建用户这条路上没有速率限制**。
   风险低（仍需 admin 身份），但**记一笔**：将来若要做「管理接口限流」，**照通常思路会漏掉它**。
