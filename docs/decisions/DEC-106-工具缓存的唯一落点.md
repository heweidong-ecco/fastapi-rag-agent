# DEC-106 · 工具缓存的**唯一落点** —— 收到工具函数体（`api/tool_cache.py`），调用层不再自己缓存

| 项 | 内容 |
|---|---|
| **状态** | ✅ **已实施（2026-10-08）** —— 批① Task 1 / 2 / 3 三笔合起来构成它 |
| **触发** | **批①「工具缓存收口」**。施工单在 `docs/ledger-reconcile` 分支上；本 DEC 把它的**决策面**落到本分支 |
| **类型** | 架构落点 · **可见行为变更** · 一处事实源 |
| **落点** | 新增 `api/tool_cache.py`；**删** `api/agent_graph_advanced.py` 的 `CACHE_TTL_MAP` / `get_cache_key` / `call_mcp_tool_with_cache` |
| **判据** | 见 §五（逐条可打印） |

---

## 一 · 要裁的是什么

「工具结果缓存」**放在哪一层**。改前它有**一份，但只盖住一条路径**：

| | 改前 | 改后 |
|---|---|---|
| 缓存在哪 | `agent_graph_advanced.call_mcp_tool_with_cache`（**调用层**） | `api/tool_cache.py` 的 `cached_tool` 包在**工具函数体**上 |
| 谁享受得到 | **只有** `/agent/mcp_chat` 那条路走这个函数 | **凡经 MCP 调工具的路径都拿到** |
| TTL 表在哪 | `agent_graph_advanced.CACHE_TTL_MAP` | `tool_cache.TTL_BY_TOOL`（**唯一一份**） |
| 键怎么算 | `md5` of `json.dumps(arguments, sort_keys=True)` | `tool_cache` 自己那套（含 `name=` 显式工具名） |

📌 **「只盖住一条路径」是这次收口的全部理由** —— 另外几条执行路径当时调的是
`call_mcp_tool`（**不带缓存**）⇒ 同一句 `date_today`，走 `/agent/mcp_chat` 会命中缓存、
走别的路不会。**同一个问题两个答案**。

🔵 **可打印的改动面**（见 §五 ①②）：三个名字**全仓消失**。

## 二 · 三个备选

| 备选 | 评价 |
|---|---|
| **甲 · 把调用层那份删掉，缓存收到工具函数体**（**选中**） | ✅ **一处事实源** —— TTL 表、键算法、失败判定各只有一份；✅ 四条路径自动共享；✅ 与 `mcp_server.TOOLS` 同层，**新工具接缓存只需登记 TTL**<br>⚠️ 代价：**可见行为变了**（见 §三） |
| 乙 · 保留调用层那份，不动 | ✅ 零行为变更<br>⛔ 「一条路径有缓存、别的没有」**继续存在** ⇒ 本批的目的（唯一落点）不达成 |
| 丙 · 两处都留 | ⛔ **两份 TTL 表**必然漂移；⛔ 同一工具可能**被缓存两层**（外层 300 秒套内层 300 秒，语义说不清） |

**⇒ 选甲。**

---

## 三 · 🔴 可见行为变更（**必须显式声明，⛔ 不许静默**）

**改前**：命中缓存时 `/agent/mcp_chat` 的工具结果返回

```
{结果}
[缓存命中]
```

**改后**：**没有这个后缀**。

- 为什么删：那个后缀是**调用层那份缓存**的产物；缓存搬走后**没人再拼它**。
  刻意**不**把它搬进 `tool_cache` —— 它是给**人**看的调试痕迹，而缓存现在在
  MCP server 进程里，**LLM 读到「[缓存命中]」只会干扰它对结果的判断**。
- ⛔ **别把这句读成"缓存没了"** —— 缓存还在，只是**不再往结果里写字**。

📌 **本仓曾有同形前科**：`search_tools` 当年把**未标记的模型输出**当搜索结果返回，
病根就是「**返回内容里混进了本不该给调用方看的东西**」。⇒ 这里同样：工具结果**只该是结果**。

## 四 · 反悔成本

| 项 | 成本 |
|---|---|
| 把缓存**搬回**调用层（乙） | **中** —— 要恢复被删的三个名字 + 撤掉四个工具的包裹 + 回退两处测试；⚠️ 且**四路径共享**这个好处会丢 |
| 把 `[缓存命中]` 后缀**加回来** | **低** —— 在 `tool_cache` 里加一行；⚠️ 但要先想清楚"LLM 读到它会不会误判" |
| 改 TTL 数值 | **零** —— `TTL_BY_TOOL` 一处 |

## 五 · 判据（**逐条可打印**）

```bash
# ① 三个名字全仓消失（调用层那份真删干净了）
grep -rn 'call_mcp_tool_with_cache' api/ --include='*.py'          # ⇒ 空
grep -rn 'CACHE_TTL_MAP'            api/ --include='*.py'          # ⇒ 只剩 tool_cache.py 的【搬运说明】注释
grep -rnw 'get_cache_key'           api/ --include='*.py'          # ⇒ 只剩 api/cache.py（**另一个**缓存，与本条无关）

# ② 那个后缀的【代码形式】没了（⛔ 别 grep「缓存命中」三个字：
#    api_v1.py:230/233 讲的是 /rag/benchmark-embedding 的 embedding 缓存，与本条无关）
grep -rn 'f"{cached}' api/ --include='*.py'                        # ⇒ 空

# ③ 工具缓存仍然生效（唯一落点真的在用）
cd api && ../venv/bin/python -m pytest test_tool_cache.py test_tool_cache_wiring.py -q

# ④ 走过这条路的那批用例**条数不变**（改前 11 / 60，见 CHANGELOG）
cd api && ../venv/bin/python -m pytest test_budget_hard_intercept.py test_agent_stream_chains.py -q
```

⚠️ **① 里的「只剩注释」要能解释**：`api/tool_cache.py:22` 那句
「本表从 `agent_graph_advanced.CACHE_TTL_MAP` **搬过来并收口**」是**搬迁留痕**，⛔ 不是死引用 ——
**删了它，下一个人就不知道这张表是哪来的**。

⚠️ **② 的写法本身就是一条教训**：施工单原写的是
`grep -rn '缓存命中' api/ | grep -v 'token_config\|embedding_client'` **⇒ 改后应为空** ——
🔴 **这条永远不可能为空**（`api_v1.py:230/233` 是无辜的第三方）。
⇒ 判据**取反检验**：把结论取反（"后缀还在"）⇒ 若那条命令**照样打同样的东西** ⇒
**这条尺子根本没在量它该量的事**。

## 六 · 边界

1. ⛔ **别把 `tool_cache` import 进 `*_impl` 模块** —— `simple_tools_impl` / `code_executor_impl`
   的不变量是「**只用标准库**」（那两个文件要能被单独抽出去跑）。缓存包在 `@tool` 那一层。
2. ⚠️ **`TTL_BY_TOOL` 是新增工具的唯一登记处** —— 忘了登记**不会 import 报错**，
   只有 `test_tool_cache.py::test_every_mcp_registered_tool_has_a_ttl` 会红。
3. ⚠️ **`date_today` 的 TTL 是 `0`（直通）** —— 它的缓存键只含空入参，
   缓存生效会「23:30 缓存、00:10 命中 ⇒ **返回昨天**」。
4. ⛔ **Redis 不通时不拒服务** —— 见 `DEC-105`（fail-open），本 DEC 与它**同批、互补**。
