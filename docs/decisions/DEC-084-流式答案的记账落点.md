## 一 · 这件事是什么

`/rag/stream_search` 的答案生成**从建立起一笔账都没记过**。

* 端点上的两道闸都在：`check_session_token_budget`（B8 会话上限）· `circuit(global_key())`（B11 全站熔断）
  —— 见 `api/api_v1_rag.py` 的 `stream_search` 函数体；
* 而 `api_v1_rag.py` **全文 `record_usage` / `record_from_response` = 0** ⇒
  **闸读的计数器它从不写** ⇒ 两道闸对这条链**等于不存在**。

⇒ 与 `DEC-072` 的原话**完全同型**：**「门在，锁坏了」**——
门挂在正确的位置（端点确实调了那两个函数），门后面的计量表没接上。

## 二 · 🔴 三处文档写着的前提，**实测是错的**

本仓**三处**文档写着同一条前提，并据此把这件事推迟了一整轮：

| 出处 | 原文 |
|---|---|
| `fastapi-rag-agent-TODO待办/施工单-20261005-RAG侧记账.md` §范围外·1 | 「要先给 `llm_factory` 开 `stream_usage`（否则 `ChatOpenAI` **根本不挂** `usage_metadata`）⇒ 会改**流式帧的形态** = 行为变更」 |
| `docs/待办总表.md` §一 · `DEC-073` 子表第 3 行 | 「`llm_factory` 没开 `stream_usage` ⇒ `astream` **不挂** `usage_metadata`；要记得**顺带开它**」 |
| `docs/specs/api_v1_rag.md` · `ROADMAP.md` · `CHANGELOG.md` | 「流式 usage 拿不到 / 协议上拿不到」 |

**实测（两次、独立）说不：**

1. **仓内既有探针** `fastapi-rag-agent-TODO待办/探针-流式与记账.py`（**2026-10-04**）§结论 1：
   > ✅ **记账【不会】因换流式而停** —— 本仓的 provider 在**最后一块**（`content` 为空的那块）上带
   > `usage_metadata` …… ⇒ **不需要** `stream_usage=True`（`False` 也拿得到）。
2. **本轮复测**（2026-10-06，同一形状反问一句）：

```
Q1 开 stream_usage 后是否拿到 usage: 是
Q3 帧序列是否相同: 相同 ✅          ← 开与不开，按 llm_chunk_text 口径过滤后【逐帧相同】
stream_usage=False（现状）：最后一帧 content=''  usage={'input_tokens':42,'output_tokens':30,…}
```

⇒ **三条结论**：
* **不需要**开 `stream_usage`（**现在的代码就拿得到 usage**）；
* **不会**改帧形态（`Q3` 相同）⇒ 当初"这是行为变更、要单独裁"的理由**不成立**；
* ⇒ 当年推迟这件事的**前提是错的**（⚠️ **不是"决策错"，是"事实核错"**）。

**⇒ 真根因只有一个**：**没有人去读那一帧**。
`llm_chunk_text(chunk)` 返回 `chunk.content or None`，而带 usage 的那一帧 `content=''`
⇒ 被判为"空块"丢掉；且流式路径上**没有任何 `record_from_response`**。

📄 复盘 ⇒ `docs/复盘/2026-10-06-未核的推断被当成前提写进文档.md`

## 三 · 裁定：记账落在**端点侧的一个 tap**

**做法**：`api/api_v1_rag.py` 新增 `_StreamUsageTap`，含两个方法：

* `extract(chunk)` —— **喂给 `sse.sse_stream` 的 `extract` 钩子**：
  对**每一块**做 `self._agg = chunk if self._agg is None else self._agg + chunk`，
  然后**照旧**返回 `llm_chunk_text(chunk)`（发帧口径**一字未动**）。
* `record(llm, *, user_name, thread_id)` —— **只在正常收尾那条出口**调用，
  把聚合块交给 `record_from_response(llm, agg, "answer_generation", …)`。

**为什么是 `extract`**：`sse_stream` 里唯一能看到**每一块**的钩子就是它 ——
`sse.py` 的循环是 `text = extract(item) …`，**排在 `if not text: continue` 之前**
⇒ 空 `content` 那一帧**必然**会经过它。骨架自己攒的 `collected` 只收**过滤后**的文本
⇒ 那份里永远没有 usage。

**为什么记账排在 `_complete` 的【第一行】（任何 `yield` 之前）**：
与 `sse.py` 约束① 同源 —— `yield` 是 await 点，被"二次投递的取消"打断
⇒ 排在它后面的收尾**一件都不跑**，可钱**已经花了**。
⚠️ `persist_turn` 仍留在原位（那是 `DEC-055` 定的），⛔ 本轮**不动它**。

### 判据（可打印）

```bash
venv/bin/python -m pytest api/test_rag_billing_wiring.py -q -k stream_search   # ⇒ 5 passed
git diff --stat api/sse.py api/test_cancel_propagation.py                      # ⇒ 空
```

**反证检验**（都真做过，⛔ 不是推断）：

| 把实现改坏成 | 预期 | 实测 |
|---|---|---|
| 聚合时 `if chunk.content:` 跳过空块 | 「空 content 那一帧也要记」那条变红 | ✅ 红 3 条 |
| 取消/异常出口也调 `tap.record` | 两条反向守卫变红 | ✅ 两条全红 |

⚠️ 第一次做第 1 项时**只红了 1 条** —— 因为测试里的假 `record_from_response` **比真的宽松**
（无脑 `append`，没复刻真函数"没有 `usage_metadata` ⇒ 恒 `False` 不记"的判据）
⇒ **桩已改成复刻真判据**。这条教训值得记：**桩比真的宽松 = 守卫漏网**。

## 五 · ⛔ 为什么不记「取消 / 异常」

usage 只在**最后一帧**回来；提前 `aclose()` ⇒ **那帧永远不到**。
硬补只能估算 = **往账本写假数** —— 比不记更坏（`DEC-053` §遗留·2）。

⇒ 本轮把这条**写成守卫**（不是"记得别做"）：
`test_stream_search_does_not_record_when_client_disconnects` ·
`test_stream_search_does_not_record_when_generation_raises`。

## 六 · ⚠️ 行为变更（必须说清）
