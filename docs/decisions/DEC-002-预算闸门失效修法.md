# 决策记录:DEC-002 · 三处预算闸门失效（单位错配）的修法

- 日期:2026-09-15
- 状态:已采纳
- 关联:M5 盘点 §0-2 / `api/token_tracker.py` / `api/agent_graph_advanced.py:245` / `docs/CODE_INVENTORY.md`

## 决策事项

一句话:`token_tracker.py` 用 **Token 预算** 减 **「元」消耗**(`remaining = get_user_token_budget(...) - get_daily_usage_cost(...)`),三处预算闸门因此**全部恒放行**。怎么修,才能既同量纲、又不引入第二处错配?

## 背景与约束

- **错配点 3 处**:`check_budget_before_call`(L506)、`check_multilevel_budget`(L626)、`check_budget_warning`(L668)。
- **实际危害分级**(已核实调用点):
  - `check_multilevel_budget` —— **唯一在真实请求路径上的闸门**(`api/agent_graph_advanced.py:245`,`tool_execute` 节点)。它的第三级(每日预算)失效后,真正还能拦的只剩**第二级**「单线程累计 ¥5」。
  - `check_budget_warning` —— 消耗达 80% 的告警**永不触发**,`/agent/mcp_chat` 响应里的 `budget_warning` 永远是 `None`。
  - `check_budget_before_call` —— 只被 `GET /agent/budget/check` 这个**诊断型**接口调用,**不在拦截路径上**。
- **可复用的现成件**:`get_daily_token_usage()`(L180-200)已存在、已按日过滤、返回 **Token**,**零改动可用**;`check_token_budget()`(L288-309)是**唯一量纲正确**的范本(Token vs Token)。
- **同一语义有三份实现**:`check_token_budget` / `check_budget_before_call` / `check_multilevel_budget` 第三级 —— 这正是 bug 的成因(同一件事多处写,写法还不一致)。
- **约束**:不引入新依赖;不动第一/二级「元」上限(它们量纲本就正确);`get_daily_usage_cost` **不能删**(`api/cost_dashboard.py:127` 的元看板仍在用)。

## 备选方案

### 第一层:取数单位怎么统一

| 方案 | 思路 | 优点 | 缺点 |
|---|---|---|---|
| **甲 预算折元** | 用 `PRICING` 把 Token 预算换算成金额 | 保留"元"作为唯一口径 | **必须同时重新标定 `ROLE_TOKEN_BUDGET` 的数值** —— 按 qwen-turbo 单价,free 的 10000 token ≈ **¥0.03**,比当前真实日消耗还低 ⇒ 从"永不拦截"变成"**过早拦截**",且拦得毫无道理。会让"名字叫 TOKEN_BUDGET 却存金额"更别扭 |
| **乙 消耗折 Token** | 三处取数换 `get_daily_token_usage()` | 复用现成函数、零改动;与 `check_token_budget` 的量纲一致;**数据层已就绪**(`token_usage_logs` 同时存了 3 列 token 与 1 列 cost) | 需要一并处理"预估花费"这个新错配(见第二层) |
| 丙 全面改元 | 新增 `ROLE_COST_BUDGET`,连 `get_token_budget_info` 一起改成元 | 副作用最小 | 要动对外 API 的返回字段语义(`api_v1_agent.py:329` 的消息、看板的展示) |

### 第二层:预估花费(元)怎么参与比较

| 方案 | 思路 | 优点 | 缺点 |
|---|---|---|---|
| **(a) 新增 Token 预估表** | 加 `TOOL_ESTIMATED_TOKENS` / `PURPOSE_ESTIMATED_TOKENS`,参数改名 `estimated_cost`→`estimated_tokens` | 保住"预估超额即拦"的设计意图;与第一/二级的前瞻语义一致;**有现成经验值锚点**(`agent_graph_advanced.py:302/340` 已在用 `estimated_tokens=500`) | 与现存"元"表并存 ⇒ 两份真相;需靠紧邻放置 + docstring 互相指名来缓解 |
| (b) 删掉该比较 | 第三级只留 `remaining <= 0` | diff 最小(每函数 −4 行);**不会引入新的单位错配**(因为不做那个比较) | 三级门禁语义割裂(前两级前瞻、第三级存量);删掉 4 处 message 与 2 处 `record_intercept` reason ⇒ `budget_intercepts` 表少一类拦截原因,历史数据与新数据不可比 |
| (c) 固定折算率 | 用一个模型无关的汇率把元折成 Token | — | 等于用一个更差的近似替代直接的 token 估计,且多一处要维护的魔数 |

## 评估标准

**修完真能拦住** / 是否引入第二处错配 / 与既有代码的重复度 / 数据基础是否就绪 / 回滚难度 / 对现有测试的影响。

## 方案对比

- **"修完真能拦住"**:甲会导致过早拦截(等于把 bug 换成另一种错误);(b) 会让"预估超额即拦"这一设计意图消失。**乙 + (a)** 是唯一两个都保住的组合。
- **数据基础**:乙 的可行性直接建立在一个已核实的事实上 —— `token_usage_logs` 表**同一行同时存了 `prompt_tokens`/`completion_tokens`/`total_tokens`(INTEGER)与 `cost`(REAL,元)**。所以"按 Token 算"不是退而求其次,而是**表里本来就有这条数据**。
- **对现有测试的影响**:⚠️ 关键事实 —— 所有测试与 locust 都登录 `admin`,而 `get_user_role("admin") → ADMIN → float("inf")`,**四个闸门全部在第一行就 early-return「管理员无限预算」**。所以本修复**在结构上不可能弄坏任何现有测试**;但**同样意味着用 admin 永远验不出修复效果**(见验证)。

## 最终决策 + 理由

**第一层选乙(消耗折 Token);第二层选 (a)(新增 Token 预估表)。**

理由:乙 复用了已存在、已按日过滤的 `get_daily_token_usage()`,零新增数据依赖;甲 需要重新标定常量,等于把"永不拦截"换成"过早拦截",不是修复。第二层必须选 (a) 而非 (b) —— 只换取数单位的话,`cost > remaining` 会从「元 vs Token」变成**反向的**「元 vs Token」,**错配只是换个方向,依旧恒放行**;而 (a) 的经验值不是凭空发明的,是把 `agent_graph_advanced.py:302/340` 已经在用的 `500` 收进常量表。

**放弃了什么**:放弃"统一到元"(丙)带来的口径单一性。**为何放弃**:那要动对外 API 的返回字段语义,收益(口径统一)不抵成本(改契约)。

## 影响与后续行动

- 抽出 `check_token_budget_detail(user_name, estimated_tokens) -> (bool, str)`,**消除三份重复实现** —— 只改单位不消除重复,下次依旧会漂。
- 9 处 `¥{x:.4f}` 文案改 tokens;`check_budget_warning` 返回 dict 的 `used_cost` 键改名 `used_tokens`(唯一消费者只读 `["message"]`)。
- 顺手处理(同主题):`record_cost` 的兜底价目表与 `record_usage` 不一致(`_DEFAULT_PRICING` 统一,**当前不可达**,属防御性);`agent_graph_advanced.py:302/340` 的 `check_token_budget` 在 `llm.invoke()` **之后**(钱已花,拦不住)→ 上移到 `invoke()` 之前。
- **验证必须用 `test_user`(非 admin)**:构造 `total_tokens=200000, cost=0` 的记录 —— **修前** `allowed: true`(复现),**修后** `allowed: false` 且文案是 tokens。

## 反悔成本

低。改动集中在 `token_tracker.py`(+ `agent_graph_advanced.py` 两处上移),独立提交可 `git revert`。**零 schema 变更、零迁移、零新依赖**,回滚后回到"三处闸门恒放行"的旧状态,**无数据损坏**。
