# 决策记录:DEC-001 · 公开仓库硬编码登录口令的处理路线

- 日期:2026-09-15
- 状态:已采纳
- 关联:M5 盘点 §0-1 / `api/auth.py:86-94` / `api/api_v1.py:73-82` / `docs/CODE_INVENTORY.md`

## 决策事项

一句话:仓库是 **PUBLIC**,而 `api/auth.py:87-89` 硬编码了明文登录口令,且该口令**在真实登录路径上**(`POST /api/v1/auth/login` → `authenticate_user`)。怎么消除这个暴露,同时不把项目改乱?

## 背景与约束

- **凭据事实**:`_users_db = {"admin": "<明文口令>", "test_user": "<明文口令>"}`(`api/auth.py:87-89`),`authenticate_user` 做**明文比对**(L92-94)。同一份口令还散落在 conftest / test_auth / test_integration / 3 个 locustfile / Postman(4 处) / `schemas.py:67` 的 Swagger example。
- **另一处更靠近"活凭据"的泄露**:`api/ rag-agent-api.postman_collection.json` 顶层 `auth.apikey` 与 collection 变量里各有一份 **35 字符真实形态的 API Key**(`sk-` + 32 hex = 正好是 `auth.py:6` 的生成格式),而该文件**已被 git 跟踪**。
- **关键事实(决定性的)**:`/api/v1/auth/login` 的**全部调用方都是测试、压测脚本、归档脚本与 Postman** —— 仓内**零生产客户端**。而 `X-API-Key` + `get_current_user_hybrid` 早已是一等公民(`api/deps.py:55-65`,约 40 个路由在用)。
- **没有任何数据层支撑**:全仓**无 users 表**(只有 `documents/api_keys/token_usage_logs/cost_records/cost_records_archive/budget_intercepts` 六张),`api/alembic/versions/` 下**无用户表迁移**,`requirements.txt` 里**无任何密码哈希依赖**(bcrypt/argon2/passlib 都没有)。
- **耦合**:`api/permission.py:18-29` 的 `get_user_role()` **按用户名字符串**给角色(`admin`→ADMIN→无限配额)。改凭证体系若不一起改它,角色判定仍是硬编码分支。本次业务方明确**不动** `permission.py`。
- **约束**:小步、不引入新依赖、不破坏现有测试、保持仓库既有风格。

## 备选方案

| 方案 | 一句话思路 | 优点 | 缺点 |
|---|---|---|---|
| **A 补数据层** | 新建 `users` 表 + `pbkdf2_hmac` 哈希口令(标准库) + 启动引导写入;`authenticate_user` 改为查库 | 最"正确";口令不再是配置而是数据;可扩展到多用户/改密/禁用 | 新增建表与迁移;而 `db.py` 的 SQLAlchemy 元数据**已与真实表漂移**(`documents_table` 缺 `requested_by`),新增迁移前得先收口径,否则 autogenerate 会误删列。**且与 M5「删代码」的方向相反** |
| **B 取消口令登录** | 删 `_users_db`/`authenticate_user`,`/auth/login` 改为「用有效 API Key / refresh_token 换 access_token」 | 删得最干净;与 `X-API-Key` 一等公民的现状一致 | **引爆半径最大**:所有测试、3 份 locustfile、Postman、2 个归档脚本**全部走账密登录**,无一例外,全要改成预置 API Key |
| **C 口令移到环境变量** | `config.py` 敏感段加 `LOGIN_PASSWORD`(缺失即拒绝启动,沿用 `validate_config` 既有风格),`_users_db` 由环境变量构造 | 改动最小、引爆半径最小;**彻底消除公开仓库的暴露**;与 `config.py:4`「敏感信息禁止设默认值」的既有契约一致 | **不新增数据层** —— 仍是「单管理员口令登录」形态;`permission.py` 的角色硬编码不动 |

## 评估标准

安全性 / 改动面 / 与现有代码的关系 / 是否契合 M5 方向 / 是否可实机验证 / 单人可维护。

## 方案对比

- **安全性**:C 已足够 —— 暴露的根源是"凭据进了公开仓库",而非"口令登录"这种形态本身。环境变量口令与数据库口令在**本场景**下安全性等价(都要求口令不出现在代码里)。A 的增量安全性(多用户/可禁用)在本项目**当前没有消费方**。
- **改动面**:C ≈ 11 处机械替换;B ≈ 全仓所有调用方改写;A ≈ 新建表+迁移+哈希实现。
- **与 M5 方向**:M5 的目标是**删掉多代际代码、删到能跑**。A 是**新增一个数据层**,方向相反。
- **决定性事实**:仓内零生产客户端 ⇒ B 的"兼容性收益"为 0,C 的"保守"也不构成技术债。

## 最终决策 + 理由

**选 C(口令移到环境变量)。**

理由:暴露的根源是"凭据进了公开仓库",C 用**最小半径**消除了它。A 增加一个当前无消费方的数据层,且与 M5「删代码」的方向相反;B 的收益(统一到 API Key)需要付出全仓改写测试资产的代价,而这件事**在 M5 收敛路由时会更自然地发生** —— 现在做属于顺序颠倒。

**放弃了什么**:放弃了一次性统一到 API Key(B)。**为何放弃**:那属于 M5 的主体范围(路由与认证收敛),应当与 Agent 图裁决一起做,而不是塞进"修一个泄露"这一刀里。

## 影响与后续行动

- 新增环境变量 `LOGIN_USER_NAME`(默认 `admin`)/ `LOGIN_PASSWORD`(必填,进 `validate_config`)/ `TEST_USER_PASSWORD`(可选)。
- **`test_user` 保留**,由可选变量驱动 —— 它是唯一**非 admin** 的现成账号(PREMIUM),而 DEC-002 的实机验证必须用非 admin(admin 在所有闸门第一行就 early-return「无限预算」)。
- ⚠️ **改代码不等于止血**:凭据在 `git log -p` 与任何已 fork 的克隆里**永久留存**。必须做运维动作:① 部署实例换新口令;② Postman 里那个 API Key 视同已泄露,`api_keys` 表删该行并重新签发。
- 后续(M5):认证体系统一到 API Key 的评估。

## 反悔成本

低。S1 是独立提交,`git revert <sha>` 即可;revert 后 `.env` 里多出的 `LOGIN_PASSWORD` 无代码读取,无害。
若日后改选 A(补数据层),代价是"新建 users 表 + 迁移 + 把 `authenticate_user` 改为查库",且**必须先解决 `db.py` 元数据漂移**,否则 alembic autogenerate 会误删 `documents.requested_by`。
