# 决策记录:DEC-003 · 压测口径错误修复改哪一侧（脚本 vs 端点）

- 日期:2026-09-15
- 状态:已采纳
- 关联:M5 盘点 §0-3 / `locustfile_hybrid.py` / `api/api_v1_agent.py:348-357` / `api/api_v1_rag.py:459-462`

## 决策事项

一句话:`locustfile_hybrid.py` 用 **json body** 打 `/agent/mcp_chat`(该端点只收 **query** 参数)→ 25% 权重的 Agent 压测必然 422;另有 `mode` 在 body 里而服务端读 query → **静默忽略**,压测标签全假。**修哪一侧?**

## 背景与约束

- **端点签名**:`mcp_agent_chat(question: str, thread_id="default", memory_space="default", user_name=Depends(check_budget))`(`api/api_v1_agent.py:348-357`)—— **无 Pydantic body 模型**,`question` 因此是**必填 query 参数**。
- **家族风格压倒性**:`api_v1_agent.py` 约 **30 个端点,0 个**接受请求体;而 RAG 家族全用 body(`QuestionRequest`)。两套风格泾渭分明。
- **仓内唯一的"约定证据"全部指向 query**:`docs/demos.md:66`、`Agent/docs/api_agent.md:52` 两处**官方 curl** 都是 `?question=...&thread_id=...`;`Agent/docs/api_agent.md:29-33` 的参数表也把 `question` 登记为**参数**而非请求体。
- **仓内零代码调用方**:Postman collection **完全不含** agent 端点;`test_*.py` 无 agent HTTP 测试;前端无。**唯一**用 body 调它的,就是待修的压测脚本自己。
- **`mode` 的真身**:`api/schemas.py:13` 的 `QuestionRequest.mode` 是**死字段**(全仓 `\.mode` 零命中)。`/rag/search` 把 `mode` 声明为**独立 query 参数**(`api_v1_rag.py:459-462`),分支判断用的是那个 query 变量(L474-481)。所以 body 里的 `mode` **被完全忽略**,所有请求实际都走 `accurate_norerank` —— **不报错,但压测口径全错**(`locustfile_v2.py` 的 `name="(基础检索)/(生成答案)/(带引用)/(多轮)"` 因此具有误导性)。
- ⚠️ **范围更正**:`mode` 问题**只涉及 `locustfile_v2.py`(5 处)与 `locustfile_hybrid.py`(2 处)**,`locustfile.py` 不传 `mode`,无关。
- **约束**:小步;不做破坏性 API 变更;压测数据需与历史基线可比。

## 备选方案

| 方案 | 一句话思路 | 优点 | 缺点 |
|---|---|---|---|
| **甲 改脚本** | 把三处 `json=` 改成 `params=`,`mode` 同步从 body 挪到 query | 改 1 个文件 3 处;**零生产代码风险**;贴合仓内已成文的 query 约定;`docs/demos.md` 与 `Agent/docs/api_agent.md` 不用改 | 压测覆盖面略缩(多轮任务不能再传客户端历史) |
| **乙 改端点** | 给 `/agent/mcp_chat` 加 Pydantic body 模型 | HTTP 语义更"正"(POST + 长文本 + 调 LLM 不该进 URL/access log) | **破坏性变更**:加了 body 后同名参数不能再作为 query 并存。会让该端点成为 agent 家族**唯一**的 body 端点(0/30 → 1/30);还要同步改 2 处官方文档 curl。**仓内代码破坏面为 0,但仓外调用方不可知** |
| 丙 两者并存 | 保留 query,另加可选 body | 兼容 + 语义兼得 | 复杂度和回归面显著高于改脚本,不符合"小步" |

### `mode` 的取值

| 取值 | 含义 | 后果 |
|---|---|---|
| **`accurate_norerank`(已选)** | **等于当前实际行为**(`api_v1_rag.py:462` 默认值 + L480-481 的 else 分支) | 把 mode 从"隐式默认"变成"显式声明",**正是修复"口径全错"的本义**,且**与历史基线仍可比** |
| `accurate` | 会额外打开 Cross-Encoder 重排(`rag_pipeline.py:231`) | 每请求耗时/成本大幅变化,**与历史基线不可比** —— 属**口径变更**,应作独立决定,不该夹在"修 422"里偷偷发生 |

## 评估标准

风险 / 改动面 / 是否贴合仓内既有约定 / 是否破坏兼容 / 与"小步"原则的契合度 / 压测数据的可比性。

## 方案对比

- **兼容收益**:乙 为 0 —— 仓内**没有任何**代码调用方,唯一的消费者就是压测脚本自己。
- **"文档即契约"**:本仓库已经吃过一次文档腐化的亏(`api/ rag-agent-api.postman_collection.json` 与 `archive/artifacts/rag-api-openapi.json` 是同一次导出、同一代际的两份,且**都已失效**)。乙 会让两处官方 curl 立即变错。
- **顺序问题**:改进压测脚本的正确做法是**让脚本贴合被测系统**,不是**为了压测脚本去改线上 API 契约** —— 后者顺序反了。

## 最终决策 + 理由

**选甲(改脚本);`mode` 统一取 `accurate_norerank`。**

理由:仓内**唯一的约定证据全在 query 一侧**(两处官方 curl + 参数表),而**唯一**用 body 的调用方就是待修的脚本本身;改脚本零生产风险,改端点则是不可逆的契约变更却无兼容收益。`mode` 取 `accurate_norerank` 是因为**它等于当前实际行为** —— 这样改完既修好了"静默忽略",又保住了历史基线的可比性。

**放弃了什么**:放弃把该端点改成 body 的 HTTP 语义正确性。**为何放弃**:那是独立的需求变更(长文本不该进 URL/日志),应当**新增**一个端点或单独评估,而不是塞进"修 422"这一刀。

**同时必须修的连带项**:只改 `mode` 不改 `name=` 标签,只是把"名不副实"升级成"准确但难懂" —— `locustfile_v2.py:48` 的「accurate 模式」docstring 是作者笔误(它传的值从未生效),要一并更正。
