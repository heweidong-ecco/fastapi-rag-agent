## 背景与约束

**业务方口径（2026-09-20 原话）**：

> 「**不用考虑 agent-eval-gate 占用 docker-compose，那个项目已经做完了，我们正常使用**，
> 不用双 requirements.txt，**这样会混**，最后肯定是用 **docker-compose 一键编排**的，
> **别人 git clone 也是 docker-compose**。你这样做，让整个事情变的很复杂，
> 整个项目阶段性完成，本来就是要**完整明了，简洁的交付**的。」

**我此前做反的地方**（已登记为 §〇）：

| 我做的 | 为什么错 |
|---|---|
| 把交付拆成"**轻量路径（推荐）** + Docker 全量"，还专门写了「**别用 `docker compose up`**」的红线 | ⇒ **读者要自己做判断**，而交付本该是**确定的**。**把一个局部环境限制（本机 8GB 构建不动）升格成了交付形态。** |
| 以「`docker compose up` 会打断 `agent-eval-gate` 评测」为理由禁止重建容器 | **该理由已作废** —— 那个项目做完了 |
| 维护两份 requirements，并在文档里教读者"别弄混" | **"会混"本身就是缺陷**，不是要靠文档补救的事 |

**⚙️ 关键环境事实（已实测）**：本机 **8GB 内存，`docker build` 含 torch 的镜像跑不动**。
⇒ 收敛成 `docker compose up -d` 之后，**本机跑不了交付路径**。
**这不是"因此要提供第二条路径"的理由**，而是**要如实记录的环境限制**（§〇·3）。

## 最终决策 + 理由

**决策 1 = 甲、决策 2 = 甲、决策 3 = 乙。**

### 决策 1（收敛成一条）
业务方口径已直接给出答案。补充理由：**"读者要自己做判断"这件事本身就是交付缺陷** ——
我提供的"两条路径"里，"轻量"那条是我为了**绕开本机硬件限制**而设计的，
它被写成了"推荐"，**等于把环境限制伪装成产品形态**。

### 决策 2（删 + CI 改回）
1. 业务方明说「**不用双 requirements.txt，这样会混**」——**只要文件还在、还得在文档里出现，就还是会混**。
2. 收敛成单一路径后，它在**交付叙事里彻底消失**，只剩 CI 与"本机跑测试"两个内部用途 —— **为这两个用途养一份平行清单，不值**。
3. **代价可测、可回退**：CI 变重，跑一次就知道。真不行再议（**届时走丙方案 pyproject extras，而不是再搞第二个 txt**）。
4. ✅ **动手前核实了安全性**：用**集合运算**（去注释/去版本号/`sort -u` 后 `comm`，比**整行含版本约束**）
   ⇒ 只在 `-test` 里出现的行 = **空**；只在 `requirements.txt` 里的恰为文档声明的 **7 项**。
   ⇒ **它是真子集，切过去不丢任何包。**

### 决策 3（从当前 HEAD 起）
1. 🔴 **决定性理由**：**"把文件搬过去"正是"修了这边漏那边"的高发动作** —— 而这一整轮工作的核心议题就是它。
   **认知资产已经在当前分支上，为什么要搬一次？**
2. **原方案（甲）唯一的优势——"历史干净"——不成立**：本仓合并一直走 **squash**
   （PR #33 → `6198ce1` 一条）⇒ `main` 上最终只有一条干净 commit，**`694d424` 那段永远不会进 main**。
   ⇒ 甲的收益被抵消，却**多背一次搬运风险**。
3. 丙（复用 PR #34）也可行，但 **PR 的标题 / 描述 / 已有评审记录全都锚在"两条路径"上** ⇒ **评审面会变浑**。
