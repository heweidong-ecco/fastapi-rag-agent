## 二 · 机制（为什么"早切通过、晚切失败"）

Starlette 取消流式任务后，**取消会在下一个真实挂起点重投**：

```
客户端断开 ⇒ Starlette 取消这个 task
           ⇒ 取消在**下一个 await** 处落下 ⇒ 抛 CancelledError
           ⇒ 如果那个 await 在 finally 里 ⇒ **finally 的剩余部分整体作废**
```

- **早切**：生成器**还没被推进过** ⇒ `aclose()` 不必真收尾 ⇒ **不挂起** ⇒ 打不断 ⇒ 看起来通过；
- **晚切**：流着流着被打断 ⇒ `aclose()` 要收尾 ⇒ **挂起** ⇒ 取消落在这里 ⇒ **后面全不跑**。

⚠️ **用户点"停止"时必然已经看到字** ⇒ **晚切才是主场景**。

## 三 · 决策

### 决策 1 · 同步收尾**提到任何 `await` 之前**

两条端点的 `finally` 一律按此序：

```
① 计数（track_stream_cancel）           ← 同步
② 日志（logger.info "[cancel] …"）       ← 同步
③ 半截落盘（_persist_interrupted_turn）  ← 同步
④ 关上游流（await stream.aclose()）      ← 唯一 await，放最后
```

⚠️ ③ 能排在里面的**唯一**理由是 `append_chat_history` 是**同步**的（`api/cache.py:39`）——
**不 await ⇒ 二次取消打断不了它**。这一点写进了代码注释，别当成巧合。

### 决策 2 · 关流用 `anyio.CancelScope(shield=True)` **护住**

```python
if stream is not None:
    with anyio.CancelScope(shield=True):
        await stream.aclose()
```

取消作用域会**反复投递**取消 ⇒ 不护住，"关"这个动作**每次都半途而废**。

### 决策 3 · **两条都要**，⛔ 不是二选一

- 只有 shield ⇒ 关流成功，但**关流自己失败**时（连接早断 ⇒ 抛 `RuntimeError`）
  排在它后面的收尾照样全丢；
- 只有顺序 ⇒ **"关"这个动作本身**完不成（上游继续生成、继续烧钱）。

⇒ 两条**各自独立**由测试钉住（见 §判据）。

### 决策 4 · 两条端点**同改**

`/rag/stream_search`（`api/api_v1_rag.py`）与 `/agent/langgraph_chat/stream`
（`api/api_v1_agent.py`）是**同一个形状**，⛔ 别只改一条。
