## 🅰️ 决策一：镜像源 `aliyun` → `tsinghua`

### 发现（**容器内实测**，同包 `numpy==1.26.4` 同条件）

| 镜像 | 速度 |
|---|---|
| `pypi.tuna.tsinghua.edu.cn` | 17.4 MB / 6.0s → **2955 KB/s** |
| `pypi.org`（官方） | 17.4 MB / 7.2s → **2466 KB/s** |
| ~~`mirrors.aliyun.com`~~ | 🔴 **120 秒超时，没下完** |

⚠️ **`aliyun` 是"能连但极慢"**：**索引页 200 OK**，**真包 ~45 KB/s**。
⇒ **这才是「build 要 15–20 分钟」的【主因】** —— 比 torch 那个还大。

### 备选

| 方案 | 评价 |
|---|---|
| **甲 · `tsinghua`（采纳）** | ✅ 国内、稳定、实测最快 |
| 乙 · `pypi.org` 官方 | ✅ 也快（2466 KB/s），⚠️ 国内长期稳定性略逊 |
| 丙 · 不动 | ⛔ **build 根本跑不完** |

**⇒ 甲。** 理由：**它是两个"快"里面更快的那个，且是国内的**。

### ⚠️ 顺带排除的两条（都不是原因，**记下来免得重查**）

- **代理**：三层全是**直连**（`scutil --proxy` 无代理 · Docker `proxyHttpMode=system` 跟随 ⇒ 也是直连 · 容器未设 `HTTP_PROXY`）
- **Docker/网络本身**：`docker pull` 通 · 容器内访问 pypi 通

## 🅱️ 决策二：构建期裁掉 **5 个包**（`sentence-transformers` / `transformers` / `locust` / `ragas` / `datasets`）

### 发现

`requirements.txt` 是 **API 运行时的依赖清单**。而这 5 个：

| 包 | 形态（**实测**） | 谁用它 |
|---|---|---|
| `sentence-transformers` | 库（**懒加载**） | 只被 `reranker.get_reranker()` 用；**连带拉 torch 554.6 MB** |
| `transformers` | 库 | 同上 |
| `locust` | ⭐ **外部 CLI** | **代码里 0 处 import**；靠 `locust -f locustfile_hybrid.py` 跑 |
| `ragas` | 库 | **只被 `evaluate_with_ragas.py` import** |
| `datasets` | 库 | 同上 |

⇒ **压测工具 / 评估库【不属于 API】⇒ 它们出现在这份清单里本身就是分类错了。**

### 备选

| 方案 | 评价 |
|---|---|
| **甲 · 构建期 `grep -vE` 过滤（采纳）** | ✅ 一行；**仓里仍只有一份 `requirements.txt`**（不违反「不用双 requirements」） |
| 乙 · 把 5 个包从 `requirements.txt` **移出** | ⚠️ 更"正确"，但**要动清单结构 + 各建条目** ⇒ 大改动 |
| 丙 · 不裁 | ⛔ 镜像 6.32 GB + build 跑不完 |

### ⚠️ 为什么【不】包一层 `cli.py`（业务方问过）

| 理由 |
|---|
| **`locust` 本来就不需要被 import** ⇒ 包 CLI = 凭空多一层转发 |
| ⭐ **`ragas`/`datasets` 已经有入口了** —— `evaluate_with_ragas.py` **自己就是命令行入口** ⇒ 再加 `cli.py` 是**重复建入口** |
| ✅ **业务方的判断对**：包了 CLI 就要测**参数解析/退出码/帮助文本** ⇒ **测试变多、价值变低** |

**⇒ 结论：问题不在"怎么调用"，在"它们不该在这份清单里"。**

### ✅ 安全验证（**实测**）

- **没有任何非评估/非测试文件 import 这 5 个包**
- **测试一条都不会增加**（没新增入口）

### 结果

| 项 | 改前 | 改后 |
|---|---|---|
| 镜像大小 | 6.32 GB | **1.28 GB** |
| build | 15–20 分钟**不完成** | **~6 分钟完成** |
| pip 解析 | 25 分钟**不收敛** | **5.9 分钟收敛** |

⭐ **而且不需要额外加 `constraints` 文件** —— 裁掉 5 个包后 pip 自己就收敛了。

### ⚠️ 代价（**已知并接受**）

镜像里**跑不了** `mode=accurate` / `rerank_search` / 压测 / RAGAS 评估
—— 而那几件事**本来就跑在开发机上**（`施工单 §4.2 档 1` 也是这么建议的）。
**恢复办法**：把那行换回 `pip install ... -r requirements.txt` 即可。

## 🅲 决策三：删掉属于**另一个项目**的两个旧容器

### 发现

`docker compose up` 报 **容器名冲突**：

```
postgres-rag / redis-rag / rag-api / prometheus / grafana  ← 名字都是【全局的】
    而它们属 project=my-fixed-name
    working_dir=/Users/heweidong/Desktop/ai-learning/…/第1个月的学习FastAPI   ← ⚠️【不是本仓】
```

本仓 compose 声明 `name: fastapi-rag-agent`（2026-09-15 改的）
⇒ **项目名不一致 ⇒ compose 认不出它们是自己的 ⇒ 名字冲突**。
⚠️ 但本仓的**卷名仍写死 `my-fixed-name_*`** ⇒ **两边共用同一个数据卷**。

### 备选

| 方案 | 评价 |
|---|---|
| **甲 · 删容器（**不带 `-v`**）→ 本仓项目名重建（采纳）** | ✅ **名实相符**；**卷不动 ⇒ 数据保住** |
| 乙 · `docker compose -p my-fixed-name up -d` | ✅ 不删东西，⚠️ **项目名仍不符合本仓声明**；且 compose 可能因配置文件路径不同仍要重建 |

### 数据安全性（**先存证、再动手、后核对**）

```
删容器【前】存证: documents=77  api_keys=1  token_usage_logs=475  cost_records=475
删容器【后】核对: documents=77  api_keys=1  token_usage_logs=485  cost_records=485
                  ↑ 前两项【一行没少】；后两项 +10 = 启动时 warmup_cache 预热 10 条 embedding（预期内）
```

⇒ **业务方裁「甲」，并要求先说明卷里是什么**（见 §"卷里的数据是什么"）。

### 卷里的数据是什么（**业务方问的**）

| 表 | 行数 | 内容 |
|---|---|---|
| **`documents`** | **77** | ⭐ **RAG 知识库**（Python/FastAPI/Docker…），含 17 行 `eval_dataset.json#*` + 8 行 `eval-gap-fill-*` |
| `api_keys` | 1 | 管理员 Key（可被 `ensure_admin_exists()` 重建） |
| `token_usage_logs` / `cost_records` | 475 | 用量与成本历史 |

⇒ **`documents` 77 行【必须保留】** —— `施工单 §2.6` 的判据④⑤全靠它。
✅ **而且【不需要搬家】**：本仓 compose 的卷名 === 实际卷名 ⇒ up 起来就是同一个卷。
