# DEC-087 · 启动自检必须问【和认证侧同一个问题】（⛔ 不是"数了几行"）

| 项 | 内容 |

## 一 · 缺陷（真库 + 真事务 + `ROLLBACK` 复现过）

`ensure_admin_exists`（启动自检）数的是**行数**：

```sql
SELECT COUNT(*) FROM api_keys WHERE user_name = 'admin'
```

而认证侧 `verify_api_key` 要的是 `COALESCE(is_active, 1) = 1` **且**未过期。
⇒ **两个门量的不是同一件事。**

复现（本机真库，跑完 `ROLLBACK`，零残留）：

| 门 | 那句 SQL | 撤销后打出来的数 |
|---|---|---|
| ① 启动自检（`api/auth.py:46`，改动前） | `... WHERE user_name = 'admin'` | **1** ⇒ 日志「管理员账户已存在，跳过自动创建」 |
| ② 认证（`api/auth.py:104`） | `... AND COALESCE(is_active, 1) = 1` | **0** ⇒ 没有一把 key 能认证 |

**⇒ admin 锁死，而日志说一切正常。**

### 🔴 近失不在假设里

2026-10-06 本机**真跑过** `scripts/issue_api_key.py admin --revoke` ——
它**按用户名撤**，撤的是该用户名下的**全部行**（连同 `id=2` 那把 2026-09-10 建的主 key）。
当时靠**手工** `UPDATE api_keys SET is_active = 1 WHERE id = 2;` 才复原。

**没有那一下，重启后 admin 就锁死，而且日志里没有一行提示。**

（📌 附带一条口径：`--revoke` 撤的是**该用户名下的全部 key**，⛔ 不是"我刚发的那把" ⇒
在共享用户名（如 `admin`）上验往返**先数该用户名下有几行**。）

## 二 · 备选与取舍

| 方案 | 做法 | 结果 |
|---|---|---|
| **A（选它）** | 自检改量**能用**的 admin key；「0 行」与「有行但全不可用」**分开**：前者照旧自动建，后者**响亮告警**、⛔ 不自动建 | **撤销保持生效**，决定权留给人 |
| **B（⛔ 否）** | 自检只加过滤条件 | admin 全被撤后，**每次重启都自动补发一把新 key 并把明文打进日志** ⇒ 把操作员的「撤销」**静默还原** |
| **C（⛔ 否）** | 只把日志措辞改准，不改判据 | 锁死照旧，只是日志不再骗人 —— **治不了病** |

**选 A 的理由**：「撤销」是**操作员做的决定**，⛔ 不该被一次重启翻掉；
而自动补发还会**把新 key 的明文打进日志** —— 正是 2026-10-06 花力气清掉的那类残渣。

**反悔成本**：**低**。A 只改「有行但全不可用」这一支；想退回 B 改一处 `if` 即可（但先想清楚上面那条）。
「0 行 ⇒ 自动建」与「有可用的 ⇒ 静默跳过」两条**一个字没动**，且各有一条守卫用例钉住。

## 三 · 改了什么（`api/auth.py`）

1. **新常量 `ACTIVE_PREDICATE`**（`COALESCE(is_active, 1) = 1`）—— `is_active` 那一半的
   **唯一口径**，`verify_api_key` 与 `ensure_admin_exists` **共用**。
   📌 这条缺陷的**成因就是两处各写了一遍** ⇒ 结构上收成一处，⛔ 不靠"记得同步"
   （本仓立场：**只有文字就漏，结构才执行**）。
2. **新函数 `_is_expired(expires_at)`** —— 过期那半的唯一口径，同样两处共用。
   ⚠️ 判在 **Python 侧**，⛔ 不在 SQL 里写 `expires_at > NOW()`：本仓 `expires_at` 存的是
   **naive 本地时间**（`create_user_api_key` 用 `datetime.now()` 写进去的），而库里的 `NOW()`
   是 `timestamptz`（容器按 UTC）⇒ 在 SQL 里比会**差 8 小时** —— 正是本仓踩过的
   「两套时区混进同一个量」那一族。
3. **`ensure_admin_exists` 分三支**：

   | # | 库里的状态 | 行为 |
   |---|---|---|
   | 1 | 名下有**能用**的 key | `info` 跳过 —— **既有行为，一个字没改** |
   | 2 | 名下**一行都没有** | 自动建一把 · 打印明文（仅此一次）—— **既有行为，一个字没改** |
   | 3 | **有行，但没有一行能用** | 🔴 **新增**：`error` 响亮告警 + 给出可照做的命令；⛔ **不自动补发** |

   ⚠️ 告警里那行命令是 `python scripts/issue_api_key.py admin --days 3650` ——
   参数形状**照 `scripts/issue_api_key.py` 的 `argparse` 核过**（`user_name` 是**位置参数**，
   ⛔ 不是 `--user admin`）。**没核就打印，等于给了一句跑不动的命令。**
4. `verify_api_key` 改用上面两个口径 —— ⚠️ **它产出的 SQL 字符串逐字符不变**
   （`ACTIVE_PREDICATE` 就是原字面量），所以 `api/test_auth_api_key_active.py` 那 5 条照绿。

## 四 · 守卫（`api/test_auth_ensure_admin_exists.py` · 8 条）

| 用例 | 钉什么 |
|---|---|
| `test_撤销后仅剩死行时不算管理员已存在` | 🔴 **缺陷本体**。实测：用例先写、跑一遍 ⇒ **5 条红**，之后才动产品代码 |
| `test_仅剩已过期的admin行时同样告警` | 「过期」同样等于「不可用」，与认证侧**同一判据** |
| `test_一行都没有时照旧自动创建` | 🔴 **取反的另一半**：修复⛔ **不许改坏首次启动** |
| `test_有可用的admin时照旧静默跳过` | 正常情形行为**一个字不能变**（⛔ 别把"正常"也喊成 `error`） |
| `test_数可用那半句真的过滤了_is_active` | 抓**产品产出的真 SQL** 丢进真 `sqlite3` 原地跑 —— ⛔ **不是测试照抄一份谓词**（照抄只能测"我抄对没有"） |
| `test_把过滤拆掉这条尺子必须变红` | **取反检验**：拆掉谓词，撤销的行必须**冒出来** ⇒ 证明那半句真在干活 |
| `test_两条路径的_is_active_口径是同一句` | 🔴 **防复发的结构**：谁把两处改回各写一遍（或丢掉 `COALESCE`），这条红 |
| `test_自检在建表之后调用` | `is_active` 在**老库**里靠 `create_table()` 那句 `ALTER` 补（`DEC-086`）⇒ 启动顺序反了就是 `UndefinedColumn`，**应用直接起不来** |
