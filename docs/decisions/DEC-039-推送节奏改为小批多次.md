## 🅱️ 决策二：那批已攒下的 commit 怎么推

**现状**：`git rev-list --count origin/main..HEAD` = **25**（2026-09-30 实测；⚠️ **这个数会变，别引用**）。

### 处置

**不一次性推**，而是**按批次推到分支**：分若干次，每次推一段（**fast-forward**，不重写历史），

> **小批多次推的是【推送动作】，不是【提交内容】** —— 两者别混。

## 🅲 边界补充：**推送分次 ≠ 提交分次**（**2026-09-30 当天补**）

> ⚠️ **本条是本决策当天踩出来的** —— **不是提前想到的。**

**发生了什么**：本决策落地当天，AI **把"推送给分成多次"错误地延伸成了
「每个文档一个 commit」** —— 改完一份文档就 `git add` + `git commit` 一次。

**业务方当场指出**：

> 「**git add 和 git commit 是不是太频繁了，一个文档没必要一个 commit**」

**⇒ 边界（写死，防再犯）**：

| 对象 | 怎么攒 |
|---|---|
| **推送（`git push`）** | 🔴 **小批多次** —— 本决策改的就是它 |
| **提交（`git commit`）** | ✅ **仍然攒着** —— **一个 PR 的活儿，提交可以攒着一次建**<br>⛔ **不必"一个文档一个 commit"** |

**为什么两者不该混**：**改的是「推上去的形态」（对风控可见），不是「本地的粒度」（只有自己看）。**
本决策的动机（**批处理形态引风控**）**只在 push 这一层成立** —— 本地 commit 攒多少，外面看不见。
