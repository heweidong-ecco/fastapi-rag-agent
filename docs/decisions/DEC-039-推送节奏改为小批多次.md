## 🅲 边界补充：**推送分次 ≠ 提交分次**（**2026-09-30 当天补**）

> ⚠️ **本条是本决策当天踩出来的** —— **不是提前想到的。**

**发生了什么**：本决策落地当天，AI **把"推送给分成多次"错误地延伸成了
「每个文档一个 commit」** —— 改完一份文档就 `git add` + `git commit` 一次。

**业务方当场指出**：

> 「**git add 和 git commit 是不是太频繁了，一个文档没必要一个 commit**」

**⇒ 边界（写死，防再犯）**：

| 对象 | 怎么攒 |
|---|---|
| **推送（`git push`）** | 🔴 **小批多次** —— 本决策改的就是它 |
| **提交（`git commit`）** | ✅ **仍然攒着** —— **一个 PR 的活儿，提交可以攒着一次建**<br>⛔ **不必"一个文档一个 commit"** |

**为什么两者不该混**：**改的是「推上去的形态」（对风控可见），不是「本地的粒度」（只有自己看）。**
本决策的动机（**批处理形态引风控**）**只在 push 这一层成立** —— 本地 commit 攒多少，外面看不见。

> ### 🔴 追加（同日 · **同一天栽了第二次**）
>
> **上面那条纪律写下来的【同一天】，AI 又犯了第二次**：
> 在 **B1–B14 还没裁完**（还剩 B7/B9/B14）的时候就 commit 了。
> **业务方当场拦住**：「**不是还没有处理完吗，等下一起 commit**」。
>
> ⇒ **原措辞（"提交可以攒着一次建"）不够狠** —— 它读起来像"**也可以不攒**"。
> **已改成禁止式**（三处同步：`docs/规范/开发规范.md` · 本仓 `CLAUDE.md` · `~/.claude/CLAUDE.md`）：
>
> > 🔴 **❌ 一件事没处理完，不 commit。**
> > **判据：「我这条 commit 发出去，接手人会不会以为这件事结束了？」—— 会 ⇒ 还不到时候。**
>
> ⚠️ **"处理完"由【业务方要的那件事】界定，不是由「我手上告一段落」界定。**

## 🅳 边界补充二：**PR 的 commit 数 ≠ 对 GitHub 的操作次数**（**2026-10-01 补**）

**起因**：业务方 2026-10-01 问 ——

> 「PR #60 这个 pr 怎么有 40 个 commit，这样提交 commit 是不是会被 GitHub 判定成批处理」

**⇒ 这个问题里藏着一次口径滑动**：**把"PR 里装了多少 commit"当成了"我们对 GitHub 做了多少次操作"。**
**两者不是一回事** —— 本决策的动机（**批处理形态引风控**）**只在后者这一层可能成立**。

### 三层要分开说（⛔ 不许糊成一句）

| # | 层 | 内容 |
|---|---|---|
| **①** | ✅ **事实**（实测，可打印） | PR #60 = **40 个 commit**、**跨 5 天提交**、**只有 7 次 push**、**0 未推** —— 见下表 |
| **②** | 🟡 **判断**（我们的读法，**未被证实**） | **风控看到的是【推送/请求】这一层，不是 PR 里的 commit 数** |
| **③** | 🔴 **未证实**（⛔ 不许当规则用） | **GitHub 到底命中哪一条** —— 见本文档「决策事项」：**它没说** |

### ① 实测（2026-10-01）

```bash
git rev-list --count origin/main..HEAD                  # 40
git log origin/main..HEAD --pretty=%ad --date=short | sort | uniq -c
git rev-list --count @{u}..HEAD                         # 0（没有未推的）
git diff --shortstat origin/main..HEAD                  # 101 files changed, 14141 insertions(+), 948 deletions(-)
```

> ⚠️ **别用 `git rev-list --count --pushed`** —— **没有这个 flag**（会打 usage）。
> 📌 本条是**写这份文档时当场试出来的**：我先按记忆写了一条**跑不通的命令**进去，
> 跑了一遍才发现 —— **这正是本仓 `a257de3` 那次 CI 红的同型动作**（**凭记忆写，没跑**）。

| 项 | 值 |
|---|---|
| **① PR #60 里的 commit 数** | **40** |
| 按天分布（**提交**时间） | 09-24 **3** · 09-25 **3** · 09-29 **17** · 09-30 **15** · 10-01 **2** |
| **② 实际 `git push` 次数** | 🔴 **7 次 —— 而且全部落在 09-30（×5）与 10-01（×2）**<br>见下方命令；**Git 自己不记推送次数**，这 7 次是**从 GitHub 事件 API 观测的** |
| 改动量 | `+14141 / −948` · **101 个文件** |

**② 怎么测的**（**GitHub 的 `PushEvent`**，不是猜的）：

```bash
for p in 1 2 3 4; do
  gh api "repos/heweidong-ecco/fastapi-rag-agent/events?per_page=100&page=$p" \
    --jq '.[]|select(.type=="PushEvent")|"\(.created_at)\t\(.payload.ref)"'
done | sort -u | grep 'docs/project-side-recon'
# 7 行：09-30 ×5 · 10-01 ×2
```

> ⚠️ **事件 API 有保留窗口（约 90 天 / 300 条）** ⇒ 严格说这是「**窗口内观测到的 7 次**」。
> **本文档用它的当天**（2026-10-01）**该分支才出生 7 天**，远在窗口内 ⇒ **可信**。
> 📌 **但换个人几个月后再跑，可能测不到** —— **所以命令留在这里，数别引用。**

### ② 判断：真正像"批处理"的是 **push**，不是 **PR**

**PR 是【内容的容器】** —— 它里面装 1 个 commit 还是 40 个，**在创建 PR 之前就已经定了**，
**GitHub 不会因为一个 PR 装得多就多记你几次操作**。

**⚠️ 但有一处确实像批处理，而且它【已经发生过】—— 实测比预想更极端**：

> **09-24 ～ 09-29 攒下的 23 个 commit（3+3+17），在 09-30 一天之内推完**（那天的 5 次 push 里）。
> ⇒ **"批"不在 PR 里，在 push 里** —— **40 个 commit 只对应 7 次 push，其中 5 次挤在同一天。**
>
> ⚠️ **这个形态发生在**：**封号之后**（09-24 封 → 09-29 18:11 UTC 解）**的第 2 天**，
> 且 **早于本决策落地**（本决策 09-30 当天订）。
> ⇒ **本决策要打散的就是它，方向对上了。**

### 推论：**拆 PR ≠ 降低风控面**

⇒ **PR 该多大就多大** —— **PR 的大小、标题、描述都不在"操作次数"这个面上**。
⛔ **别为了风控去把 PR 拆小** —— 那不会改变推了几次，只会让历史更难读。

**真正可调的旋钮只有两个**：

| 旋钮 | 现状 |
|---|---|
| **`git push`** | 🔴 **本决策管的就是它** —— 按段推 |
| **`gh pr merge` 等写请求** | ⚠️ **1 次 = 1 次 API 调用**，但 **⛔ 无任何证据**说明它构成风险 ⇒ **别据此发明规则** |

### ⚠️ 为什么要把「未证实」单列（**本仓刚栽过**）

**2026-10-01 本仓 CI 红了一次**（commit `a257de3`），原因就是 ——
**我把代码注释里的一句"因为所以"当成了规律，还写成测试** ⇒ **CI 直接红**。

⇒ **本条刻意做同一件事的反面**：
**②是"我们的最佳读法"，③是"GitHub 没说"** —— **两栏分开写，⛔ 不许把 ② 升格成 ③ 来用。**
**判据**：**凡我说"风控会/不会……"，先问一句「这是 GitHub 说的，还是我推的？」** —— **推的，就得标明。**

## 🅴 边界补充三：**PR 颗粒度 = 「一个完整任务一个」**（**2026-10-02 业务方裁定**）

> 「**今天你开了几个PR 不要频繁开，一个完整任务一个PR，不要频繁使用GitHub api**」

### ① 实测（可打印 · 当天跑过的就是这条）

```bash
gh pr list --state all --limit 20 --json number,state,createdAt,mergedAt \
  --jq '.[] | [.number, .state, (.createdAt[0:16]), (.mergedAt // "-" | .[0:16])] | @tsv'
```

⇒ **2026-10-01 一天建了 4 个**：`#61` 13:24 · `#62` 14:07 · `#63` 15:23 · `#64` 15:39
（🔴 **两个多小时里 4 个** —— 这就是业务方说的「频繁」）；

⚠️ 这 4 个是**按「小节」开的**（`Task 0/1` 一个、`Task 2+3` 一个、加上积压的 `#60`/`#64`），
**不是按「业务方要的那件事」开的** —— 与 §🅲 那条 commit 判据**用的是两套尺度**。

### ② 裁定

| 项 | 定 |
|---|---|
| **颗粒度** | **一个【完整任务】= 一个 PR** |
| **「完整任务」怎么界定** | ⭐ **沿用 §🅲 那条判据，⛔ 不另立标准** —— 由**业务方要的那件事**界定，不是由「我手上告一段落」界定 |
| **同一任务的多条 commit** | ✅ **走同一个 PR**（`#65` 即此形态：`Task 4` + 顺带修 `ci-local`，**2 条 commit / 1 个 PR**）|
| **与「小批多次」的关系** | 🔴 **两根轴，⛔ 别混** —— **push 可以碎，PR 不许碎**（§🅳 已定「PR 是内容的容器」，这里只是接上它）|
| **API 调用** | ⛔ **别频繁** —— 见 ④ |

### ③ ⚠️ 与 §🅳 的关系：**不同轴，⛔ 别互相当理由**

- **§🅳 定的是「就风控而言，拆 PR 有没有用」** ⇒ 答：**没证据有用**（「拆 PR ≠ 降低风控面」）。**这一条仍然有效。**
- **§🅴 定的是「业务方要不要这样干」** —— **它是裁定，不是从风控推出来的。**
- 🔴 **判据**：**凡把 §🅴 说成「少开 PR 是为了防风控」的，就是在做 §🅳 明文禁止的事**
  （§🅳 原话：**⛔ 无任何证据说明它构成风险 ⇒ 别据此发明规则**）。
  ⇒ 本条的正当理由是**业务方定的颗粒度** + **④ 的真实成本**，**不含风控**。

### ④ 同期被点名、且**确实可调**的一个旋钮：**API 调用次数**

「**不要频繁使用 GitHub api**」—— 我在这上面犯过的是三种**纯浪费**：

| 浪费 | 做法 |
|---|---|
| ❌ `gh pr checks` 写成**轮询循环** | ✅ **等一会儿看一次**；不行就去看那次 run 的结论 |
| ❌ 同一个 PR 用 `gh pr view` **连着敲三四遍**（元信息 / body 行数 / 抽查各一次） | ✅ `--json` **一次把字段列齐**；body 抽查能本地就本地 |
| ❌ 能用本地 `git` 答的也去问 API | ✅ **先本地**：`git log --format='%h parents=%p'` · `git rev-parse` · `grep` / `wc` |

⚠️ **这一条同样不是风控结论** —— 理由就是**成本**（1 次调用 = 1 次调用），
与 §🅳 那句「1 次 = 1 次 API 调用，但 ⛔ 无证据构成风险」**不冲突**：**它说的是"不构成风险"，不是"不用省"。**

### 反悔成本

| 要改哪条 | 代价 | 判据（改完怎么验） |
|---|---|---|
| 回到「按小节开 PR」 | **低**（纯流程，无代码影响） | 但要重新接受**号段切碎、后来者看不出哪几条 commit 是同一件事** |
| 改成「多个任务共用一个 PR」 | **中** —— 一个 PR 里混两件事，**回滚时拆不开** | `gh pr view <n> --json commits` ⇒ commit 主题应能**归到同一件事** |
