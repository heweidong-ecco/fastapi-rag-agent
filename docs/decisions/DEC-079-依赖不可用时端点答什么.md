# DEC-079 · 依赖不可用时端点答什么：503，以及 fail-open / fail-closed 的分工

| 项 | 内容 |
|---|---|
| **状态** | ✅ **已实施（2026-10-05）** |
| **触发** | 🅗 **`N9`** —— 「`auth.verify_api_key` 的 `get_db()` 没有 `try` ⇒ 库一抖就回 **500 而不是 401**」<br>⚠️ **`N9` 那句话里「500 而不是 401」两个都不是答案** —— 见 §二 |
| **类型** | 接口选型（错误应答形状）+ 可靠性取向（fail-open / fail-closed） |
| **落点** | `api/auth.py`（`verify_api_key`）· `api/main.py`（`resolve_quota_identity` 新增 · `RateLimitMiddleware.dispatch` · `QuotaMiddleware.dispatch`）· `api/token_config.py` + `api/rate_limiter.py`（同批的 `S7`/`S8`，取向同源） |
| **判据** | `api/test_auth_db_unavailable.py`（**22 条**）· `api/test_rate_limiter_resilience.py`（13 条）· 全量 **654 passed** · 变异自证 **17/17** |

---

## 一 · 要解决的问题

`verify_api_key` 是裸的 `with get_db() as conn:` —— **前后没有 `try`**。

⇒ 库连不上（容器没起、池耗尽、网络抖动）时，`psycopg2.OperationalError` 一路冒到
**中间件里** —— 而 `main.py` 自己写着：

> 「注意：**中间件中抛出的异常不会被 `@app.exception_handler(AppException)` 捕获**
> （会落到 `ServerErrorMiddleware` 的通用 Exception 处理器，返回 500）」

⇒ 调用方拿到一个 **非结构化的 500**，与"这把 key 到底行不行"**没有任何关系**。

---

## 二 · 🔴 `N9` 原文的「500 而不是 401」—— **两个都不是答案**

| 读法 | 为什么不行 |
|---|---|
| **500**（现状） | 非结构化，且把一次**可恢复的抖动**说成"服务器内部错误"。调用方**不知道能不能重试** |
| **401**（`N9` 字面想要的那个） | 🔴 **更糟**：库连不上时我们**并不知道**那把 key 是真是假 ⇒ 报 401 等于**替用户断言「你的 key 坏了」** ⇒ 他会去换一把**没问题的** key，然后照样连不上，**且永远查不到原因** |

### ✅ 正确答案 = **503 `SERVICE_UNAVAILABLE`**

**这不是新口径，是照抄 WS 侧已经裁过的**（`api/test_ws_auth.py` / `DEC-075` / `docs/specs/deps.md`）：

| 情形 | WS 码 | HTTP 码 | 该做什么 |
|---|---|---|---|
| **凭据不行** | `1008` | **401** | **换 key** |
| **认证服务不行** | `1011` | **503** | **重试，⛔ 别换 key** |

⚠️ `ErrorCode.SERVICE_UNAVAILABLE` 与 `ERROR_CODE_TO_HTTP_STATUS[..] = 503`
**`api/exceptions.py` 里早就有，此前从未被用过** —— 这次是它的第一次投用。

📌 **判据**：`test_库不可用时抛服务不可用而不是返回None` 明写了「⛔ 不许返回 `None`」——
因为返回 `None` 会让调用方（`deps.get_current_user`）报 **401**，正好落进上表右边那一格。

---

## 三 · 四个落点，**两种取向**（⛔ 别"统一"）

同一个失败在两处出现，处置**故意相反**：

| 层 | 落点 | 取向 | 具体 |
|---|---|---|---|
| **安全边界** | `deps.get_current_user` | **fail-closed** | **拦住**，但说 **503**（"我这边不行"），⛔ 不是 401、也⛔ 不是 500 |
| **保护措施** | `resolve_rate_limit_identity` | **fail-open** | 返回 **`None`** ⇒ 本请求**不参与用户级限流**（＋ ERROR 日志） |
| **成本控制** | `resolve_quota_identity`（`QuotaMiddleware`） | **fail-open** | 返回 `None` ⇒ 走**该中间件本来就有**的"识别不了 ⇒ 原样放行"出口 |
| **限流阀本身** | `rate_limiter`（同批 `S8`） | **fail-open** | Redis 不通 ⇒ **放行** + ERROR 日志（限流是**保护**，不是**边界**） |

**判据不是"哪个安全选哪个"，是「放错了会怎样」**：
* 安全边界放错 = **匿名进门** ⇒ 必须 fail-closed
* 保护 / 成本控制放错 = **限流与配额短暂失效** ⇒ 而 fail-closed 的代价是**全站 500**

---

## 四 · 🔴 为什么限流那边是「不参与限流」，⛔ **不是「降级到匿名桶」**

`anonymous` 是**一个** 20 容量 / 3 每秒的桶。库一挂，**所有带 key 的人都挤进同一个桶**
⇒ **大面积假 429**。

⚠️ 那正是 `docs/specs/deps.md` 里 1008/1011 那条禁止的 **归错因** 的限流版：
**把"我这边的抖动"说成"你发太快了"**。

⇒ 所以 `resolve_rate_limit_identity` 的返回值**多了一个 `None`**：

| 值 | 含义 | 中间件据此做什么 |
|---|---|---|
| `"anonymous"` | **判了，就是匿名**（用户侧的问题） | 落匿名桶，照常限流 |
| `None` | **判不了**（我这边的问题） | **本次请求不参与用户级限流** |

⚠️ **全局限流那一层仍然照常生效** —— 它**不依赖身份**，⛔ 没有一起被跳过。

---

## 五 · 捕获范围**必须按类型**（⛔ 不是 `except Exception`）

三处新的 `except` 分别写死 `psycopg2.Error` / `AppException` / `redis.RedisError`。

**理由有两条，第二条才是本仓特有的**：

1. 宽捕获会把**代码 bug** 伪装成"依赖挂了" ⇒ 真 bug 永远查不出来（本仓的"静默降级比报错更危险"）。
2. 🔴 **它会把一道已有的门静默关掉**：`api/test_rate_limit_identity.py` 的 `_no_db` fixture
   靠**抛 `AssertionError`** 抓「谁在测试里碰了库」。写成 `except Exception`，
   那道守卫就**被吞进 except 里** ⇒ **门还在，但永远不响**。

📌 守卫：`test_非数据库异常必须照样冒泡` · `test_限流分桶遇到别的异常不许吞` ·
`test_额度中间件遇到别的异常不许吞` · `test_只捕获redis错误_别的异常要照样冒泡`（四条同型）。

---

## 六 · 接线也有判据（⛔ 别只测函数）

「函数返回 `None`」**不等于**「中间件照 `None` 办了事」——
把 `if user_name is None: return await call_next(request)` 那两行删掉，
函数级的用例**照样全绿**。

⇒ `api/test_auth_db_unavailable.py` 里另有一组**中间件级**用例
（直接调 `dispatch`，`call_next` 用替身），判据是「**碰了不该碰的东西就炸**」：
把 `user_limiter` / `get_token_budget_info` 换成**一碰就抛** ⇒ 走错路立刻红。

⚠️ 同组里必配**反向守卫**（`身份正常时用户桶照常生效` / `照常查预算`）——
没有它们，把中间件改成"无脑放行"也能让正向用例全绿。
