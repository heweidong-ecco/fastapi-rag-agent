### ① 放哪 —— 🔴 **不是一个问题，是三个**

| 层 | 放哪 | 关键理由 |
|---|---|---|
| **源**（乙产的 `.md`） | 本仓 **`testdata/demo-corpus/`** | 与既有 `isolation-seed/` **同族**；**正好填上** §六 判据里的 `<语料目录>` 占位 |
| **产物**（烤好的 `.db`） | **Studio 仓**（⛔ **不进本仓**） | 进镜像才叫"预置"；且 `.gitignore` 有 `*.db` |
| **运行时数据** | 容器 **`/mnt/workspace`** | 平台唯一持久目录 |

🔴 **拆成三层就是解开 `DEC-098` 占位 #1 的钥匙** —— 原问题「`demo/` 已 gitignore ⇒ 语料放不进那里」
是**把三件事当成一件问**了。

### ② 什么格式 —— **文件名即契约**

`<类别字母>-<序号>-<标题>.md`（A 产品 / B 流程 / C FAQ / D 报告 / E 负样本块）
· **灌库脚本按字母显式传 `doc_type`** · **⛔ 不引 front-matter**（要 `PyYAML` = 加依赖）。

### ③ 怎么进镜像 —— **本仓出源，Studio 仓收产物**

`本仓 .md` → **甲本机重烤** → `.db` → **Studio 仓** → 平台构建镜像。
🔴 **⛔ 绝不在容器构建时烤**（要 key = 红线 · 烧免费额度 · 构建时间不可控 ⇒ 构建失败 = 部署失败）。

## 四 · 🔴 **LFS：本 demo 用不上**（2026-10-08 定 · 业务方裁「**不做探针**」）

**业务方原话**：「**我们的数据集会很多吗？量不大，不要再做探针，还是一定需要做**」。

**量级估算**：20–40 篇 × 3–6 万字 ⇒ 约 **60–200 块** ⇒ 向量 ≈ **~1.2 MB**
⇒ **烤好的 `.db` 合计约 1–3 MB**。

🟢 **离平台 LFS 门槛（**>100 MB 才必须**）差两个数量级** ⇒ **LFS 与本 demo 无关**：
⛔ **不做 LFS 探针**、⛔ **不装 `git-lfs`**。

🔴 **留一条判据**（将来量大了它自己会响）：
```bash
du -sh <烤好的 .db>      # 超过 100 MB ⇒ 必须 `brew install git-lfs && git lfs install`
```

> 📌 **一条实测事实（本机 2026-10-08）—— 当【已知】留着，⛔ 不是待办**：
> Studio 仓自带 `.gitattributes` 把 `*.db*` 映射到 LFS；而**本机没装 git-lfs** 时，
> `git add x.db` **退出码 0（成功）**，存进去的却是 **`SQLite format 3` 原始字节**（⛔ 不是 LFS 指针）。
> ⇒ **「`.gitattributes` 写了 `filter=lfs`」≠「LFS 生效」，而且它不报错。**
> ⚠️ **在本 demo 的量级下【无后果】**（1–3 MB 走不走 LFS 都能推）⇒ 所以它**不是**待办。
> （方法：`git check-attr filter -- x.db` · `git cat-file -p "$(git rev-parse :x.db)" | head -1`。）
