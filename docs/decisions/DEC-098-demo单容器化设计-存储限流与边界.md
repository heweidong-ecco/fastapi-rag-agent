## 一 · 要裁的是什么

### 1.1 目标换了，架构就得跟着换

🎯 目标（业务方 2026-10-07）：「把它变成一个**能分享的链接**」—— 部署到**魔搭创空间**。

而魔搭创空间是**托管平台**，它的约束是**平台强加的**（完整清单 ⇒ `docs/说明/魔搭创空间-部署与平台约束.md`）：

| 平台约束 | 直接打在本仓的哪里 |
|---|---|
| **一个 Studio = 一个容器** | 本仓 `docker-compose.yml` 是**5 容器**（api · pg · redis · prometheus · grafana）⇒ ⛔ **不能直接搬** |
| 端口只能 `0.0.0.0:7860` | 与本仓 `8000` 不同 |
| **不得使用 `Authorization` 头** | 🔴 本仓 JWT **就走 `Authorization`** ⇒ demo 版必须改道 |
| **重启即丢数据** | 本仓一切"写进去的东西"都要重新想落在哪 |
| 免费档 **2 vCPU / 8 GiB / `SwapTotal=0`** | ⚠️ 本仓 `docker-compose` 是按**本机 8 GB 但多容器**写的；这里是**一个容器吃整台**，且 **OOM = 直接 kill** |

### 1.2 本仓现有的三个"必须回答"

| # | 现状（可打印 ⇒ §四 4.1） | 在单容器 + 重启丢数据的平台上，它成了问题 |
|---|---|---|
| 1 | **存储** = PostgreSQL + pgvector（`vector(1536)` + ivfflat），SQL 是**裸 PG 方言**（`%s::vector` · `<=>` · `CURRENT_DATE`） | 单容器塞不下"另起一个 pg 进程"这条路线（见 §三 方案 C 的代价） |
| 2 | **限流** = 令牌桶在 **Redis**（`rate_limiter.py`）· 日额度记账在 **PG**（`token_tracker.py`） | 🔴 **限流的两条腿，各自挂在"我们打算拆掉的存储"上** |
| 3 | **语料** = 现灌现算（`/rag/upload_document`） | 重启丢数据 ⇒ 访客一进来**库是空的**，demo 看起来"没东西" |

### 1.3 本轮查出的两条**本仓**缺陷（🔴 与上面三条独立，但必须一起裁）

| # | 现象 | 证据（可打印） |
|---|---|---|
| **A** | `upload_document` **没有任何入库侧上限** —— 只有**文件类型**白名单，没有大小 / token / chunk 数 / 每人额度 / 并发 | `grep -c 'allowed_extensions' api/api_v1_rag.py` ⇒ 有；`grep -c 'MAX.*SIZE\|max_size\|content_length' api/api_v1_rag.py` ⇒ **0** |
| **B** | 同一个函数**把整个文件一次性读进内存**，且 `os.unlink` 在**函数末尾** | `api/api_v1_rag.py:304` `tmp.write(await file.read())` · `:328` `os.unlink(tmp_path)` |

🔴 **A + B 合起来的失效模式**：容器 **8 GiB · `SwapTotal=0`** ⇒ 内存见底时**没有 swap 缓冲，直接 kill**。
⇒ 一次超大上传**不需要恶意、不需要并发**就可能把整个 demo 打死。⚠️ **具体多大会触发，本轮【未实测】** ⇒ 列进 §五 占位。

### 1 · 容器里跑什么

```
单容器（0.0.0.0:7860）
├── uvicorn + FastAPI      ← 现有 api/，几乎不动
├── redis-server           ← 现有，原样保留（限流的桶 + 缓存都在这）
└── SQLite 文件            ← 新增，替掉 PG
```

**为什么 Redis 留着**（这是本节最容易被"单容器就该什么都塞一个"推翻的一条）：
🔴 **限流的令牌桶就在 Redis 里**（`rate_limiter.py`，Lua 脚本 + Redis Hash）。
丢掉它 = **要重写"必须做"的那套限流**。而 `redis:7-alpine` 空闲占用是**十几 MB 量级**。
⇒ **保 Redis = 改动面不含限流那三块；丢 Redis = 要动 `rate_limiter.py` · `cache.py` · `query_rewriter.py`，且改的正是最在意的那块。**

> ⚠️ **2026-10-07 更正**：本行原文写的是「**保 Redis = 只改 2 处；丢 Redis = 改 5 处**」——
> **那两个数都取自"改动面就 `db.py` + `token_tracker.py`"这个前提，而该前提已被实测推翻**
> （见 §二·2 下面的复核块 ⇒ **实测至少 6 个文件**）。
> ✅ **两个数都作废，改成"差集"这个说法** ——
> ⭐ **A 与 B 的差集⛔ 没变，仍是那 3 个文件**（`rate_limiter.py` · `cache.py` · `query_rewriter.py`）

#### 2.1 🔴 换 embedding 模型 = **"模型名 + 维度 + 表定义"三件套**

| | `text-embedding-v2`（现状） | `qwen3.7-text-embedding-flash`（新） |
|---|---|---|
| 维度 | **1536** | **1024**（官方资料：「支持 256/512/768/1024 维，**默认为 1024**」） |
| 价格 | 0.7 元/百万 token | **0.125 元/百万 token**（**便宜 5.6 倍**） |

⇒ 只把模型名变可配 ⇒ **维度对不上**：

* 维度不同 ⇒ pgvector（`api/db.py:69` `embedding vector(1536)`）**会直接报错**
  （`expected 1536 dimensions, not 1024`）—— **这是好的失败，至少它响**；
* 🔴 **真正危险的是"维度恰好相同"的情况** —— **不报任何错**，但老向量与新查询向量**不同源** ⇒ **检索结果全是垃圾**。
  **这是本仓最怕的那类失败：静默错配。**

⇒ **决策**：**模型名与维度一起管**，且**启动时自检** —— 拿模型名**实测一次维度**，
与表定义对不上就**响亮地断**（⛔ 不是警告、不是回落）。

⚠️ **连带两条要一起登记**（§五 占位 5）：
`token_config.py` 的 `MODEL_PRICING` 要加 `qwen3.7-text-embedding-flash`
（不加就落兜底价 `0.003`，**高报 24 倍**）；且仓里有一条守卫测试
`test_models_actually_in_use_have_explicit_pricing` **会因此转红** —— **那是它在干活，⛔ 别绕过它。**

理由是**本仓自己的立场**：demo 想证明的是「**闭环可验证**」；

### 3 · 限流（**四层**）

| 层 | 拦什么 | 现状 |
|---|---|---|
| **L1** | **per-IP 短窗** —— 一个人狂点 · **含并发上传** | 🔴 **新增**。⚠️ **真 IP 在 `X-Forwarded-For` 第一跳** —— `request.client.host` 在平台上拿到的是**内网代理地址**（实测 `21.0.0.1`） |
| **L2** | **全站【日】额度**（100 万 token/日） | ✅ 已有（`token_config.py:41` `GLOBAL_DAILY_TOKEN_LIMIT`） |
| **L2b** | 🔴 **全站【总额】度** —— **"用光即停"** | 🆕 **新增**。⚠️ 见下 |
| **L3** | **单请求上限** | ✅ 已有（`MAX_SINGLE_CALL_COST` 等） |

#### 🔴 L2b 为什么非加不可：**口径错配**

```
token_config.py:41    GLOBAL_DAILY_TOKEN_LIMIT = 1_000_000   # 【每日】
token_tracker.py:330  WHERE created_at >= CURRENT_DATE       # 跨天自动翻页
```

⇒ 那是一个 **100 万/天** 的闸门，而业务方手上的是 **100 万【总量】** 的额度。
**两把尺子量纲不同** ⇒ **一天就能烧光全部额度，而闸门第二天照常重置。**
⇒ 必须补一条**与额度同口径**的总额闸门。

📌 **一条好消息**：`embedding_client.py` 的调用**已经在记账**（`purpose="embedding"`）
⇒ **"记账"这一环不用重做，缺的只是【口径】。**

#### 3.1 🔴 所有闸门共用**同一个池子**

`ingest`（访客上传）**也烧 embedding token** ⇒ 它必须并进 **L2 / L2b**，
⛔ **不能另开一个只由"问答"计数的池子**。理由：否则"上传"这条路**绕过了限流**。

### 4 · ingest 的**七条**上限（＋两条实测风险）

业务方原话要的三条（「单文件大小上限 · 单次 chunk 数上限 · 每个访客的总 ingest 额度」）
**是起点，不是全集** —— 补齐后是七条：

| # | 拦什么 | 为什么不能少 |
|---|---|---|
| 1 | 单文件**字节**上限 | ⭐ **必须卡在 `await file.read()` 【之前】** —— 见下 |
| 2 | 单次 **token** 上限 | 成本（ingest 与问答**同一个池子**） |
| 3 | 单次 **chunk 数**上限 | ⚠️ **与 token 是【两个量纲】**：token 决定**花多少钱**，chunk 数决定**调多少次 embedding**（单批 ≤20 行）⇒ 决定 2 vCPU 上的**耗时 / 超时** |
| 4 | **每访客 ingest 次数**（100） | 防一人占满 |
| 5 | 🆕 **每访客【库存总量】上限** | 不只是"传了几次" —— **SQLite + 暴力余弦下，检索延迟 ∝ 全站 chunk 总数** |
| 6 | 🆕 **全站 ingest 总额，并进 L2 / L2b** | 见 §3.1 |
| 7 | 🆕 **并发上传** | ⚠️ **"次数"拦不住"同时"** |

> 📌 **量化示例（为什么 2 和 3 都要）**：同样 1 万 token，切成 500 个 20-token 小块 vs 10 个 1000-token 大块
> ⇒ **成本一模一样，批次数差 50 倍。**

#### 4.1 额度的**具体数字**：**每次 1 万 token ≈ 42 KB · 每访客 100 次**

🔴 **这个数是【反推出来的】，不是我拍的** —— 起点是业务方的 **100 万 token 总额度**：

| 上限 | ≈ 多少汉字 | 文件大小 | 能撑多少次上传 |
|---|---|---|---|
| 20,000 token | 2.8 万字 | ~85 KB | 50 次 |
| **10,000 token** ⭐ | **1.4 万字** | **~42 KB** | **100 次** |
| 5,000 token | 7 千字 | ~21 KB | 200 次 |

**⇒ 正确的量级是「几十 KB」，不是「几 MB」。**
⚠️ **这里记录一次我自己犯的错**：初稿我提的是"中档 **5 MB**"，
按 UTF-8 汉字 3 字节 + 汉字≈0.7 token 算，**5 MB ≈ 117 万 token** —— **一次上传就能烧光全部 100 万额度**，
**超了 50 倍**。⇒ **上表是纠正后的版本**，⛔ 不要再用"MB 级"那个量级。

#### 4.2 🔴 两条实测风险（本节真正的重点）

**① `api/api_v1_rag.py:303-304`** —— 上限**必须卡在读之前**：

```python
with tempfile.NamedTemporaryFile(delete=False, suffix=f".{ext}") as tmp:
    tmp.write(await file.read())        # ← 整个文件一次性进内存
```

⇒ **"读完再判大小"等于没判** —— 内存已经吃掉了。
⚠️ **为什么这条不是"锦上添花"**：容器 **8 GiB / `SwapTotal=0`** ⇒ **OOM 直接 kill，没有缓冲**。
⇒ **限额必须卡在 `read()` 之前**（看 `Content-Length` / 流式计数），⛔ **不是读完再拦。**

**② 同一个函数末尾**（`api/api_v1_rag.py:328` `os.unlink(tmp_path)`）——
**中间任何一步抛异常**（解析失败 / embedding 失败）⇒ **临时文件残留**，demo 跑久了 `/tmp` 攒垃圾。
⇒ **修法：`try/finally`。** ⚠️ 这是**独立于限流**的一处缺陷，**一并修**。
