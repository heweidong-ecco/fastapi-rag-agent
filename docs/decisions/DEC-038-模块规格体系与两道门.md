## 🅰️ 决策一：**建 `docs/specs/`，一个模块一份**（业务方定名）

### 备选

| 方案 | 评价 |
|---|---|
| **甲 · `docs/specs/`，一个模块一份文件（采纳）** | ✅ **新增模块 = 加一个文件** ⇒ 天然"一眼看出有什么"；不冲突 |
| 乙 · 一份大表 | ⛔ 会**冲突**（两个 agent 同时改一行）、**越写越长** |
| 丙 · 塞进 `docs/原理/架构.md` | ⛔ **业务方明确否决**：「`docs/原理` 这样写不好」 |

**⇒ 甲。**

### ⭐ 每份 spec 的**价值在那第三节**

四节里 **前三节（做了什么 / 缺什么）读代码也能推出来**，
**只有「⚠️ 看代码会误判的地方」推不出来** —— **那才是这份 spec 的存在理由。**

已写的 8 份里，最典型的三条：

| spec | 看代码会以为 | 实际 |
|---|---|---|
| `hybrid_search.md` | 它是 RRF 的实现 | 🔴 **它是在全仓的【第二份】**（第一份在 `rag_pipeline.py:201`）<br>⚠️ **而测试测的是【第三份副本】** ⇒ **真融合逻辑没被覆盖** |
| `reranker.md` | 重排序做完了 | 🔴 **只在开发机能跑** —— 镜像里没装 torch |
| `quota_limiter.md` | 有限额 | 🔴 **匿名请求完全绕过** |

## 🅱️ 决策二：**硬拦 + 提醒（业务方裁「硬拦」）**

| 触发 | 做什么 | 拦不拦 |
|---|---|---|
| **提交前**（`pre-commit-gates.py` 第 ④ 道门） | **新增了一个 `api/` 下的模块，但 `docs/specs/` 里没有与它同名的那份** | 🛑 **硬拦** |
| **写完 `api/*.py` 后**（`spec-remind.py`，`PostToolUse`） | 提醒更新 spec | ⛔ 不拦 |

**⇒ 分工的判据**：**能机械判的（"新增"是事实）⇒ 硬拦；判不了的（"要不要更新"是判断）⇒ 只能提醒。**

### ⚠️ 已知局限（**照实说，不掩盖**）

**spec 靠人/agent 写 ⇒ 它会过期。** 本仓对这类事有明文教训：

> 「**门挂在别处，就等于没有门**」—— **8 个 PR 一次都没跑过 `/留痕-checks`**

⇒ **所以它同时挂在三处**：`CLAUDE.md`（规矩）· **hook**（硬拦 + 提醒）· **`/specs` 命令**（随时对账）。
**⛔ 但最终兜底是【对账】，不是【门】** —— **对账能查出来，就不算失控**（同 `ROADMAP` 的 `T1–T7` 那个模式）。
