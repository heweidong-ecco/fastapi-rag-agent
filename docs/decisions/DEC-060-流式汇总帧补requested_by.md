## 一 · 要裁的是什么

`api/api_v1_agent.py` 里是 **5 对**「非流式 / 流式」端点。**同一天花板的字段，两侧不一样**：

| 业务 | 非流式端点（响应体） | 流式端点（**汇总帧**） |
|---|---|---|
| langgraph_chat | `:177` ✅ 有 | ❌ **没有** |
| advanced_chat | `:469` ✅ 有 | ❌ **没有** |
| plan_execute | `:682` ✅ 有 | ❌ **没有** |
| memory_chat | `:840` ✅ 有 | ❌ **没有** |
| mcp_chat | `:1195` ✅ 有 | ❌ **没有** |

判据（改前，可打印）：

```bash

grep -n '"requested_by": user_name' api/api_v1_agent.py
```

### 1.1 为什么这不是「小事一桩」

**它是一个静默的形状不一致**：同一个业务的两个入口，**调用方拿到的对象一个是另一个的严格超集**。
从 `/agent/advanced_chat` 切到 `/agent/advanced_chat/stream`，其余字段**长得一模一样**，
**只有它无声无息地没了** —— 而**没有任何用例 / 文档说过这件事**。

⚠️ 这类差异**最难发现**：它不是"报错"，是"少一个键"。

### 1.2 链 D 是**计划承诺过、实现没落地**

`B1` 的原计划（**仓外**，`/Users/heweidong/.claude/plans/misty-wandering-bee.md`）**§八**明写
`/agent/plan_execute/stream` 的末帧形状是：

```
{goal, plan, execution_result, requested_by}
```

**`#78` 发出来时没有 `requested_by`。** ⇒ 这不是"要不要加"的新想法，**是补一条没兑现的承诺**。

## 四 · 裁决与理由

> ### **选 乙 · 5 条流式端点一起补（业务方 2026-10-04 裁定：「补上，5 条流式端点一起对齐」）。**

| 标准 | 甲（只补 D） | 乙（5 条一起） | 丙（改末帧形状） |
|---|---|---|---|
| **1 · 两侧一致** | 🔴 只一致 1 对 | ✅ **5 对全一致** | ✅ 但**换了一种不一致**（改了整个形状） |
| **2 · 弄坏消费方** | ✅ 不会 | ✅ **不会**（纯加法） | 🔴 **会**（前端按现形状解析） |
| **3 · 成本** | 1 行 + 1 断言 | 5 行 + 5 断言 | 大（要重写前端解析 + 契约文档 + 全部用例） |
| **4 · 反悔成本** | 低 | 低 | 高 |

### 4.1 落在**汇总帧**上，⛔ 不是逐 token 的 content 帧

逐 token 帧（`{"content": …}`）是**增量**，不是**终态** —— `requested_by` 是元数据，
**放增量里 = 每块都重复一遍**（且第一块还没聚合完，值也无意义）。
⇒ **终态信息只放终态帧**，与非流式兄弟（一个响应体 = 一个终态）**同语义**。

### 4.2 写法**刻意与非流式兄弟逐字同形**

非流式那两条 `**summary` 型端点（`:177` / `:840`）写的是：

```python
{
    ...
    "requested_by": user_name,     # ⚠️ 在 **summary 之前**
    **summary,
}
```

⇒ 流式侧照抄这一形状：`{"thread_id": thread_id, "requested_by": user_name, **summary}`，
⛔ **没有新立第二种写法**。

⚠️ **放前放后会不会被 `**summary` 覆盖？** —— **不会**，已核：`summarize_agent_result`（`:82`）
**只返回** `status` / `answer` / `pending_tool_calls` 三样，**不含** `requested_by`。
（判据：`grep -n "def summarize_agent_result" -A 45 api/api_v1_agent.py | grep "return"`。）

### 4.3 范围边界：**RAG 的 `/rag/stream_search` 不在内**

它**没有汇总帧** —— 帧序是 `content… → [DONE] → sources`（`DEC-059` §五 · 本批任务 3 刚给它补了钉子）。
⇒ **没有放 `requested_by` 的落点**，⛔ 不是"漏了"。要给它补，得**先裁"加不加汇总帧"**，那是另一件事。

### 4.4 ⚠️ 顺带纠正计划里一个**吓人的假信号**：`!` 不成立

原计划 §Task 4 的提交标题写的是 `feat(流式)! …`（`!` = 破坏性变更）。
**执行到那一步核实：不成立** —— **加字段是增量的**，老客户端照常解析。
⇒ **已去掉 `!`**（`b0b1835` 的 subject 是 `feat(流式): …`）。
📌 这与本仓「**别留一个吓人的假信号**」同一条道理，也是判据纪律第 9 条（**改口径立刻全仓搜那个词**）的现场应用。

## 五 · 由此立的一条规矩

> ### **同一个业务有「流式 / 非流式」两个入口时，两者的【终态对象】必须同形。**
> ### 「流式少一个键」不是设计，是**债** —— 而且它是**静默的**（不报错、用例不红）。

**配套两条**：

1. **终态信息只放终态帧**（汇总帧），⛔ 不放逐 token 的增量帧。
2. **加字段前先问一句「这是破坏性变更吗」** —— 加字段**不是**；
   ⛔ 别在 commit type 上打一个不成立的 `!`。
