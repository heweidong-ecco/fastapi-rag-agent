## 一 · 结论先行 —— 可执行的要求（**十一条**）

### 2.7 🔴 分节与篇幅（**第 11 条的正身** · ✅ 2026-10-08 业务方已裁）

**要求**：**每篇 = 一个主题，500–1500 字；用 `##` 分节（节数 4–6）。**
⛔ **本文件【不规定"每节多少字"】** —— 理由见下。

**为什么是这条**（🔴 这条推理是**本仓的**，⛔ 不是调研结论）：

| 事实 | 出处 | 置信度 |
|---|---|---|
| 本仓分块器 `chunk_size=500` 是**字数上限**，且**先按 `["\n\n", "\n", "。", "！", "？", "，", " ", ""]` 切** | `api/chunker.py:14-21` | 🟢 实测 |
| 🔴 **它是"攒到 500 为止"**（`RecursiveCharacterTextSplitter` 的语义）⇒ **节很短时，相邻的节会被【合并】进同一块** | 同上 | 🟢 |
| **现有 9 篇实测**：全篇 **498–666 字** · 节数 **4–6** · **各节 40–196 字** | `testdata/isolation-seed/*.md`，python 逐节量（见 §六 判据 3） | 🟢 **实测** |
| 本仓上传端点**按扩展名猜档**：`"legal" if ext == "pdf" else "technical"` ⇒ **`.md` 全吃 `technical`（500/50）** | `api/api_v1_rag.py:326` | 🟢 实测 |

⇒ ⚪ **结论（已裁）**：
- **节太长（>500 字）** ⇒ 节内被切断 —— **可接受**（切点会落在句号上，同节两块语义连续）
- **节太短** ⇒ 相邻节**被合并**成一块 ⇒ **块的语义变宽**；⚠️ 但同一篇同一主题 ⇒ **仍然连贯**
- ⇒ 🔴 **真正承重的要求是「一篇一个主题」**；**节长是次要的**，⛔ 不必去凑某个区间

🔴 **修正记录（2026-10-08 · 本条初稿是错的）**：
初稿我写的是「**每节 300–600 字、每篇 800–1500 字**」—— **那是我凭"500 是上限"想当然推的**。
实测现有语料**每节只有 40–196 字**，与那个区间**差一个量级**。
⚠️ **若照初稿执行，现有 9 篇【一篇都不达标】** ⇒ 那是**尺子定错了**，⛔ 不是语料错了。
📌 **同族前科**（本仓反复栽的那一类）：**拿一个想当然的量当判据，而没先量一次真身**。

## 三 · 🎯 类别：建议 **4 类内容 + 1 个负样本设计**

> 🔴 **这一节是业务方点名要的**（「有几个不同类别」）。
> ⚪ **以下是我按调研 + 本仓情况提的**，⛔ **不是行业硬规定** ⇒ **要你拍**。

### 3.1 为什么"要分几类"（依据）

| 依据 | 置信度 |
|---|---|
| 语料应**按功能/使用场景划分**，提高召回准确率与回答速度 | 🟢 |
| 文档**类型会影响分块策略**（专业手册适合大块、QA 适合小块）⇒ 混在一起就没法按类调 | 🟢 |
| 「**per-domain 分块**（按文档类型路由到不同 chunker）在同路线下能带来 **5–15 点召回提升**」 | 🟡 单一来源（Future AGI） |
| 金标测试集要**按文档类型分层** | 🟢 |

### 3.2 建议的 4 类（**每类各自能测一种能力**）

| # | 类别 | 形状 | **它能测什么** | 置信度 |
|---|---|---|---|---|
| **A** | **产品 / 规格类** | 型号、参数表、版本差异 | **单跳精确事实**（型号/数字/错误码） | 🟢 来源：Azure/Northwind 的 D1 就是这类；评测清单里「exact error codes/model numbers」是独立一类 |
| **B** | **流程 / 制度类** | 步骤、时限、审批条件 | 🔴 **多跳**（条件要叠加：工龄 + 当地法 + 政策 ⇒ 谁能休） | 🟢 来源：Northwind 的 D2 与 D1 交叠正是为测这个 |
| **C** | **FAQ / 问答类** | 口语化问句 + 短答 | **复现用户真实问法**（口语 ≠ 书面） | 🟡 |
| **D** | **数据 / 报告类** | 含数字、表格、同比 | **数字与表**（表在中文资料里被点名要预处理好） | 🟢 |

### 3.3 加一个**负样本设计**（⛔ 不是第 5 个内容类别）

| 要求 | 依据 | 置信度 |
|---|---|---|
| 🔴 **语料里必须有一块"其它 4 类都不覆盖"的主题** —— 访客问它时，系统**应当拒答**（⛔ 不是编） | 调研里「no-answer / unanswerable questions」被反复列为**独立评测类**；Ragas 的测试集也单列 | 🟢 |
| 🔴 **本仓已有现成的机制**（`REFUSAL_SENTENCE` / `no_answer` 帧 / `/trace` 页的解释分支）⇒ 这块**能让它被看见** | 本仓 `api/api_v1_rag.py` · `DEC-091` · `DEC-093` | 🟢 **本仓实测** |

本仓已有 `testdata/isolation-seed/` 的 **9 篇中文语料**（**3 主题 × 3 篇**，每篇约 1000 字）：

## 四 · 问题类型覆盖（**语料要能答出什么**）

> 🔴 **这一节决定"语料合格没合格"** —— 语料不是"读起来好"就行，是**要能撑起一组像样的问题**。

| 问题类型 | 占比（调研给的） | 语料要满足什么 | 置信度 |
|---|---|---|---|
| **事实型（单跳）** | **50%** | 每类都有**明确、唯一**的事实 | 🟢 |
| **摘要型** | **20%** | 单篇内**跨段落**能汇总 | 🟢 |
| **多跳 / 跨文档** | **20%** | 🔴 **两篇之间要真有交叠**（§一 第 9 条） | 🟢 |
| **模糊型** | **10%** | 同一概念有**多种说法** ⇒ 测召回 | 🟢 |
| **不可答 / 拒答** | ⚠️ **调研说「应排除」** —— 但那是在测"上下文长度效应"的语境下 | 🔴 **本 demo 要【保留】**（§一 第 10 条） | 🟡 ⚠️ **来源与我们的目的不同，别照抄** |

⚠️ **一条要写清的差异**：调研里那份学术数据集把**不可答问题排除**，理由是「它不提供关于上下文长度的判别信息」——
而**我们的目的不是测上下文长度，是演示"无据拒答"这个功能** ⇒ **我们的取向与它相反**，⛔ 别把它当反例。

## 五 · 规模、预算与两条发现

### 5.1 规模建议（⚪ 本仓推断 · **要你拍**）

| 量 | 建议值 | 理由 |
|---|---|---|
| **篇数** | **20–40 篇** | 少于 20 ⇒ 4 类 × 5 篇都凑不满；多于 40 ⇒ 镜像与检索延迟上去了 |
| **每篇字数** | **500–1500 字** | ⚠️ **与 §2.7 同一条口径**（一篇一个主题） |
| **总量** | **1–6 万字** | ⇒ ≈ **1.1–6.6 万 token** |

⚠️ **一处实测更正**：`testdata/isolation-seed/README.md` §三 写的是「每篇**约 1000 字**」，
而**实测是 498–666 字**（§六 判据 3 的输出）⇒ **那个「约 1000」偏高约 40%**。
🔴 **本文件用【实测】那组数**；⛔ 上面这条建议**不是**从那句抄的。

**预算核算**（连 `DEC-098` §2.3）：免费额度 **100 万 token** ⇒ 上述总量占 **1–7%**。
⛔ **别按"100 万"去铺语料** —— 那是**额度**，不是**目标**。

### 5.2 🔴 发现①：**TPM 100 万/分钟 ⇒ 灌库脚本必须限速**

`DEC-098` §2.3 记的模型限流是 **RPM 24,000 · TPM 1,000,000**。
⇒ 3–6 万 token **一次打满也不会超分钟额度**（🟢），**但**：
⚠️ **embedding 调用是【分批】的**（本仓单批 ≤20 行）⇒ 脚本要按批走，⛔ 别一次性全发。

### 5.3 🔴 发现②：本仓**已经**按文档类型分档分块（⛔ 我第一版漏看了）

🔴 **2026-10-08 更正**：本节初稿只写了 `CHUNK_CONFIGS["default"]`，**漏了它其实是一张【分档表】**。
实测（`api/chunker.py:16-21`，🟢 **本仓实测**）：

| 档（`doc_type`） | `chunk_size` / `overlap` |
|---|---|
| `default` | **500 / 50** |
| `technical`（技术文档） | **500 / 50** |
| `legal`（法律合同） | **800 / 100** |
| `report`（财报、报告） | **800 / 100** |
| `article`（长篇文章） | **1000 / 200** |

⚠️ **`api/chunker.py:32`**：`config = CHUNK_CONFIGS.get(doc_type, CHUNK_CONFIGS["default"])`
⇒ **传了 `doc_type` 就分档，不传就吃 `default`**。

| 依据 | 值 | 置信度 |
|---|---|---|
| 中文资料：专业文献 / 技术手册 / 长文 ⇒ **1024–2048 字符**；概念定义 / QA / 代码 ⇒ **256–512** | 中文资料 | 🟡 |
| `RecursiveCharacterTextSplitter` 默认 **800**（range 200–2000）· overlap 150 | 学术/工程资料 | 🟡 |

⇒ ⚪ **推断（要你拍）**：
- **本仓的高档（`legal` / `report` 800、`article` 1000）与调研的"1024–2048"仍差一档**；
- **`technical` 只有 500** —— 而调研说技术手册属"适合大块"那一类 ⇒ **这一档可能偏小**；
- ⚠️ **但语言不同**：调研给的字符数是**英文**语境，**中文一个字的信息量更高** ⇒ ⛔ **别直接搬数**。

⚠️ **改分块 = 改行为面**（要重烤 + 可能触碰既有守卫）⇒ **本节只登记，⛔ 不建议现在改**。

🔴 **对 `乙` 的直接影响（这条是承重的）**：分档靠 `doc_type`，而它**是【按扩展名猜的】** ——
`api/api_v1_rag.py:326`（🟢 **本仓实测**）：

```python
doc_type = "legal" if ext == "pdf" else "technical"
```

⇒ 🔴 **`technical` 档（500/50）实际上被用在【除 PDF 外的一切】** ——
包括 `.md` / `.txt` / `.docx`。
⚠️ 而 §3.2 建议的**四类语料**里，**只有 A（产品/规格）像 `technical`**；
**B（流程/制度）更像 `legal`** · **D（报告）更像 `report`** —— **它们现在全都落 `technical`（500/50）**。

📌 **对 `乙` 的落法提示**：若语料**全用 `.md`**（§2.2 推荐），那**四类都吃 500/50** ——
⇒ 「按类型分档」这件事**在当前实现下【不会发生】**，⛔ 别在语料要求里假设它会发生。

> ✅ **2026-10-08 业务方已裁：`doc_type` 的推断【不改代码】，改【语料要求】** ——
> ⇒ 落点 = **§2.7 第 11 条**（`##` 一节 300–600 字 ⇒ 让 500 这个上限咬不到语义中间）。
> 理由：**语料是我们控制的，比改代码便宜且无行为风险**。
> ⚠️ **本节的三个候选** —— ① 不改代码、② 给上传接口加可选 `doc_type`、③ 改推断规则 ——
> **选了 ①**；② ③ 的代价分别是"改接口契约"与"影响所有上传（含访客）"。

### 🔴 判据 3 的命令（**已实测**，2026-10-08）

⛔ **别用 `awk 'length($0)'` 替它** —— **`awk` 数的是【字节】，中文一字 3 字节**：
本机实测，同一条命令在同一个文件上给出 **1459**，而真身是 **643**（`python3 len`）。
🔴 **这就是本仓那条**：「**拿一个没量过的代理量当判据**」—— 字节数看着"像字数"，**它不是**。

```bash
python3 -c "
import sys, re, pathlib
for f in sorted(sys.argv[1:]):
    p = pathlib.Path(f)
    if p.name == 'README.md': continue
    text = p.read_text(encoding='utf-8')
    secs = re.split(r'^## ', text, flags=re.M)
    body = [len(re.sub(r'\s', '', s)) for s in secs[1:]]
    print(f'{p.name:28} 全篇={len(text):4}  节数={len(body)}  各节={body}')
" testdata/isolation-seed/*.md
```

**实测输出**（现有 9 篇 —— ⛔ **是真身，不是合格线**）：
