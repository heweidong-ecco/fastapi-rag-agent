## 二、为什么这是**第二次**（沿革，⛔ 不重写历史）

本仓早就知道这条：

- **规矩**：「`gh pr merge --squash` **不带 `--subject` / `--body`** 会把多条 commit 正文拼进主干 commit」
  —— 记在 Agent 的长期记忆与当日的对话里，**合并前刚复述过一次**。
- **前科**：2026 年更早的一次是 **114 KB / 45 条**。

⇒ 🔴 **知道 ≠ 会做。** 这条提醒**只挂在"谁的记性"上** ——
而本次真正的风险点是「**谁按下那个按钮**」，提醒**没有作用在那一端**。

## 三、防错措施（**这次要落成动作，⛔ 不再只是文字**）

> 本仓立场：**只有文字就漏，结构才执行**。⇒ 下面两条**都必须是能跑的东西**。

| # | 措施 | 为什么这样 |
|---|---|---|
| **1** | ⭐ **合并这件事由 Agent 来做**，用 `gh pr merge --squash --subject "<标题>" --body "<正文>"` | 让**执行合并的那个进程**自己带上参数 ⇒ **不需要任何人记得** |
| **2** | 若由人**在网页上点** ⇒ **点之前先把那段 squash 说明整个清空重写** | 网页上的默认值就是"把各条 message 拼起来" ⇒ 清空 = 把默认值变成空 |

⚠️ **两条都是"改默认做法"，⛔ 不是"下次注意"**（后者本仓已证无效 —— 它就是本次失手的形态）。

## 四、判据（**可打印** · 本目录规矩：⛔ 只写"下次注意"没用）

```bash
# ① 主干上最近一条提交的正文有多长
git log -1 --format=%B origin/main | wc -c
#   ✅ 正常：**几百字节**（标题 + 一段说明）—— 本次修复后实测 **1293**
#   🔴 异常：**上万字节** —— 那是"各条正文被拼进来"了
#      · #135 那次实测 **30511**（13 笔）
#      · 更早一次 **114 KB**（45 笔）

# ② ⚠️ 反证检验：换一条提交，输出会不会变？
git log -1 --format=%B origin/main~1 | wc -c
#   ⇒ **会变**（`b4363e5` 那次是 30511）⇒ 这条尺子确实在测"**那一条**提交"，⛔ 不是个常量
```

⚠️ **这条尺子测的是"长度"，⛔ 不是"内容对不对"** —— 它只能告诉你**默认说明没被覆盖**，
**判定不了**合并说明写得好不好（那件事没有自动判据）。

📌 **另外这条只在【合并之后】才量得到** —— ⇒ 它是**事后判据**，
真正的动作在前面（§三 那两条）。**别把事后判据当预防措施。**
