## 二、教训(可复用的判断规则)

1. **`--hard` 是"工作区级"的破坏,不是"提交级"的。**
   凡意图是"**我只想撤销一个提交**" ⇒ **绝不能用 `--hard`**。
   能用的是 `--soft`(只动 HEAD)或 `--mixed`(动 HEAD + 索引)。**`--hard` 只在"我确实想丢弃工作区改动"时用。**

2. **撤销前的第一动作是 `git status`,不是 `git reset`。**
   判据:**「这条命令跑完,我损失的最大范围是什么?」**
   对 `reset --hard` / `checkout -- .` / `clean -fd` / `stash drop`,
   **答案永远是"全部未提交改动"** —— 而这四个字必须在敲之前想一遍。

3. **频繁 `git add` 是一种保险。** 本次 11 个文件里,10 个因**进过索引**而被 temp 提交兜住;
   唯一丢的 `check_secrets.sh` v4,**恰恰是唯一只改了工作区的那一个**。
   ⇒ **索引是"最后一道可恢复层"** —— 长时间不 `git add`,就等于把这段工作放在没有网的地方。

4. **"验证"这个动作本身不该有破坏性。**
   我为了验一条只读性质(删除行不触发),付出了"临时提交 + 回退"的代价 ——
   而这两步**都动历史**。正确做法:验证在**不影响主工作区**的地方做
   (临时 worktree / 临时目录里的副本),或者干脆用**只读方式**验证。

5. 📌 **与今天同源的第三条**:`docs/复盘/2026-09-17-给用户的选项里写了没验证的前提.md` 是
   「**动作前没确认那个断言**」;本条是「**动作前没确认那个动作的作用域**」。
   **都是"先做,再想"**。
