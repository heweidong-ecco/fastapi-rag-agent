## 二、教训(可复用的判断规则)

1. **检查点必须逐个时点登记，不许用「开 PR 前」概括整条交付链。**
   本仓的交付链至少三个时点：**①动代码前 ②开 PR 前 ③合并前**。只在 ② 建了门 ⇒ ① 和 ③ 的判据全是摆设。
   ⚠️ **本仓已三次同型**：`DEC-007`（A 级 skill 从判据改成动作）· `DEC` 触发器（`DEC-001~004` 之后断了两个月）· **本次（换了时点）**。
   ⇒ **写判据时同时写：它在哪个动作上被强制执行？答不出 ⇒ 这条判据等于没写。**

2. **凡写进 PR 正文 / 交付物的「后果性断言」，都要有一条当场能跑的命令支撑。**
   "可 revert" 不是形容词，是一个**可验证的命题**（在哪一层 revert？粒度多大？）。
   写它之前先问：**"我用什么命令证明它？"** —— 答不出就别写。

3. ⚠️ **「我已经写下来要补」≠「会补」。**
   PR 正文里那句「合前补」，写下去的**那一刻感觉已经处理了**（有个交代），**实际等于没有执行者**。
   **写在文档里的待办，和没写是同一种结果** —— 除非它绑在一个**必然发生的动作**上。
   （本仓真正生效的那几次，全都绑在动作上：commit 时的钩子、开 PR 前跑 skill。）

## 四、对机制/母体 Kit 的反馈

> 本仓若暴露了治理机制本身的缺陷 → 提请回写体系。本仓不留登记表。

- **KD 候选：把 checklist 的表头从「时点」改成「时必须发生的动作」。**
  - **线索**：本仓的 A 级 skill 表按**时点**分行（动代码前 / 开 PR 前 / 合并前 / 遇到 bug…），
    但真正落地成"动作"的只有**开 PR 前**那一个。其余时点的判据**一条都没被执行过**。
  - **证据**：`ROADMAP.md` 的 A 级表 + 本次 PR #29 的实测（两条"合并前"skill 命中未调）。
  - **影响**：**表越长，看着越完备，越像已经管住了** —— 而实际生效的比例是 1/6。
    这是"**形式完备掩盖实质空缺**"，比一张短而全生效的表更危险。
  - **最小修复建议**：每个时点必须写出**一个可执行动作**（"跑 X" / "调 Y"），
    **写不出动作的时点 ⇒ 该条判据作废，从表里删掉**（依 `Product/` 的减法优先）。
