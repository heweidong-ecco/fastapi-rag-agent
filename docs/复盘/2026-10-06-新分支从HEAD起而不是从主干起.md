# 复盘 · 新分支从 `HEAD` 起，而不是从刚更新的主干起

**日期**：2026-10-06 · **触发**：`/handoff` 第 1 步核对「这次的账」
**结论**：`PR #106` 一开出来，GitHub 上的 diff 是 **25 文件 / +4134 −66** —— 看着像把**刚合并的 `F1` 整批又塞了一遍**。
**而本地那几条最常用的命令，全打「正常」。** 修法是一次 `rebase --onto` + `push --force-with-lease`。

---

## 一 · 现象（时间线）

| # | 动作 | 结果 |
|---|---|---|
| 1 | `#105`（`feat/approvals-page`）被合并 | 主干 `f180ecf`（**squash 合并**） |
| 2 | `git fetch` + 把本地 `main` 推到 `f180ecf` | ✅ 这一步**是对的** |
| 3 | `git checkout -b docs/roadmap-stale-next` | 🔴 **它从 `HEAD` 起** —— 而 HEAD 还是 `feat/approvals-page` @ `a1710a6` |
| 4 | 两条 doc commit + `git push` + 开 PR | GitHub 三点 diff ⇒ **25 文件 / +4134 −66**；`mergeStateStatus: DIRTY` |
| 5 | `git rebase --onto origin/main a1710a6 docs/roadmap-stale-next` + `push --force-with-lease` | ✅ 三点 diff ⇒ **3 文件 / +19 −4** |

---

## 二 · ⚠️ 为什么【本地看不出来】（**这一段是重点**）

把错 base 那支（`a1710a6`）与 `origin/main` 比，实测输出：

| 命令 | 打在错 base 的分支上 | 读起来像 |
|---|---|---|
| `git status --short` | 干净 | 正常 |
| `git log --oneline origin/main..HEAD` | **2 条**（就是那两条新 commit） | 正常 |
| `git diff --stat origin/main HEAD` | **空** | ✅ **完全正常** |
| `git diff --stat $(git merge-base origin/main HEAD) HEAD` | 只有那 3 个文件 | 正常 |
| **GitHub 的三点 diff** | **25 files, 4115 insertions(+), 62 deletions(−)** | 🔴 像「整批又塞了一遍」 |

**根因**：`F1` 是 **squash 合并**的（`a1710a6` → `f180ecf`）—— **树一样、sha 不同**。
⇒ **两点 diff 比的是【树】**，两边的树**一模一样**，所以打**空**；
⇒ **三点 diff 从【merge-base】起算**，于是把整批 `F1` 算成「这一支带来的」。

> 🔴 一句话：**在本仓，「内容对不对」与「这一支是从哪儿分出去的」是两根轴** ——
> 本地那几条常用命令**只管前者**，而 GitHub 评审页看的是**后者**。
> 📌 同源：`docs/复盘/2026-09-20-diff行序伪影被当成集合差异.md`（**也是"两点 vs 三点"这一族**）。

## 三 · 根因

**不是「没确认在哪个分支」** —— 我知道自己在 `feat/approvals-page` 上，也**正是想开一条新分支**。
错在 **`git checkout -b <名>` 的默认 base 是 `HEAD`**，而 `checkout -b X` 这个写法**读起来像「从主干开」**。

⚠️ **同族前科 · 且上一轮的防错措施没兜住**：
`docs/复盘/2026-09-17-切开点3落在错分支.md`（**忘了切回 `main`** ⇒ 改动混进上一件事的分支）——
那次给的防错措施是**「工作习惯：开工前先跑 `git branch --show-current`」**。
**它抓不到今天这一种**：我今天**确实在开新分支**，`--show-current` 打出来也「对」。

⇒ 这正是本仓自己那句：**「只有文字就漏，结构才执行」**（`agent-pitfalls-kb` `A2`）。
**这次补的是一条【命令】，不是又一句「注意」。** 见 §五。

## 四 · 判据（**可打印**）

```bash
test "$(git merge-base origin/main HEAD)" = "$(git rev-parse origin/main)" \
  && echo "✅ base 对：本支就是从主干分出来的" \
  || echo "🔴 base 错了：本支从别处分出 —— ⛔ 先别开 PR"
```

**反证检验**：把结论取反（「这支**不是**从主干分的」）⇒ 上一条命令**会变**（打 🔴）⇒ **它确实在测那件事。**

**实测**（2026-10-06）：

* 已修好的 `docs/roadmap-stale-next` ⇒ ✅（两个 sha 都是 `f180ecf`）
* 临时的错 base 支（`a1710a6`）⇒ 🔴（merge-base = `ffb2c54` ≠ `f180ecf`）

⚠️ **栈式 PR 是例外** —— 那时 base **有意**不是 `main`（`docs/规范/开发规范.md` §2.7）。
⚠️ **开 PR 之后的第二道**：`gh pr view <n> --json changedFiles,additions,deletions`
—— **拿它跟"我这次到底改了几个文件"对**，对不上就是 base 出问题了。

## 六 · 对机制 / 母体 Kit 的反馈

* **<KD-n 候选：「分支 base 错置」是测试抓不到、且本地命令**看不见**的一类静默错误。**
  线索：`git status` 干净、`git log origin/main..HEAD` 只有本意中的 commit、
  **`git diff --stat origin/main HEAD` 打空** —— 三条全「正常」，而 GitHub 上多出 4134 行。
  证据：`git diff --stat $(git merge-base origin/main <支>) <支>` ⇒
  `25 files changed, 4115 insertions(+), 62 deletions(-)`（错 base 支实测）。
  影响：评审页失真 ⇒ 评审人以为你重做了整批（本例差点如此）；`git revert` 粒度也被破坏。
  **最小修复建议**：把「新分支 base 校验」做成**一条命令**（§四），并**与"开 PR 前跑 `/留痕-checks`"
  同级** —— 都是「到了某个时点必须跑一条命令」。⚠️ **⛔ 不要再写成"注意一下"**：
  `2026-09-17` 那份就是这么写的，**两周后同族复发**。
