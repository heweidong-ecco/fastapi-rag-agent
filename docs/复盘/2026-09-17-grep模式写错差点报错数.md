# 复盘 · grep 模式写错,差点报出一个错的「0 次」(2026-09-17)

> 依据:源自 `Product/agent-eval-gate/docs/复盘/模板-复盘.md`(同体系模板,本仓为对齐沿用)。
> **纪律**:复盘写「**为什么**」,不写「谁的问题」;每条错误必须有**根因**与**防错措施**,没有就写「待查」,不许空着。
> **分记原则**:同一天的多件事,**根因不同就分记**(各自一份),不合并。

- 范围:业务方提问「切开点 3 是否有使用 skills」后的**取数核查**
- 参与:Agent 单方
- 结论:**"查不出来"和"真的没有"长得一模一样** —— 而这次差点把前者当成了后者

## 一、错误清单

| # | 现象 | 根因 | 影响 | 状态 | 防错措施 |
|---|---|---|---|---|---|
| 1 | 核查 Agent 调用次数时,我用 `grep -o '"type":"tool_use","name":"Agent"'` 得 **0 次** | ⚠️ **JSON 里 `id` 夹在 `type` 与 `name` 之间**:实际是 `"type":"tool_use","id":"call_…","name":"Agent"`。**我的模式形状与实际数据不符** | 若直接采信,**会向业务方报出一个错的「0 次」** —— 而真实是 **11 次** | **已修**(换正确模式后得 11) | 见教训 1–3 |

**注意错误的性质**:这次**不是"算错了",是"查不到却当成没有"**。
`grep` 返回 0 时,**它不会区分"确实没有"与"我的模式错了"**。

## 二、教训(可复用的判断规则)

1. **0 命中必须先自证模式有效。** 判据:**拿一个"我明知存在"的样本去跑同一个模式** ——
   若它匹配不到,说明**模式错,不是数据没有**。
   (本次立刻可用:同一文件里 `"name":"Skill"` 是能查到的,说明 JSON 结构可查 —— 只是我的字段序假设错了。)
2. **写模式前先看一条真实样本。** 别凭对 JSON 形状的记忆下笔 ——
   先 `grep -o '.\{0,40\}"name":"Agent".\{0,40\}'` 打出一条**原始上下文**再决定模式。
3. ⚠️ **"查不出来"与"真的没有"产出物上完全一样。** 这条与本仓已记过的
   `Product/CLAUDE.md`「**默认值填充**」是同一类风险 —— **没读到 ≠ 没有,要区分**。

## 三、行动项

| 行动 | 归属 | 状态 |
|---|---|---|
| 用正确模式重跑,得 Agent=11 / Skill=6 / Task=0 | Agent | ✅ 已完成 |
| 把该模式写进结论里(让业务方可复核) | Agent | ✅ 已写在会话回复中 |
| 修正过程中先打一条原始样本再定模式 | Agent | ✅ 见教训 2 |

## 四、对机制/母体 Kit 的反馈

- <KD-n 候选:**「判据写法决定结论」在本仓 24 小时内出现了三次**。
  线索:① 本复盘(grep 模式)② `docs/规则草稿-规则必须绑定路径.md` 的误判源(根治不全)
  ③ `docs/skill-适配体检` 首版(只对两个根)。
  证据:三次都是**"用了不完整的判据,却输出了确定结论"**,且**产出物上看不出判据不完整**。
  影响:这类错误**不会被测试抓到**,只会被"恰好知道真相的人"抓到 —— 本次是业务方问了一句才发现。
  最小修复建议:**凡给出"0 / 无 / 不存在"这类否定结论时,必须附一句自证** ——
  「我用什么模式查的、它能不能查到已知存在的样本」。>
